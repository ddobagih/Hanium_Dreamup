# WalkSafe Android Gateway

## 2026-09-30 현재 작업 안내

이 README는 현재 소스·계약 안내다. [인수인계 시작 문서](../../docs/handoff/2026-09-30/README.md), [Part B: Gateway·Backend 분담](../../docs/handoff/2026-09-30/part-b.md), [현재 상태·검증 범위](../../docs/handoff/2026-09-30/status.md)를 먼저 확인한다. 실제 Android HTTP 클라이언트의 JVM→Gateway→Backend 연동 근거와 전체 Gateway 시험의 남은 실패·후속 재검증은 상태 문서에서 구분한다. 실제 Android Activity·최신 APK 설치·운영 서비스 배포의 완료 근거는 아니다.

HTTP 계약은 [`openapi.json`](openapi.json), 경로·method·auth·body·query·deadline·family와 개인정보 변형의 공통 판정은 [`src/route-registry.ts`](src/route-registry.ts), dispatch는 [`src/routes.ts`](src/routes.ts)를 함께 확인한다. Node adapter·telemetry·RAW relay도 같은 registry를 사용한다. 구조와 검사 진입점은 [현재 코드 지도](../../docs/guides/code/android-gateway.md)를 따른다.

Android가 사용하는 가입·세션·현장·음성 API와 앱 밖 개인정보 권리요청·통합 동의 제어면을 제공하는 독립 Node.js 22 + TypeScript 서비스입니다. Next.js, React, Web/PWA 런타임을 사용하지 않습니다.

## 현재 권한 경계

- 상태: `NOT_DEPLOYED` — 현재 구현·로컬 계약 검증과 실제 배포를 구분합니다. 기능별 최신 결과는 위 상태 문서를 따릅니다.
- 이 패키지의 테스트 통과는 운영 배포, 실제 휴대전화 연결, 정식 시험 또는 출시 승인을 뜻하지 않습니다.
- 실제 운영 URL은 이 저장소에 고정하지 않습니다.
- 백엔드는 정확히 `http://127.0.0.1:8000`만 허용하고 외부에 직접 노출하지 않습니다.

## 공개 계약

공개 경로와 메서드는 다음 표와 OpenAPI·route registry를 기준으로 확인합니다. 후행 슬래시와 그 밖의 경로는 404입니다. 허용하지 않은 메서드는 경로별 인증·은닉 순서를 거쳐 405 또는 인증 전 404로 처리하며, `/privacy/rights`의 `control` 변형은 별도 검증·폐기 응답을 유지합니다. 운영용 `GET /internal/health`(프로세스 liveness)와 `GET /internal/ready`(저장소·outbox·Backend/Voice readiness)는 loopback peer에만 응답하고, 그 밖의 peer에는 404입니다. S19-57: readiness는 공유 원장(보행 원장 shard 16개, 계정 삭제 원장, 개인정보 권리 원장) 파일이 암호화 상한의 90% 이상이면 파일 metadata(lstat)만으로 not ready를 반환합니다(원장을 읽거나 복호화하지 않음). 한 사용자의 포화가 전체 서비스를 빼지 않도록 설치별 동의·actor별 세션 파일은 제외합니다. 응답 본문은 `{status}`만 유지하고, 포화 원장 이름은 바뀔 때마다 한 번 서비스 로그(stderr)에 남깁니다.

모든 응답에는 `Cache-Control: no-store`를 설정합니다. 가입 relay는 exact JSON key와 성공 응답 schema를 검사하고, Backend 오류에서는 허용된 status와 code만 재구성합니다. 새 계정 비밀번호(`AccountCreateRequest.password`)는 NUL 없는 12~128 code point여야 하며 그 밖의 길이는 Backend 호출 전 422 `account_create_request_invalid`로 거부합니다. 흔하거나 추측하기 쉬운 비밀번호는 Backend가 400 `account_password_too_common`으로 거부하고 Gateway는 비밀번호를 반사하지 않고 그 code만 전달합니다. 로그인(`AccountPasswordSessionLogin`)은 기존 계정 호환을 위해 10~128 code point를 계속 허용합니다. 계정 이메일 local part는 ASCII만 허용합니다. domain은 `domainToASCII()`로 IDNA ASCII(`xn--` punycode 포함) 소문자 형식으로 변환한 값만 Backend로 전달하며, Backend는 이 Gateway 변환 결과를 전제로 합니다. 변환할 수 없거나 형식이 잘못된 이메일은 원문을 반사하지 않는 422로 거부합니다. Backend 인증의 429/503과 안전한 `Retry-After`는 같은 no-store status로 투영합니다. 이메일 OTP relay는 `WALKSAFE_GATEWAY_TRUSTED_IP_HEADER`에서 읽은 단일 IP를 canonical 형식으로 검증한 뒤 Gateway가 `x-walksafe-client-ip`를 새로 설정하며, 클라이언트가 보낸 동명 헤더는 전달하지 않습니다. 이메일·생년월일·IP·OTP·비밀번호·enrollment handle·동의 선택은 telemetry나 로그에 넣지 않습니다. 요청 telemetry(`walksafe.gateway-telemetry.v3`)는 Response 객체가 준비된 시점의 `walksafe.gateway.request.prepared`와 body 전달이 끝난 시점의 `walksafe.gateway.request.finished`(`outcome`: `completed`=body 전체를 전송 계층에 넘김, `aborted`=클라이언트 연결 종료 등으로 취소, `stream_error`=헤더 뒤 body 실패, `first_byte_ms` 포함)를 따로 기록하며 지연 시간은 180초까지 잘리지 않습니다. 그 밖의 보호 API에서 백엔드의 401/403은 내부 서비스 자격 증명 실패이므로 Android 사용자 세션 오류로 노출하지 않고 502 `gateway_upstream_auth_failed`로 변환합니다.

음성 경로는 기본 비활성이며 로그인된 general session에서만 열립니다. STT는 허용 audio content type만 받아 내부 multipart로 다시 만들고, Voice의 intent/action/slots/segments/timestamps를 폐기한 뒤 transcript와 네 acoustic 근거 및 고정 model revision만 반환합니다. TTS는 exact `{schema_version,text,request_id}`를 내부 `{text,use_cache:false,allow_fallback:false}`로 바꾸고 WAV type·byte·duration을 재검증합니다. inbound Authorization/cookie/actor/assertion/voice-token은 Voice로 전달하지 않으며 APK나 공개 예제에 내부 token을 넣지 않습니다. 서버 장애는 안전 안내 성공으로 처리하지 않고 Android 내장 TTS·진동 fallback이 담당합니다.

신고 multipart는 `metadata` 문자열 1개(최대 64 KiB)와 `image` JPEG 1개(1 byte~8 MiB)만 허용합니다. 중복 part, 추가 필드, 다른 이미지 형식은 Backend로 전달하지 않습니다.

R1 전송 계약의 `x-walksafe-report-id`, `x-walksafe-report-payload-sha256`, `x-walksafe-report-payload-bytes`는 신고 POST에 세 개 모두 필수입니다. 하나라도 없으면 본문을 읽거나 Backend를 호출하기 전에 422 `report_transport_headers_incomplete`로 거부합니다. 모두 있으면 canonical 형식을 검증한 정확한 값만 Backend로 전달합니다. status GET은 세션에서 확인한 FIELD actor와 account generation만 전달하며 다른 actor·누락 actor·알 수 없는 신고는 같은 404로 숨깁니다. 성공 응답은 `PERSISTED`, 사용자 상태, 동일 transport receipt만 허용하고 Backend의 다른 필드와 임의 헤더는 폐기합니다.

사용자 신고 열람·정정·삭제 권리는 현재 `backend_account_device` v7 세션의 actor와 account generation에만 결속합니다. 선택 동의 거절이나 통합 동의 header는 이 권리 행사를 막지 않으며, Gateway-local audit hash도 권한 판단이나 Backend 요청에 사용하지 않습니다. 구조화 정정은 append-only revision과 `expected_revision` CAS를 사용하고 동일 canonical UUID 멱등키의 정확한 재전송만 허용합니다. `user_description`과 `category_hint` 중 하나 이상을 보내야 하며 생략한 필드는 유지하고 명시적 `null`은 지웁니다. 기존 자유문 `CORRECTION` 요청은 `/requests`에서 계속 지원합니다. DELETE 요청으로 받은 요청 ID는 Android의 계정·generation 결속 암호화 no-backup 저장소에만 보관하여 신고 자체가 404가 된 뒤에도 `/deletions/{request_id}`에서 `PENDING|LEGAL_HOLD|REJECTED|DELETED` 상태를 확인할 수 있습니다.

원본 collection write는 `backend_account_device` v7 cookie의 actor·account generation·auth epoch·device·session, 같은 계정·기기의 종료된 field walk(계정에 활성 보행이 없어야 함), privacy generation, 통합 동의 원장의 Backend authoritative receipt를 본문 읽기 전과 본문·upstream I/O 뒤에 다시 확인합니다. `GENERAL_RAW`는 wifi에서만 가능하고, `AUTO_REPORT`는 원본+자동신고 동의가 필요하며 cellular에서는 이동통신 동의도 추가로 요구합니다. Gateway-local audit hash는 이 권한 판단이나 Backend header에 사용하지 않습니다. 클라이언트 actor/assertion/raw proof는 전달하지 않고 Gateway가 같은 Backend path에 HEAD admission proof와 실제 메서드 proof를 각각 새로 만듭니다. manifest/commit은 서로 다른 domain-separated canonical JSON digest를 쓰며 chunk header는 raw byte SHA-256입니다. 신규 commit은 `QUARANTINED` 상태와 `RAW_QUARANTINE_14D` receipt v2만 허용합니다. 기존 `COMMITTED` collection의 receipt v1/`RAW_ORIGINAL_180D`는 status 복구에서만 엄격하게 읽기 호환합니다.

세션 쿠키 이름은 `walksafe_field_session`입니다. 쿠키는 `Path=/`, `HttpOnly`, `SameSite=Strict`이며 `NODE_ENV=production`에서는 항상, 그 밖의 환경에서는 HTTPS 요청에 `Secure`를 붙입니다. 기본 단기 세션은 최대 12시간입니다. 로그인 token은 세션 생성에만 사용하며 Android의 이후 API 요청이나 백엔드 응답으로 전달하지 않습니다. 단기 로그인 body의 선택 필드 `purpose`는 `general|account_deletion_recovery`이며 생략하면 legacy 호환으로 `general`입니다. 성공은 200 JSON의 정확한 `session_scope`와 cookie를 반환하고 기본 GET 상태도 같은 scope를 확인합니다. recovery scope는 계정 삭제 v2 세 경로, 세션 상태 조회, query/body 없는 logout에만 쓸 수 있고 보행·길찾기·신고·동의·기기·refresh 작업은 403으로 거부합니다. scope는 cookie MAC과 암호화된 active-session 상태에 함께 결속됩니다. rollout 전에 남은 exact v3 3-key 상태는 startup 검사는 통과시키되 인증에는 사용하지 않으며, 사용자는 새 scope-bound 로그인이 필요합니다.

Backend 계정 로그인은 `POST /api/field-session`의 `grant_type=password`, `email`, `password`, `remember_me`와 선택적인 canonical `device_id`를 사용합니다. `device_id`가 없으면 Gateway는 Backend의 canonical `actor_id`, `account_generation`, `auth_epoch`를 별도 session secret으로 서명한 v6 단기 cookie와 암호화 active-session 원장에 결속하며, 이 v6 세션은 일반 API·재인증용이고 field-walk 결속으로 승격하지 않습니다. `device_id`가 있으면 같은 값과 session ID까지 결속한 v7 cookie/state를 발급하고 generation-bound account ID로 field-walk를 허용합니다. `device_id`는 앱 설치 식별값이며 요청자가 등록 단말의 키를 가졌다는 요청별 증명이 아닙니다. cookie와 refresh token은 bearer credential이므로 기기별 세션 관리는 토큰 복제 방지를 보장하지 않습니다. 보행 lease는 session(family)까지 결속되므로 같은 `device_id`로 다시 로그인해도 기존 보행을 자동 승계하지 않고 409 뒤 사용자 확인 takeover 또는 90초 만료로만 넘어갑니다. 반대로 그 session의 로그아웃(`DELETE /api/field-session`, refresh-token 로그아웃 포함)이나 `?device_id=` 원격 해제가 성공하면 해당 session·기기가 보유한 active 보행을 즉시 `ENDED`로 기록합니다(원장 오류 시 로그아웃은 유지되고 lease 만료가 대체 경로). v7도 refresh token이나 장기 세션이 아니며 서버측 최대 만료는 동일하게 12시간입니다. 소유자 결정 2(2026-09-29)·S19-1: 요청에 `session_mode: "long_lived"`를 더하면(`device_id`와 `remember_me=true` 필수, 아니면 400 `field_session_request_invalid`; 장기 모드가 꺼져 있으면 503 `field_long_lived_sessions_unavailable`) Backend 인증 결과의 `actor_id`·`account_generation`·`auth_epoch`와 `device_id`에 결속한 장기 refresh family를 만들고 장기 세션 응답(기존 FieldLongSession 9키 + Backend 계정의 `account_generation`)과 짧은 access cookie(field-long `v6.` 형식, auth.ts 단기 v6와 필드·HMAC 영역이 달라 서로 해석되지 않음)를 줍니다. 이 cookie는 v7 기기 세션과 같은 모든 경로(상태·기기 목록·원격 해제·로그아웃·field-walk·원본·신고 권리)에서 인정되며, 요청마다 `backendAccountSessionGate`와 refresh마다 저장 binding의 Backend 현재성을 확인하므로 계정 잠금·auth epoch 변경은 모든 기기를 막습니다. field-walk 결속은 v7과 같이 `<actor>:generation:<g>` 계정 키와 auth epoch를 쓰고 refresh 회전으로 바뀌지 않습니다. 이 필드가 없으면 기존 v7 응답은 그대로입니다. 이 세션은 `WALKSAFE_FIELD_ACCOUNTS_JSON`에 의존하지 않으며 password를 저장하지 않습니다. `remember_me=false`는 `Max-Age` 없는 브라우저 세션 cookie를 사용합니다. 정적 actor/token v5 로그인과 선택적인 장기 device login은 호환 목적으로 유지됩니다.

보행 소유 gate: 한 기기(session)가 계정의 active 보행 lease를 보유하는 동안 `POST /api/navigation/walking`과 `POST /api/reports/v2`는 field 인증 직후, 신고 본문을 읽거나 Backend를 호출하기 전에 다른 기기·session의 요청을 409 `walk_owned_by_other_device`로 거부합니다. active 보행이 없거나 호출자 자신의 session이 보유하면 동작은 바뀌지 않으며, device 결속이 없는 v5/v6 세션은 보유자가 될 수 없습니다. 보행 원장을 읽거나 잠글 수 없으면 검사를 건너뛰지 않고 503 `field_walk_ledger_unavailable`로 닫습니다. `GET|POST /api/field-walk`의 503 `field_walk_ledger_unavailable`은 원장이 바뀌지 않았다는 뜻입니다. 반면 503 `field_walk_ledger_outcome_unknown`(`retry: "same_request_id"`, `Retry-After: 1`)은 원자 rename 뒤 저장 오류로 명령이 이미 커밋됐을 수 있다는 뜻이므로, 같은 `request_id`로만 재시도해 저장된 결과를 replay해야 하고 새 `request_id`로 재시도하면 안 됩니다.

소유자 결정 3(b)(2026-09-29, 보행 명시 종료 뒤 전송): `POST /api/reports/v2`는 호출자 자신의 기기 session이 계정의 active 보행을 보유하는 동안에도 같은 지점(본문 읽기·Backend 호출 전)에서 409 `report_walk_in_progress`로 거부합니다(대기열 신고는 보행이 끝난 뒤 보냄, 경로 요청과 다른 기기 409는 그대로). 원본 수집 쓰기(`manifest`·`chunk`·`commit`)는 `x-walksafe-raw-walk-id`에 세그먼트의 원래 walk ID를 쓰며, 그 walk가 같은 계정·같은 기기(`device_id`, session family는 비교하지 않음)의 보행으로 최근 30일 안에 끝났고(명시 종료, 로그아웃·원격 해제, lease 만료, takeover) 지금 계정에 active 보행이 없을 때만 받습니다. 계정에 active 보행이 있으면 409 `raw_collection_walk_in_progress`(보행 종료 뒤 재시도), 기록이 없거나 다른 계정·다른 기기·30일 초과·기록 상한에서 밀려난 walk면 409 `raw_collection_walk_not_uploadable`이며 둘 다 본문을 읽기 전에 반환합니다. 종료 기록은 계정별 보행 원장(같은 shard·암호화 파일, S19-26 marker 규칙 그대로)의 `endedWalks`에 최대 256개(오래된 것부터 버림, 30일 동안 하루 8회 넘게 걸어도 남도록)를 두고, 30일이 지난 항목은 새 보행 종료 때뿐 아니라 그 계정 원장을 읽거나 바꿀 때(업로드 판정 포함)마다 지우며(transfer-F6), 종료 walk가 생긴 계정에만 키가 생기므로 그 뒤 이전 build로 rollback하면 원장 검증 실패로 닫힙니다(`idempotency`와 같은 방식). 상태 조회(`GET`)는 종전처럼 보행 조건 없이 복구용으로 허용합니다.

세부 공개 형식은 `openapi.json`이 기준입니다. 내부 `x-walksafe-*` 서비스 token과 actor assertion은 공개 계약이 아닙니다. S19-52: Backend로 가는 일반 actor assertion은 `fetchBackend` 한 곳에서 요청마다 v4로 서명합니다. 서명은 대상(`walksafe-backend`)·키 ID·actor·account generation·auth epoch·30초 만료·1회용 jti와 실제 method, 정규 경로+query, 전송 본문 SHA-256을 묶습니다. multipart 신고는 Gateway가 한 번 직렬화한 bytes를 그대로 보내고 서명합니다. 서명할 수 없는 본문은 Backend로 보내지 않고 502로 닫힙니다. Backend는 v4의 요청 불일치·만료·jti 재사용을 거부하며, v1~v3 병행 수용은 `WALKSAFE_ACTOR_ASSERTION_V3_POLICY`로 끝냅니다: 기본 `safe-methods`(쓰기는 v4 필수, v1~v3는 GET/HEAD만), 그다음 `reject`(v4 전용). `accept`는 레거시 형식 호환 시험 전용이며, v1을 발급하는 레거시 웹(PWA) 러너는 지원하지 않습니다(소유자 결정 7, S20-41). 계정 삭제 v2 assertion과 RAW request proof는 별도 요청결속 형식으로 유지됩니다.

query 없는 `GET|HEAD /privacy/rights`는 공개 HTML 안내 화면입니다. 앱 설치와 로그인 cookie 없이 열 수 있고, 서버 자료 열람·동의 철회·삭제 요청을 승인된 외부 접수 URL로 연결합니다. 현행 OpenAPI의 `/privacy/rights` GET 설명에는 이 HTML 변형도 포함됩니다. POST는 405, 접수 URL 설정이 없으면 503으로 닫힙니다. 같은 경로의 `?control=` 통합 동의 GET/PUT과 bootstrap은 인증·계정 세대·설치 결속을 따로 확인합니다.

같은 정확 경로의 `GET|PUT /privacy/rights?control=integrated-consent`는 FP-013-1.2.0 통합 동의 제어면입니다(Root 결정 R3: 원본·자동신고 전송 시점이 '보행 종료 뒤'로 바뀌어 두 항목과 문서가 1.2.0, 이동통신·학습 항목은 그대로. 저장된 1.1.0 확인서는 RAW·신고 권한이 없고 1.1.0 기록 요청은 409 `integrated_consent_reconsent_required`이며 앱은 bootstrap으로 다시 동의받음). 설치별 256-bit 제어 비밀을 요구하며 서버에는 그 SHA-256만 저장하고, GET과 PUT 모두 인증된 general session의 actor·account generation에도 결속합니다. 계정 전환 뒤 로컬 원장의 actor binding이 현재 세션과 다르면 다른 계정의 선택을 반환하지 않고 409 `integrated_consent_actor_reconsent_required`로 bootstrap 복구를 요구합니다. S19-31: 로컬 원장은 캐시일 뿐이므로 GET은 Backend bootstrap이 READY/CURRENT_CONSENT이고 그 선택 항목·항목 버전이 로컬 confirmation과 같을 때만 `current: true`를 반환합니다. 최신 subject receipt가 로컬 `backend_consent_receipt_sha256`와 달라도 같은 선택을 같은 계정의 다른 설치가 다시 기록한 경우는 current로 보며(S19-31-F1, 두 설치가 번갈아 재동의·재기록하지 않음), 다른 선택으로의 변경이나 Backend 재동의 요구는 409 `integrated_consent_reconsent_required`, Backend 확인 실패는 fail-closed 오류로 응답합니다(GET마다 Backend 1회 조회). 인증된 general session은 `GET /privacy/rights?control=integrated-consent-bootstrap&installation_id=...&policy_version=FP-013-1.2.0`에서 actor·account generation에 결속된 Backend의 현재 동의 또는 가입 동의를 strict projection으로 조회합니다. Android는 반환된 `client_revision_floor + 1`과 `expected_previous_backend_receipt_sha256`를 다음 PUT에 그대로 사용하며, Backend CAS 409 때 Gateway 로컬 원장은 변경되지 않습니다. 원본 수집, 자동신고, 이동통신 전송, 학습 재사용은 독립 boolean과 독립 항목 버전을 가지며, 영구 증가 client revision이 늦게 도착한 이전 선택의 역행을 막습니다. 새 confirmation은 Gateway-local chain 값 `gateway_audit_record_sha256`와 Backend authoritative 값 `backend_consent_receipt_sha256`를 분리합니다. Gateway audit 값은 무결성 감사에만 쓰고 허용 판단에는 Backend receipt만 사용합니다. 과거 v2/v3 원장과 로컬 `receipt_sha256`는 검증 가능한 legacy 기록으로만 읽으며 authoritative receipt로 승격하지 않고 재동의를 요구합니다. 기존 schema v4 원장은 읽기 호환하고, 새 정책 PUT은 CAS predecessor를 감사 hash에 결속한 schema v5 이벤트를 추가합니다. 설치 ID별 원장은 hash chain과 다른 원장과 같은 커널 잠금(같은 `.lock` 경로의 `flock`, 0600·링크 1개·inode 일치 검사)을 사용하며 잠금 파일 내용은 읽지 않으므로 빈/부분 JSON이나 과거 PID 기록이 복구를 막지 않고 보유 프로세스가 종료되면 커널이 즉시 해제합니다(S19-22). 과거 PID 잠금의 `.reaper` hardlink가 남아 링크가 2개가 되면 503 `integrated_consent_store_unavailable`로 닫히며, 서비스를 멈춘 상태에서 운영자가 `<digest>.json.lock.reaper`를 삭제해야 합니다. Backend receipt를 이벤트에 결속한 뒤 0600 임시 파일 fsync, 원자 rename, 디렉터리 fsync가 끝난 후에만 confirmation을 반환합니다. 동의는 저장 시점의 field actor와 account generation에 결속되고, 다른 actor나 generation은 새 동의 revision을 명시적으로 저장하기 전까지 그 영수증을 사용할 수 없습니다. 신고는 현재 항목 버전, 제어 비밀, Backend receipt와 actor 결속이 모두 일치해야 합니다. 직접 신고는 건별 전송 확인을 Android UI에서 받고 선택 raw 동의를 요구하지 않습니다. 자동신고는 `automatic_reporting`, 이동통신 전송은 `mobile_network_transfer` 선택을 각각 추가로 요구합니다. 현재 계약은 인증된 first-party Android의 `x-walksafe-report-purpose: explicit|automatic` 선언을 multipart `metadata.auto_reported`와 교차 확인해 직접·자동 동의 요구를 분리합니다. 이 선언은 암호학적 client attestation이 아니며, 두 값을 함께 위조하는 인증된 변조 client는 `NOT_COVERED` 신뢰 경계입니다. Android는 관측 문자열이 아니라 선택한 실제 `Network`로 소켓을 열며, `cellular`이면 이동통신 선택도 Backend 전달 직전에 다시 확인합니다.
S19-29: 설치별 동의 원장이 4,096건(또는 4 MiB)에 도달하면 허용을 넓히는 기록은 거부하지만, 항목 수만큼의 철회 예약분(4건, 16 KiB 여유)은 남깁니다. 직전 이벤트가 같은 actor의 권위 이벤트이면 선택 일부를 끄는 단조 철회가, 그 밖의 경우(legacy·재동의 필요 이벤트, 다른 actor 결속)에도 네 선택을 모두 false로 하는 요청은 항상 이 예약분으로 기록됩니다. S19-30: Backend가 동의를 커밋한 직후 Gateway가 죽어도 로컬 원장에는 쓰이지 않은 상태로 남고, Android가 영속 보관한 같은 request ID·내용을 재시작 뒤 다시 보내면 Backend 멱등 영수증을 채택해 기록합니다(자식 프로세스 SIGKILL 시험).

계정 전환을 포함하는 최신 로컬 상태 schema version은 6입니다. ledger revision은 설치 전체 append 순서를 유지하고, client revision과 request ID 멱등성은 actor·account generation binding별로 분리합니다. schema v4/v5 파일은 계속 검증해 읽으며 다음 성공 PUT에서만 schema v6로 승격합니다.

## FP011 장기 현장 세션

장기 세션은 기본 비활성입니다. 명시적인 활성화 값과 access·refresh idle·refresh absolute TTL 세 값이 모두 존재하고 보안 범위 안에 있을 때만 열립니다. 활성화 값이 없으면 장기 세션을 만들지 않으며 기존 단기 로그인은 계속 200 `session_scope=general`과 단기 cookie를 반환합니다. 활성화 값이 `true`인데 TTL이 하나라도 없거나 잘못되면 Gateway는 listen 전에 시작을 거부합니다. recovery purpose에는 `device_id`를 허용하지 않으며 장기 family를 만들 수 없습니다.

- 설치 로그인: `POST /api/field-session`에 `actor_id`, `token`, `device_id`를 보냅니다. 장기 모드에서는 200 JSON으로 `session_scope=general`, `actor_id`, `device_id`, `family_id`, `rotation`, `refresh_token`, 세 만료시각을 받고 짧은 access cookie를 함께 받습니다.
- 이메일 장기 세션의 로그인·갱신·상태 응답에는 양의 정수 `account_generation`이 추가됩니다. Android는 이를 암호화 저장·복원하고 갱신 및 상태 확인 시 동일 값을 요구합니다. 정적 actor/token 장기 응답에는 이 필드가 없습니다. 완료된 이메일 교육·동의 기록이 같은 계정·설치·서버에 결속된 경우 다음 비밀번호 로그인부터 장기 모드를 적용하며, 최초 교육 중에는 기존 v7 세션을 유지합니다. debug 테스트 빌드는 `-Pwalksafe.longLivedLoginEnabled=true`가 필요합니다. 비밀번호는 저장하지 않습니다.
- 갱신: 같은 POST에 `grant_type=refresh_token`과 actor/device/family/rotation/refresh token을 JSON으로 보냅니다. 성공하면 정확히 한 단계 회전한 새 refresh token과 access cookie를 받습니다.
- 상태·기기: 기본 GET은 기존 상태 응답을 유지합니다. 유효한 장기 access cookie의 상태에는 장기 세션 메타데이터가 추가됩니다. `GET ?devices=true`는 현재 actor의 활성 기기만 반환합니다.
- 철회: 기본 DELETE는 현재 cookie family를 철회합니다. access cookie가 없거나 만료된 복원 후보는 DELETE JSON body에 refresh proof를 보내 같은 family를 철회할 수 있습니다. refresh token은 URL이나 header에 넣지 않습니다. 올바른 형식의 유효·불일치·이미 철회된 proof는 token oracle을 만들지 않도록 모두 멱등 204입니다.
- 선택 철회: `DELETE ?device_id=...`는 유효한 access cookie의 actor에만 묶이며 다른 actor의 같은 device ID에는 영향을 주지 않습니다. S19-4-F1(FP-011 민감한 계정 변경): 현재 기기가 아닌 다른 기기의 세션 철회는 계정 삭제와 같은 최근 자격 로그인 창(5분, `ACCOUNT_DELETION_REAUTHENTICATION_WINDOW_MS`)을 요구하며, 창 밖이면 아무것도 철회하지 않고 401 `field_session_reauthentication_required`(`reauthentication_required: true`, S01-20 표 next action REAUTHENTICATE)로 응답합니다. 자기 기기 철회와 일반 로그아웃은 제한하지 않습니다.

서버는 raw refresh token을 성공 JSON 응답에 한 번 반환할 뿐 파일이나 로그에 저장하지 않고 현재 token의 SHA-256 digest만 보관합니다. 갱신은 actor별 단일 원자 구간에서 파일 교체로 커밋합니다. 새 family의 refresh token은 86자 `무작위 43자 + HMAC-SHA256(family별 암호화 저장 key, family_id·rotation·무작위부)` 형식이어서, 이미 소비한 이전 회전 token이 다시 오면 digest 이력 없이 그 proof로 재사용을 판정합니다. 소유자 결정 1(2026-09-29, FP-011-DETAIL-02)에 따라 재사용이 아직 활성인 family에서 탐지되면 그 계정(actor)의 모든 기기 family(legacy·Backend 결속 모두)를 `refresh_token_reuse` 사유로 즉시 철회하고, 같은 actor의 단기 세션(v5/v7)도 끝냅니다(Backend 계정은 generation/auth_epoch watermark 유지). 재사용한 요청은 401 `refresh_token_reuse_detected`, 그 뒤 다른 기기가 자기 refresh token으로 갱신하면 401 `field_session_revoked_reuse_detected`(`reauthentication_required: true`, next action REAUTHENTICATE)를 받아 이유를 안내하고 재로그인합니다. proof가 맞지 않는 token에는 사유 없이 `field_session_revoked`만 줍니다. 이미 철회된 family의 옛 token을 다시 보내도 새로 로그인한 기기는 철회하지 않습니다(훔친 옛 token으로 반복 전체 로그아웃 방지). 무작위 불일치나 proof가 맞지 않는 token은 family를 철회하지 않습니다. 이 재사용 판정은 회전에 결속됩니다. proof는 발급 rotation을 포함하므로 소비된 proof 형식 token은 발급 당시 rotation과 함께 제시될 때만 재사용으로 판정합니다. 같은 token을 다른 rotation(다른 과거 회전, 현재 회전, 미래 회전)과 함께 보내면 401 `invalid_refresh_token`만 반환하고 family는 철회하지 않습니다. 그 요청은 어떤 경우에도 갱신에 성공하지 못하므로 우회는 아니며, 잃는 것은 rotation을 틀리게 보낸 요청에 대한 재사용 신호뿐입니다. Android는 token과 rotation을 함께 저장하므로 일반적인 재전송 경로는 계속 family를 철회합니다(`test/field-long-session.test.ts`의 R19-GB-05 고정 시험). 이 변경 전 family(64자 무작위 token)는 다음 회전에서 마지막 digest 하나를 기존 이력에 한 번 더하고 key를 받은 뒤로는 이력이 늘지 않으며, 기존 digest 이력으로 과거 token 재사용도 계속 탐지합니다. 이 형식을 모르는 이전 Gateway로 rollback하면 새 형식 소비 token의 재사용 탐지는 무작위 불일치(철회 없는 401)로 약화됩니다. idle 또는 absolute 만료 시에는 재로그인이 필요합니다.

w24 fix-login 보강: (F3) 재사용 전체 철회는 같은 actor 상태 파일의 원자 쓰기 안에 `reuse_revoked_at_epoch_ms`를 함께 기록하고, auth.ts는 v5/v6(단기)/v7 세션의 발급 시각(`expiresAtSeconds − 12시간`, 초 단위)이 그 값 이하이면 거부합니다. 단기 세션 파일 정리(`revokeShortFieldSessionsForActor`)가 잠금 경합·저장 오류·rename 뒤 결과 불명으로 실패해도 단기 세션은 즉시 끝납니다(fail-closed). 발급 시각이 초 단위라 철회와 같은 초에 새로 로그인한 단기 세션도 거부되어 한 번 더 로그인해야 할 수 있습니다. 이 필드를 모르는 이전 build는 값을 무시하므로 rollback하면 이 보강만 사라집니다. (F6) Backend 결속 family의 소비 token 재전송은 Backend 현재성 확인 전에 판정하므로 Backend 확인이 불가해도 재사용 탐지와 전체 철회가 지연되지 않습니다. (F7) 이미 철회된 family에 소비 token을 다시 보내면 legacy도 Backend와 같이 상태를 바꾸지 않고, 재사용으로 철회된 family의 자기 token 보유자에게는 401 `field_session_revoked_reuse_detected`, 다른 사유(로그아웃·원격 해제·보안사고·상한 퇴출)로 철회된 family에는 401 `field_session_revoked`를 줍니다. (F13) 소비된(옛) refresh token으로 보내는 refresh-proof `DELETE /api/field-session`은 그 family만 `logout`으로 끝내고 다른 기기와 재사용 watermark는 건드리지 않습니다. Android가 갱신 응답을 잃은 뒤 PENDING_REVOCATION으로 옛 token을 보내도 계정 전체 로그아웃이 일어나지 않습니다(`test/field-session-login-hardening.test.ts` F13).

absolute TTL이 유한하면 family 하나의 refresh 회전은 최대 4,096회입니다. 상한에 닿은 다음 갱신은 family를 철회하고 401 `refresh_rotation_limit_reached`와 `reauthentication_required: true`를 반환하므로 재로그인이 필요합니다. 따라서 absolute TTL은 최대 수명일 뿐이며, access 만료마다 갱신하는 기기의 실제 최대 유지 기간은 대략 `min(absolute TTL, access TTL × 4,096)`입니다. 예를 들어 access 60초·absolute 365일이면 약 2.84일 뒤, access 3600초면 약 170.7일 뒤 재로그인이 필요합니다. absolute TTL이 `unlimited`이면(소유자 결정 2) 4,096회 상한은 숨은 최대 유지기간이 되므로 적용하지 않고 rotation 번호만 2,147,483,647 이하로 제한합니다(S19-8). 회전마다 소비 digest를 누적하지 않으므로 한 actor 파일(평문 상한 4 MiB)의 크기는 회전 수와 무관하게 family 수에만 비례합니다(활성 기기 32개 × 4,096회 실제 회전 후에도 수십 KB). (F8) absolute를 family 생성 때 값으로 고정하므로, `unlimited`로 만든 family는 운영자가 나중에 유한 absolute로 되돌려도 absolute가 생기지 않고(`null` 유지) 회전 상한만 설정 기준(유한 absolute면 4,096회)으로 적용됩니다. 되돌린 설정의 절대 기간을 기존 기기에도 적용하려면 해당 family를 원격 해제하거나 재로그인을 요구해야 합니다.

기기 상한(Root 결정 R2, login-F2): 계정당 활성 장기 family는 32개입니다. idle TTL이 유한하면 상한에서 새 로그인은 종전처럼 503 `field_session_device_capacity_unavailable`입니다. idle이 `unlimited`이면 재설치·데이터 삭제·분실로 남은 family가 만료로 정리되지 않으므로, 상한에서 가장 오래 회전하지 않은(`last_rotated_at_epoch_ms`가 가장 이른, 같으면 먼저 만든) 활성 family 하나를 `capacity_evicted` 사유로 철회하고 새 로그인을 같은 원자 쓰기로 받습니다. 퇴출된 기기는 다음 갱신에서 사유 없는 401 `field_session_revoked`를 받고 다시 로그인합니다. legacy와 Backend 결속 family는 각각 따로 32개를 셉니다. 이 사유를 모르는 이전 build로 rollback하면 퇴출 기록이 있는 actor 파일은 검증 실패(503)로 닫힙니다. (F14) v7 기기 세션(auth.ts 단기 원장)과 장기 family(Backend 결속·legacy)는 기기 목록·원격 해제가 분리되어 있어, 같은 계정이라도 장기 cookie로는 v7 기기를 보거나 해제할 수 없고 반대도 마찬가지입니다. Android 이메일 장기 경로를 연결할 때 통합합니다.
S19-10: 공개 refresh grant는 본문 검사 뒤, 세션 상태를 읽거나 잠그기 전에 메모리 admission을 거칩니다(로그인 실패 제한과 별개). 신뢰 client IP당 분당 60건, 주장된 (actor, refresh family)당 분당 refresh 판정 거절(R12: 400·401·403·409만) 30건을 넘으면 429 `field_session_refresh_rate_limited`(`retryable: true`, Retry-After=창 끝까지)이고, 동시에 진행 중인 refresh가 16건이면 503 `field_session_storage_busy`(`retryable: true`)입니다. 성공한 회전, 저장 장애, client 취소(499), 요청 deadline(504)은 거절 한도를 소비하지 않으므로 여러 기기의 정상 갱신과 불안정한 망의 취소는 이 한도와 무관하고, 한 family를 겨냥한 무효 proof 반복만 상태 복호화 전에 멈춥니다. family ID는 서버가 만든 무작위 값이라, 같은 actor ID로 추측한 family에 무효 proof를 계속 보내도 그 actor의 실제 기기 family 회전은 막히지 않습니다(추측 family마다 IP 한도 안에서 상태를 한 번씩 읽음). 남는 위험: 실제 (actor, family)를 아는 공격자가 분당 30건을 계속 보내면 공격이 이어지는 동안 그 family의 정상 refresh도 매 창마다 같은 429를 받습니다(무기한, 자격 증명은 유지). production에서 쓸 수 있는 신뢰 IP가 없는 요청은 adapter가 먼저 503으로 거부하고(S19-53), 그래도 도달하면 한 공유 bucket으로 IP 한도를 셉니다. S19-11: 503 `field_session_storage_unavailable`은 아무것도 커밋되지 않은 저장 실패(읽기·복호화 실패, rename 전 쓰기 실패)에만 쓰며 `retryable: true`를 가지므로 client는 같은 refresh proof를 지우지 않고 Retry-After 뒤 그대로 다시 보냅니다. rename 뒤 실패나 커밋 뒤 잠금·guard 해제 실패는 500 `field_session_storage_outcome_unknown`(`retryable: false`, `reauthentication_required: true`)입니다(단기 세션 원장도 같은 구분, S19-27).
S19-27: Gateway의 모든 상태 저장소(장기·단기 세션, 보행 원장, 통합 동의, 개인정보 권리 원장, 삭제 원장·archive, 서버 용량 snapshot)는 원자 rename 뒤의 실패(디렉터리 fsync 등)만 공통 `GatewayStorageOutcomeUnknownError`로 던지고, 그 밖의 저장 실패는 "커밋 안 됨"입니다. 응답 투영: 세션 500 `field_session_storage_outcome_unknown`(다시 로그인), 보행 503 `field_walk_ledger_outcome_unknown`·통합 동의 503 `integrated_consent_outcome_unknown`·삭제 503 `privacy_deletion_outcome_unknown`(셋 다 `retry: same_request_id`, Retry-After 1: 같은 request ID 재전송은 커밋됐으면 저장된 결과를 재응답하고 아니면 새로 실행하거나 Backend 멱등 영수증을 채택). 로그인 중 개인정보 원장 세대 결속은 멱등이라 503 `privacy_ledger_unavailable`로 로그인 재시도를 안내하고, 서버 용량 snapshot은 내부 캐시라 호출부가 이전 값으로 대체합니다.

배포 순서(login-F5): release 앱은 `WALKSAFE_LONG_LIVED_LOGIN_ENABLED=true`로 토큰 로그인에 `device_id`를 보내고 장기 세션 9키 응답을 요구합니다. 장기 모드가 꺼진 Gateway는 같은 요청에 단기 `{session_scope}`만 주므로 앱은 `gateway_session_binding_failed`로 로그인을 거부합니다(fail-closed). 따라서 Gateway에 `WALKSAFE_FIELD_LONG_LIVED_SESSIONS_ENABLED=true`와 세 TTL을 먼저 적용하고, 시작 로그와 `GET /api/field-session` 장기 세션 응답(`session_mode: "long_lived"`)을 확인한 뒤 앱을 배포합니다. `WALKSAFE_FIELD_LONG_LIVED_SESSIONS_ENABLED`는 정확히 `true` 또는 `false`(또는 빈 값)만 허용하며 `True`·`1` 같은 다른 값은 listen 전에 시작을 거부합니다(F12). 비밀번호 로그인의 `session_mode: "long_lived"`는 장기 모드가 꺼져 있으면 Backend 인증 전에 503 `field_long_lived_sessions_unavailable`로 끝납니다(F11).

저장 오류로 반환하는 503은 회전 커밋 전에 발생하므로 같은 요청을 재시도할 수 있습니다. 반면 Android가 응답을 전혀 받지 못한 연결 중단은 서버 커밋 여부를 확정할 수 없으므로 자동 rotation 증가나 무한 재시도를 하지 않고 재로그인으로 닫아야 합니다. account lock과 security incident는 내부 호출 `revokeFieldSessionsForSecurityEvent()`로 해당 actor의 단기·장기 family 전체를 철회합니다.

## 실행 계약

```bash
npm ci
npm run typecheck
npm run build
npm test
npm start
```

`npm run build`는 이 패키지의 `dist`만 먼저 비워 삭제된 소스의 오래된 출력이 남지 않게 합니다. `npm start`는 `node dist/server.js`를 실행하며 기본 bind는 `127.0.0.1:8081`입니다.

필수 운영 설정:

- `NODE_ENV=production`
- `BACKEND_API_BASE_URL=http://127.0.0.1:8000`
- `WALKSAFE_FIELD_TEST_TOKEN`: 백엔드 전용 field service token, 24자 이상
- `WALKSAFE_GATEWAY_SESSION_SECRET`: 백엔드 service token과 분리된 32자 이상 전용 session secret
- `WALKSAFE_GATEWAY_TRUSTED_IP_HEADER`: `cf-connecting-ip` 또는 `x-real-ip` (S19-53: production에서 없거나 다른 값이면 서비스가 시작하지 않음)
- `WALKSAFE_GATEWAY_RATE_LIMIT_DIR`: 절대 경로, 서비스 계정 소유, 권한 0700. 로그인 제한, 장기 세션, 통합 동의 원장의 공통 상위 디렉터리입니다.
- `WALKSAFE_GATEWAY_STATE_KEYRING_FILE`: writable 상태 디렉터리 밖의 canonical 절대 경로. production에서는 `root:<service-group>` 소유 0640, 정확히 하나의 active AES-256 키가 필요합니다.
- `WALKSAFE_FIELD_WALK_LEDGER_PATH`: 암호화된 현장 보행 원장의 canonical 절대 경로. production에는 임시 경로 기본값이 없습니다.
- `WALKSAFE_PRIVACY_RIGHTS_REQUEST_URL`: 앱 밖에서도 접근 가능한 승인된 HTTPS 권리요청 접수 URL

선택 설정:

- `WALKSAFE_FIELD_ACCOUNTS_JSON`: legacy 정적 actor/token 로그인을 유지할 때만 `[{"actor_id":"...","token":"..."}]` 형식으로 설정
- `WALKSAFE_ANDROID_GATEWAY_HOST`: 생략 시 `127.0.0.1`; 보안 경계상 다른 값은 거부
- `WALKSAFE_ANDROID_GATEWAY_PORT`: 생략 시 `8081`
- `WALKSAFE_VOICE_ENABLED=true`: 고정 Voice revision/manifest와 내부 서비스가 준비된 경우에만 활성화
- `WALKSAFE_VOICE_API_BASE_URL=http://127.0.0.1:9001`: 정확한 loopback Voice URL
- `WALKSAFE_VOICE_SERVICE_TOKEN`: Backend/session 자격과 분리된 24자 이상 내부 token. Android 배포물에는 포함하지 않음

장기 세션 설정(소유자 결정 2, 2026-09-29: 로그아웃·앱 삭제·원격 해제·비밀번호 변경·계정 잠금·재사용 탐지·보안사고·관리자 강제조치·계정 삭제가 아니면 재로그인을 요구하지 않음. 운영 예제 `deploy/config/walksafe-android-gateway.env.example`는 access 900초 + idle/absolute `unlimited`로 켬):

- `WALKSAFE_FIELD_LONG_LIVED_SESSIONS_ENABLED=true`
- `WALKSAFE_FIELD_ACCESS_TTL_SECONDS`: 60~3600초(권장 900초, FP-011-DETAIL-01의 15분). 무기한 불가
- `WALKSAFE_FIELD_REFRESH_IDLE_TTL_SECONDS`: 300~7776000초이며 access TTL 이상, 또는 정확히 `unlimited`(미사용 만료 없음)
- `WALKSAFE_FIELD_REFRESH_ABSOLUTE_TTL_SECONDS`: 3600~31536000초이며 idle TTL 이상, 또는 정확히 `unlimited`(절대 최대 유지기간 없음). idle이 `unlimited`이면 absolute도 `unlimited`여야 합니다.

TTL에는 암묵적인 기본값이 없습니다. 무기한도 `unlimited`라는 명시 값으로만 켜집니다. 활성화 flag가 없으면 장기 모드는 닫힙니다. 활성화 flag가 `true`인데 세 값 중 하나라도 누락·빈 값·범위 초과·순서 위반이면 `field long-lived session TTL configuration is invalid`로 listen 전에 시작이 실패합니다(S19-9: 조용히 단기 세션으로 바뀌지 않음). 무기한일 때 로그인·갱신 응답, 상태, 기기 목록의 `idle_expires_at_epoch_ms`/`absolute_expires_at_epoch_ms`는 JSON `null`입니다(필드는 생략하지 않음, openapi `EpochMillisecondsOrUnlimited`). access 만료는 항상 유한하고 refresh는 매 사용마다 회전합니다. null 만료를 저장한 상태 파일은 이 형식을 모르는 이전 Gateway로 rollback하면 읽기 실패(503)로 닫힙니다.

## 상태 열쇠 회전·마이그레이션

Gateway는 시작할 때 검증한 keyring을 프로세스 수명 동안 고정합니다. 실행 중 파일을 바꿔도 새 active/compromised 상태를 다시 읽지 않으므로, keyring 변경은 반드시 서비스 중지 상태에서 수행하고 재시작해야 합니다.

1. Gateway 서비스를 중지하고 실행 중 프로세스가 없음을 확인합니다.
2. 기존 active를 `decrypt-only` 또는 `compromised`로 전이하고 정확히 하나의 새 active를 둔 keyring을 별도 열쇠 관리 경계에서 원자적으로 발행합니다. compromised 항목에는 열쇠 재료 대신 과거 32-byte 재료의 소문자 SHA-256을 `key_sha256`으로 남깁니다. Gateway는 이 fingerprint를 모든 active/decrypt-only 재료와 대조해 손상 재료의 새 key ID 재사용을 거부합니다.
3. 서비스 유닛이 아닌 일회성 유지보수 명령에만 `WALKSAFE_GATEWAY_STATE_MAINTENANCE_SERVICE_STOPPED=true`를 주고 `npm run state-encryption-maintenance -- inspect` 후 필요에 따라 `rotate` 또는 승인된 `migrate-plaintext`를 실행합니다.
4. `inspect`에서 plaintext, unknown key, compromised key, `integrity-failed`가 0인지 확인한 뒤 acknowledgement를 제거하고 서비스를 새로 시작합니다. CLI `inspect`는 파일별 결과 JSON을 항상 출력하고(gw-F5), 하나라도 있으면 exit 2입니다.
S19-35 세션 서명 키(`WALKSAFE_GATEWAY_SESSION_SECRET`) 교체: 새 삭제 요청의 capability 검증은 keyring 목적 파생 키와 key ID(`capability_key`)를 쓰므로 세션 키와 무관하지만, `capability_key`가 없는 이전 요청은 비밀값이 저장되지 않아 미리 재키할 수 없고 그 capability가 한 번 제시될 때까지 세션 키로 검증됩니다. 따라서 서비스 중지 상태에서 `npm run state-encryption-maintenance -- check-session-secret-retirement`를 실행해 `legacy_deletion_capabilities.total`이 0(`session_secret_retirement: "allowed"`, exit 0)일 때만 이전 세션 키를 폐기합니다. 0이 아니면(exit 3, `"blocked"`, active·archive 건수 표시) 교체하지 않고 해당 요청의 상태 조회로 전환될 때까지 기다립니다. `inspect` 출력에도 같은 건수가 나오며, 삭제 원장이 compromised·unknown key 등으로 읽히지 않아 셀 수 없으면 파일별 결과는 그대로 출력하고 `legacy_deletion_capabilities`에 `{"error": "<code>"}`를 넣어 exit 2로 끝납니다.

keyring과 암호화 원장에는 symlink·hardlink를 사용하지 않습니다. 운영 keyring은 root:service-group 소유의 exact `0640` 파일이어야 하고 모든 상위 디렉터리는 root 소유이며 group/other 쓰기가 금지됩니다. keyring은 writable 상태 경계와 분리하고, 열쇠 파일을 실행 중 직접 편집하거나 maintenance acknowledgement를 서비스 환경에 영구 설정하지 않습니다. Gateway는 listen 전에 관리 대상 상태 전체를 복호화·schema 검증하며(봉인된 보행 감사 segment만 envelope·key 상태 확인, R13) plaintext, unknown key, compromised key가 하나라도 있으면 시작하지 않습니다. 실제 KMS·운영 회전·복구훈련은 이 저장소 내부 절차로 수행됐다고 간주하지 않습니다.

S19-26: 서비스 시작 검사는 상태 루트에 `state-init-marker.v1`(0600 strict JSON, 경로·시각만 포함, `.json`이 아니어서 암호화 maintenance 대상 아님)이 없으면 최초 실행으로 보고 그 시점에 존재하는 필수 원장(`WALKSAFE_FIELD_WALK_LEDGER_PATH`, `privacy-rights/ledger.json`, `privacy-deletion-v2/ledger.json`)을 기록합니다. 이후 처음 durable write된 필수 원장도 marker에 등록됩니다. 등록된 원장이 사라지면 빈 원장으로 다시 시작하지 않고(보행 fencing 1 재시작·삭제 차단 소실 방지) 읽기는 503으로 닫히며 다음 시작은 `state_file_missing`으로 거부됩니다. marker 손상도 시작 거부입니다. 빈 볼륨이나 잘못된 상태 볼륨이 연결되면 marker도 함께 없으므로, 운영(`NODE_ENV=production`)은 marker를 기본 필수로 봅니다(소유자 결정 7, 2026-09-29): marker가 없으면 시작을 거부하고, 최초 설치 첫 시작 한 번만 `WALKSAFE_GATEWAY_STATE_INIT=first-run`을 설정해 marker를 만듭니다. marker가 있는데 이 플래그가 남아 있으면 시작을 거부하므로 첫 시작 뒤 환경에서 지웁니다. (login-F10) marker가 없던 이전 build(w22 이전)로 초기화한 기존 운영 볼륨을 이 build로 올릴 때도 시작이 거부되므로, 서비스를 멈춘 상태에서 연결된 볼륨이 올바른 운영 상태인지(필수 원장 경로·파일이 있는지) 확인한 뒤 같은 방법으로 `first-run`을 한 번만 켜고 시작해 marker를 만들고, 곧바로 플래그를 지웁니다. 빈 볼륨이나 잘못된 볼륨에서 `first-run`을 켜면 그 상태가 기준이 되므로 확인 없이 켜지 않습니다. 운영에서 `WALKSAFE_GATEWAY_STATE_INIT_MARKER=optional`은 거부됩니다. 개발·시험은 기존대로 marker가 없으면 최초 실행으로 만들며, `WALKSAFE_GATEWAY_STATE_INIT_MARKER=required`로 같은 필수 동작을 켤 수 있습니다. 복구는 서비스를 멈춘 상태에서 백업 원장을 복원하거나, 의도적 초기화라면 운영자가 marker의 해당 경로를 제거한 뒤 시작합니다. S19-26-F1: marker가 있는 시작에서도 존재하지만 목록에 없는 필수 원장(첫 durable write 직후 등록 전 crash)은 marker 잠금 안에서 등록합니다. 보행 원장의 clock anchor(`<원장 경로>.clock`)도 필수 원장으로 등록됩니다. S19-22-F1: 시작 검사와 state maintenance는 `integrated-consent/`에 남은 과거 PID 잠금 복구 링크(`<digest>.json.lock.reaper`, 또는 링크가 2개 이상인 `.lock`)를 발견하면 `integrated_consent_lock_residue`로 거부하고 목록과 삭제 절차(서비스 중지 상태에서 `.reaper` 삭제)를 알립니다.

삭제 원장 archive(S19-36, w22 review): 완료 요청을 `privacy-deletion-v2/archive/`로 옮기면 active 원장의 선택 키 `archive_index`가 옮긴 actor fence 파일을 등록하고(`actor_prefixes`, actor digest 앞 16 hex, 건당 16 B) outbox 작업이 남은 archived 요청만 색인합니다(`outbox_request_refs`, 보통 빈 목록). 등록된 actor의 archive fence 파일이 없으면(디렉터리 삭제·부분 복원) 그 actor의 재가입·삭제 판정은 integrity 오류로 닫히고 다른 actor는 영향이 없습니다. outbox drain(5초)과 paused 목록은 색인된 archive 파일만 읽습니다. index가 없는 이전 archive는 첫 쓰기에서 한 번 전체 스캔해 색인을 만듭니다. S19-41-F1: 단말 삭제 증거 작업은 요청별 제출 순번(`sequence`)을 가지며 superseded 이력 축출은 그 순번으로 가장 오래된 것부터 합니다(숫자만으로 된 evidence ID도 순서가 바뀌지 않음). S19-41(w25): 새 증거 작업은 제출 설치 ID(`installation_id`)도 기록하고, 요청당 64건 예산에는 대기·종결 충돌 작업과 설치별 가장 새 ACK 1건만 셉니다. 같은 설치의 이전 ACK는 revision-superseded 항목과 함께 재전송 전용 이력(256건, 오래된 것부터 축출)으로 넘어가므로 같은 단말의 실패→재제출→ACK 반복이 예산을 소진하지 않습니다(`installation_id`가 없는 이전 작업은 계속 예산에 셈). 이 두 변경과 S19-14 shard stamp 이후의 원장은 이전 build가 무결성 오류로 거부하므로 rollback은 지원하지 않습니다(서비스 중지 상태의 백업 복원만).

서비스가 loopback에 직접 연결된 Android 요청(개발용 adb reverse)을 받을 때 신뢰 IP 헤더가 없고 실제 socket peer도 loopback이면, production이 아닐 때만 설정된 신뢰 헤더에 그 peer 주소를 보충합니다. 이미 Nginx가 설정한 신뢰 헤더는 덮어쓰지 않습니다. S19-53: `NODE_ENV=production`에서는 보충하지 않고, 설정된 신뢰 헤더(`WALKSAFE_GATEWAY_TRUSTED_IP_HEADER`)가 없거나 그 값이 정확히 하나의 유효한 IP가 아닌 요청(빈 값, IP가 아닌 값, 중복 헤더가 합쳐진 `a, b`)을 handler 전에 503 `gateway_trusted_client_ip_unavailable`로 거부합니다(무효 값에서 refresh IP 한도가 사라지는 것도 막음, gw-F2; 모든 사용자가 127.0.0.1 하나로 합산돼 로그인·refresh·업로드 제한을 서로 소모하는 것을 막음). loopback 전용 `/internal/health`·`/internal/ready`는 헤더 없이 응답합니다. 따라서 운영 프록시는 모든 요청에 이 헤더를 재설정해야 하며(예제 nginx는 `X-Real-IP $remote_addr` 설정, `CF-Connecting-IP` 제거), 실제 프록시에서 위조 헤더가 재설정되는지는 배포 환경에서 확인해야 합니다.
S19-59: `server.requestTimeout`(75초)은 요청 수신만 제한합니다. handler 전체(메모리 admission 대기·잠금 대기·업무 처리·Backend/Voice 호출, Response 준비까지)는 요청별 deadline으로 따로 제한합니다. 내비게이션 외 경로의 deadline은 한 요청이 차례로 만날 수 있는 제한의 합에 여유 5초를 더합니다(gw-F6). v7 계정 세션은 경로 전에 Backend 계정 세션 확인(`/accounts/session-current`)을 거치므로 이 확인은 자체 5초 제한(초과 시 503, 로그아웃 아님)을 갖고 이들 경로의 합에 들어갑니다: 일반 경로(내비게이션 제외) 확인 5초+JSON 본문 10초+Backend 15초(35초), `POST /api/reports/v2` 확인 5초+multipart 15초+Backend 15초(40초), RAW 경로 확인 5초+본문 15초+Backend 20초(45초), STT·TTS 확인 5초+본문 10초+설정된 Voice timeout(기본 55초·85초). 내비게이션 외 경로 자체 제한 수치는 바꾸지 않았고, 안쪽의 원인 있는 timeout이 deadline보다 먼저 답합니다. keyed admission 대기는 기존대로 1초입니다. deadline에 도달하면 요청 signal을 abort해 Backend·Voice fetch, admission 대기, 본문 읽기를 client 연결 종료와 같은 경로로 취소합니다. 그 뒤 1초 안에 handler가 스스로 돌려준 결과(커밋 결과 포함)는 그대로 보내고, 취소 응답(499)이나 무응답은 504 `gateway_request_deadline_exceeded`(`OUTCOME_UNKNOWN`: 취소를 관측하지 않은 작업은 커밋됐을 수 있음)로 답하며 늦게 도착한 응답 본문은 취소합니다. 내비게이션 외 경로는 Response가 준비된 뒤의 본문 전송을 deadline에 넣지 않습니다(client 종료와 각 relay 제한이 담당).

S07-30: 내비게이션은 v7 계정 세션 확인·요청 본문 읽기·Backend 호출·응답 본문 수신을 한 요청의 제한 시간에 포함합니다. 보행 경로는 안쪽 7.5초/Node 외측 8초, 목적지 검색은 안쪽 6.5초/Node 외측 7초이며, Backend 호출은 헤더부터 본문 완료까지 5초·최대 2 MiB입니다(Android가 받는 최대 응답 크기도 2 MiB). Android는 전체 호출 10초, 연결 2초, 읽기 9초 제한입니다. 안쪽 기한 초과는 504 `gateway_navigation_timeout`, Backend 호출·본문 기한 초과는 504 `gateway_upstream_timeout`, Backend 응답이 2 MiB를 넘으면 502 `gateway_upstream_response_too_large`입니다. 취소 시 진행 중인 본문 읽기와 upstream 작업을 중단합니다.

## 단일 프로세스 제약

세션 상태와 로그인 제한은 소유자 전용 파일에(로그인 제한 기록도 세션 원장과 같이 임시 파일 fsync → rename → 디렉터리 fsync 후 반영되어 재시작·전원 차단 뒤에도 유지되는 보안 상태로 취급), actor별 회전 잠금과 업로드 동시성·속도 제한은 프로세스 메모리에 저장됩니다. 장기 세션 파일에는 refresh/access의 digest와 회전·만료·철회 상태만 들어갑니다. 따라서 이 버전은 반드시 한 프로세스·한 worker·한 replica로 실행해야 합니다. Node cluster worker 실행은 거부합니다. 계정당 활성 보행 lease 하나와 fencing token 단조 증가도 `WALKSAFE_FIELD_WALK_LEDGER_PATH` 원장 파일과 같은 host의 `/usr/bin/flock`에만 의존합니다. S19-14: 보행 원장은 account ID hash로 16개 shard 파일(설정 경로 자체가 shard 0, 나머지는 `<경로>.shard-01`…`.shard-15`)에 나뉘며 shard마다 자기 잠금·감사 기록을 가지므로, heartbeat는 자기 shard만 읽고 쓰고 서로 다른 shard의 계정은 서로 기다리지 않습니다. 이전 단일 파일 원장의 계정은 처음 접근할 때 home shard에 먼저 기록한 뒤 shard 0에서 제거해 fencing을 이어갑니다(감사 상한은 shard별). S19-14-F1: 다른 shard를 처음 쓰기 전에 shard 0에 `shardLayout` stamp를 기록하므로, shard 0만 읽는 이전(단일 파일) build로 rollback하면 원장 검증 실패로 닫히고 다른 shard 계정의 fencing을 조용히 1부터 다시 발급하지 않습니다. 첫 shard 쓰기 뒤 rollback은 지원하지 않습니다(필요하면 서비스 중지 상태에서 백업 복원). S19-13/S19-14/S01-28: shard 파일에는 계정 상태·fencing·요청 캐시와 최근 감사 꼬리(최대 1,024건)만 두고, 꼬리가 차면 그 항목을 암호화 archive segment `<shard 경로>.audit-00000001`…에 봉인합니다. segment는 파일·디렉터리 fsync까지 끝난 뒤에만 shard의 `auditArchive`(segment 수·누적 건수·마지막 segment plaintext SHA-256, segment마다 이전 hash chain)가 가리키므로 그 사이 장애는 이름 없는 orphan만 남기고 다음 봉인이 덮어씁니다. 따라서 8,192건 감사 상한은 더 이상 start/renew/takeover를 막지 않고, heartbeat가 다시 쓰는 shard 크기도 감사 누적 건수와 무관합니다. segment를 쓸 수 없으면 꼬리가 shard에 남고 종전 상한(비종료 전환 8,192건에서 fail-closed, 종료·만료는 2배 여유)이 그대로 적용됩니다. segment는 자동 삭제하지 않으며(보존 기간 미결정, R13), `state-encryption-maintenance` inspect/rotate가 shard의 managed state로 함께 복호화·구조 검증합니다. 서비스 시작 preflight는 segment의 파일 안전성·envelope·key 상태만 확인하고 복호화하지 않으므로(gw-F4) 시작 비용이 감사 이력 복호화에 비례해 늘지 않고, 본문이 손상된 segment 하나가 보행과 무관하게 서비스를 멈추지 않습니다(손상은 CLI `inspect`가 파일별 `integrity-failed`로 보고, `rotate`는 거부). 시작 때 segment가 있으면 stderr에 개수·bytes를 한 줄(`walksafe gateway state: field walk audit segments N, B bytes …`) 남기고, CLI `inspect` 출력의 `field_walk_audit_segments`에도 같은 값(lstat 기준)이 나옵니다. `auditArchive`가 기록된 shard는 이전 build가 거부하므로 rollback은 지원하지 않습니다. 원장 삭제로 해결하지 않습니다. S19-17: 명령은 `walksafe.field-walk-command.v2`(`issued_at_epoch_ms` 추가, 같은 request ID 재전송 시 동일 값)를 받고, 캐시에 없는 요청은 서버 시각 ±24시간 밖이거나 같은 기기의 축출된 요청보다 오래되면 실행하지 않고 409 `idempotency_expired`로 닫습니다. 발급 시각이 없는 v1은 기본값으로 409 `walk_command_version_retired`(실행 없음)이며, 구형 client가 남은 경우에만 `WALKSAFE_FIELD_WALK_V1_COMMANDS=accept`로 명시 허용합니다(허용 시 축출된 v1 start는 `idempotency_expired`; `accept|reject` 외 값은 시작 오류). S01-31(R11): 명시 종료(end·로그아웃·원격 해제)된 walk ID는 계정이 기억하는 동안(30일, 최대 256건) 종료 명령의 발급 시각(v2 end의 `issued_at_epoch_ms`, v1 end·로그아웃·원격 해제처럼 발급 시각이 없거나 Gateway가 끝낸 경우 서버 시각)을 함께 기록합니다. 그 walk ID의 start·takeover는 발급 시각이 이 값 이하이면 요청 캐시와 무관하게 과거 명령의 재전송으로 보고 409 `walk_already_ended`(실행 없음, fencing token 미소비)로 거부하고, 더 늦게 발급된 명령은 새 명령으로 실행합니다(Android가 READY에서 받은 start lease를 end로 반납한 뒤 같은 walk ID로 다시 시작하는 경로). 발급 시각이 없는 v1 start·takeover와 이 필드가 없는 이전 종료 기록은 순서를 증명할 수 없어 계속 거부합니다. 만료·인수된 walk ID는 Android 소유 보행 복구가 한 번 재획득해 종료할 수 있도록 고정하지 않습니다. S19-20: lease 시각은 프로세스 안에서 monotonic 경과를 따르고, 2초를 넘는 벽시계 step 뒤 90초 동안 start/takeover는 503 `field_walk_clock_unavailable`, renew/end는 계속 허용됩니다. 흡수한 step은 `<원장 경로>.clock`(암호화 managed state, S19-26 marker 등록)에 anchor로 영속해 재시작 뒤에도 같은 서버 시각을 이어가고, 창이 끝나면 벽시계가 앞으로 간 경우 즉시 벽시계로 재기준(창 이전 lease는 이동량만큼 유예), 뒤로 간 경우 10분 이하는 10% 속도로 수렴(그동안 90초 lease는 실제 최대 100초), 그보다 크면 재기준합니다. 남은 시간이 TTL을 넘거나 획득 시각이 미래인 lease(재시작 중 벽시계 후퇴 등)는 지금부터 90초로 잘라 영속하며 늘리지 않습니다. step 감지와 lease 절단은 `walksafe.gateway-state-telemetry.v1` 이벤트로 stderr에 남습니다. v2 명령의 ±24시간 창은 서버 시각 또는 벽시계 어느 쪽 기준이든 안에 있으면 통과합니다. 시작 시 같은 상태 디렉터리와 같은 원장 경로의 두 번째 서비스는 instance lock으로 거부하지만, 서로 다른 host나 서로 다른 원장 파일을 쓰는 replica는 감지하지 못하므로 같은 계정의 보행을 각각 허용할 수 있습니다. 여러 host 운영은 이 보장을 PostgreSQL 같은 공유 트랜잭션 저장소로 옮긴 뒤에만 가능합니다. 수평 확장은 회전과 재사용 탐지를 원자적으로 수행하는 공유 상태 저장소로 이전한 후 별도 변경으로 진행해야 합니다.

## 계정 삭제 제어 (FP-046)

- `POST /privacy/account-deletions`은 `walksafe.account-deletion-request.v2`, 요청 ID, 단조 증가 client revision, `DELETE_MY_ACCOUNT` 확인값을 사용합니다. 새 요청에는 `general` 또는 `account_deletion_recovery` field session과 32-byte client capability가 모두 필요하고, 정확한 replay에는 capability만 필요합니다.
- `GET /privacy/account-deletions/{request_id}/status`와 `POST /privacy/account-deletions/{request_id}/device-evidence`는 field session에 의존하지 않고 요청에 결속된 capability만 요구합니다. capability는 `x-walksafe-deletion-access-secret`에 43자리 unpadded base64url로 전달하며 원문은 저장하거나 backend로 전달하지 않습니다.
- 상태 조회에 `X-WalkSafe-Deletion-Status-View: device-verification.v1`을 보내면 Backend의 기기 확인 요약을 검증하여 `device_verification`으로 전달합니다. 헤더가 없는 기존 앱에는 기본 v2 형식을 유지합니다. 이 시간 의존 요약은 삭제 revision·원장·완료 영수증에 합치지 않습니다. `SERVER_COMPLETED_DEVICE_UNVERIFIED`는 서버 자료만 완료되고 일부 기기는 미확인인 상태이며, 전체 완료나 재등록 허용 근거가 아닙니다. Android는 새 조회 결과만 표시하며 재시작 뒤에는 다시 조회해야 합니다.

- 잘못된 capability와 알 수 없는 요청은 동일한 404/no-store로 숨깁니다. 세 경로 모두 recovery cookie 동반을 허용하지만 status/evidence 권한은 capability에서만 나옵니다.
- 새 요청 접수는 actor generation을 먼저 durable fence한 뒤 기존 단기·장기 field session을 폐기합니다. gateway는 서버·학습·백업 삭제 완료를 추정하지 않고 backend의 canonical v2 상태와 durable evidence만 반영합니다.
- 단말 삭제 증거의 `evidence_sha256`은 단말이 제출한 요청·설치 ID·결과·시각 문장을 다시 계산해 전송 내용의 정합성만 확인합니다. gateway는 이를 "단말이 제출한 삭제 결과"로만 보관·전달하며, 단말 저장소에서 자료가 물리적으로 삭제됐다는 독립 증명으로 취급하지 않습니다.

### 보고 목적 신뢰 경계 (FP-015)

- 개인정보 ledger의 프로세스 간 배타 잠금은 Linux `/usr/bin/flock`과 fd 3 상속을 runtime prerequisite로 요구한다. helper 부재, timeout, 비정상 종료는 fail-closed하며 stable `ledger.lock` path는 삭제하지 않고 process crash 시 kernel fd close로 자동 해제된다.

- `x-walksafe-report-purpose`는 gateway가 인증한 first-party Android 앱의 선언이며 암호학적 client attestation이 아니다.
- gateway는 이 header와 multipart `metadata.auto_reported`를 교차 확인하고 불일치하면 backend fetch 전에 fail-closed한다.
- 변조됐지만 유효한 자격 증명을 가진 Android client가 두 값을 함께 위조하는 경우는 이 gateway 계약의 `NOT_COVERED` 잔여 신뢰 경계다.
- `x-walksafe-network-transport`(`wifi|cellular`)도 같은 first-party 앱의 선언이다. gateway와 backend는 실제 통신망이나 사용자의 신고 의사를 독립적으로 증명하지 않는다.
- S19-34 현 단계 결정: 인증된 first-party 앱을 신뢰하는 범위를 유지하고, 등록 기기·배포 무결성 증명(attestation)은 도입하지 않는다(출시 전 재검토 대상). 나중에 도입하더라도 그것은 앱·기기 무결성의 근거일 뿐이며, 사용자의 실제 신고 의사나 실제 통신망 사용을 증명한다고 설명하지 않는다.
- report 요청에는 installation, consent control secret, policy, revision, receipt, current network transport, report purpose header가 모두 필요하다. transport/동의 precondition 누락은 428이며 선택 거부, stale receipt·generation, metadata 불일치는 각각 명시적 오류로 거부한다.
- 삭제 요청 replay는 암호화된 actor recovery envelope로 field 세션 폐기를 재시도한다. tombstone은 폐기 작업 성공 여부와 무관하게 기존 access·refresh를 즉시 거부한다.
- 로그인 없는 account-deletion POST에서 알 수 없는 request ID와 기존 request의 틀린 secret은 동일한 404/no-store 응답을 사용한다.
