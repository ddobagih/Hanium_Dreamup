## 리스크와 확인 필요
- 확인 필요: Android 실폰, USB 디버깅, ADB, LAN, HTTPS 중 어떤 접속 방식이 실제로 가능한지.
- 확인 필요: Docker/PostGIS와 local TCP가 가능한 일반 개발 세션인지. 같은 sandbox면 runtime 검증이 다시 막힐 수 있다.
- 확인 필요: reports 테스트 row/upload를 삭제할지, disposable DB를 쓸지, 보존할지.
- 확인 필요: `서울역으로 안내해줘`를 `set_destination`으로 확장할지 제품 판단 필요.
- 확인 필요: `/reports`, `/uploads`, status patch를 외부 공개 전 어떤 인증/권한 정책으로 제한할지.
- 리스크: LAN HTTP는 카메라, 마이크, 위치, service worker 권한이 secure context 문제로 막힐 수 있다.
- 리스크: fake detector는 UI/API/운영 흐름 근거일 뿐 정확도, 지연시간, 실제 보행 안전 근거가 아니다.
- 리스크: `source=server` headless PASS는 known-positive fixture smoke이며 실폰 목걸이 field 성능 근거와 분리해야 한다.
- 리스크: v2 모델은 class `0` baseline이다. 4개 위험 클래스 전체 서비스 성능으로 표현하면 안 된다.
- 리스크: `/` 사용률 99% 기록이 있어 full inference, 새 학습, 대형 산출물 생성은 보류 또는 별도 디스크 확보가 필요하다.
- 리스크: STT 8/8 성공은 known-intent 샘플 기준이다. 보행 중 잡음, 바람, 복수 화자, 실폰 마이크 성능으로 확대 해석하지 않는다.
- 리스크: TTS direct-call cache와 HTTP `X-Voice-Cached` 근거를 분리해야 한다.
- 리스크: 원본 이미지, 위치 데이터, 음성 샘플, 생성 WAV, `.pt`, `.onnx`, `runs/`, `outputs/`, dataset images/labels는 GitHub 업로드 대상이 아니다.
- 리스크: 실폰 테스트는 안전한 실내/통제 smoke로만 표현하고 실제 시각장애인 대상 현장 검증으로 쓰지 않는다.
