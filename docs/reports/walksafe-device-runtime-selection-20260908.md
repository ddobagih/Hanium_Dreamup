# WalkSafe 기기별 실행 구성 선택·부하 적응 구현 결과

2026-09-08. 원본 사용자 앱 기준. **1차 구현·통합·APK 업데이트 설치를 완료했다.** 단위 시험, 실기기 종료·취소·재진입, 실제 UI 부하에 따른 주기 조절을 확인했다. 원본 앱은 현재 로그인 화면이므로 로그인 이후 자동 점검·저장값 재사용 흐름의 실기기 E2E는 대기 상태다.

## 적용한 동작

1. 필수 기기 점검 PASS와 카메라 종료를 확인한 뒤, 필요한 경우 별도 성능 점검 화면을 연다. 설정의 `성능 다시 확인`으로 수동 실행할 수도 있다.
2. 최대 300초 안에 GPU 활용을 먼저 비교하고 CPU 기준과 비교한다. 가능한 CPU 스레드 수 1..N 모든 정수를 후보로 삼고 결과에 따라 탐색 순서를 조정한다. 한 번에 기존 실행기 A와 후보 B만 보유한다.
3. 같은 입력의 출력·라벨 대응, AB/BA 순서 교차와 반복 잡음, 실제 카메라/추적/Depth/UI 부하를 확인한다. 선별 뒤 최종 검증·카메라 관측·정리를 위한 시간을 남긴다. 전역 최적값을 증명하는 시험은 아니다.
4. 확인된 선택만 기기에 저장한다. 모델·입력·정밀도·라이브러리·OS·기능 범위·검증 입력이 바뀌면 기록을 재사용하지 않는다. 저장값과 실제 활성 실행기를 구분하며 실제 참조 교체와 기존 실행기 종료를 확인한다.
5. 사용 중에는 실제 처리 지연과 각 기능의 시간 예산 대비 초과량에 따라 추론 빈도와 여유 시간을 조절한다. 여러 번의 새 정상 관측이 쌓이면 점진적으로 복구한다. 일정 CPU/GPU 사용률을 예약하는 방식은 아니다.
6. 정상 조건의 지속 악화는 다음 안전한 전경 진입의 재점검 사유로 남긴다. 같은 실행 계약의 자동 재시도는 24시간 제한을 적용하며, 정상 기록을 매일 다시 측정하지 않는다. 수동 요청과 실행 복구는 별도로 처리한다.

입력 해상도 768, FLOAT32 모델, 기존 가중치와 인식 기준은 이번 작업에서 변경하지 않았다. CPU 전처리와 다음 프레임 GPU 계산의 중첩은 이 1차 선택 기능과 별개의 후속 범위다. 250ms는 초기 추론 간격이며 고정 하한이 아니다.

## 종료와 측정 경계

- 로그인·화면·초기설정·보행 상태가 바뀌면 늦은 결과의 적용을 막는다.
- 점검 입력은 실제 위험 안내·신고·제품 tracker에 들어가지 않는다.
- 300초에는 새 측정과 선택 수락을 끝낸다. 이미 실행 중인 native 작업과 이미지·카메라의 실제 종료는 뒤늦게 끝날 수 있다. 종료 실패를 해제 성공으로 표시하지 않는다.
- Depth가 유효하지 않은 관측으로 metric 성능 우위를 확정하지 않는다. CameraX 시험에서 관측하는 분석 프레임 간격은 preview FPS와 구분한다.
- 테스트용 이미지의 GT 비교는 실행 구성 변경의 회귀 확인이다. 전체 클래스 정확도나 실보행 안전성을 입증하지 않는다.

## 어느 부분이 얼마나 빨라졌는가

S20(SM-G981N, 이용 가능 프로세서 8)에서 원본 앱과 같은 모델·전처리 코드를 사용하는 분리된 점검 화면으로 CPU 기준과 GPU 후보를 비교했다. 첫 측정에서 CPU 모델 스레드4를 기준으로 GPU 활용·잔여 CPU 모델 스레드5가 선택됐다. 5는 이 측정의 결과이며 다른 기기에 고정하지 않는다.

| 실제 카메라 입력 관측 | CPU 기준, 모델 스레드4 | GPU 활용, 잔여 CPU 모델 스레드5 |
|---|---:|---:|
| 입력 확보부터 최종 인식 완료까지 중앙값 | 548ms | 191.5ms |
| 유효 인식 완료 | 15회 / 10.206초 | 40회 / 10.074초 |
| 관측 시간당 유효 인식 완료율 | 약 1.47회/초 | 약 3.97회/초 |
| 가장 긴 인식 완료 간격 | 698ms | 276ms |
| 관측 카메라 프레임 간격 | 33.60ms | 33.61ms |
| 관측 stale / dropped 입력 | 0 / 0 | 0 / 0 |

이 짧은 비교에서 입력 준비·모델 실행·결과 해석을 포함한 완료 지연 중앙값은 약 **65% 감소**했다. native 모델 계산 시간만을 따로 나타낸 수치는 아니다. CPU 입력 준비와 GPU 지원 모델 연산·CPU 잔여 연산의 역할 분담을 이용하며, 앱이 CPU/GPU 사용률을 일정 비율로 예약한 결과도 아니다.

두 창 모두 ARCore TRACKING, 유효 pose, fresh 양수 Depth 표본을 관측했다. 카메라 간격은 약 29.8프레임/초에 해당하며 **ARCore Depth가 초당 60번 새로 생성됐다는 근거가 아니다**. 인식 완료율도 60FPS가 아니다. 짧은 분리 화면의 결과를 보행 중 Main 전체 성능으로 확대하지 않는다.

같은 고정 입력 4개에 대한 출력 대응·라벨 매칭과 A→B/B→A/별도 확인 비교를 통과했다. 입력은 COCO 사진3개와 검은 무객체 입력1개이며 version/hash와 배포 조건을 assets에 보관했다. 이 축소 묶음은 모든 클래스·임계값 주변·현장 오탐을 포괄하지 않는다. 첫 측정의 live 콜백에 객체 개수 계측이 없어서 카메라 장면에서 실제 인식된 객체 수와 박스 추적 성공률은 미확인이다.

## 실기기 시험에서 발견한 문제와 재검증

| 시험 | 관측과 판정 |
|---|---|
| 1차 metric 비교 | 243.058초에 GPU5 우위 확인, 실제 참조 교체1회·기존 CPU 실행기 실제 close1회. 이후 종료 타이머 스레드 잔류로 **전체 lifecycle 시험 실패** |
| 수정 | 일반 shutdown 뒤에도 예약된 300초 작업이 남는 문제를 수정. 세션은 지연 작업의 shutdown 후 실행을 금지하고, runner는 예약 future를 취소한 뒤 종료. 실행 중 native 연산은 강제 중단하지 않음 |
| 2차 metric 구간 | 300.345초에 실제 정리 완료. 표본으로 확보한 서로 다른 카메라 시각 최소8,927개와 AR TRACKING은 관측했으나 runner 시작 관문을 통과하지 못해 **NOT_EVALUATED**. 총 프레임 수를 센 값은 아니며 성능 선택·교체0회 |
| 2차 취소·재진입 | 실제 CameraX Image를 보유한 채 화면 pause 취소, 카메라 재획득 뒤 명시적 취소, image/runner/camera 종료, 최종 detector close와 executor 종료 모두 PASS |

2차의 시작 조건은 pose·시각이 일치하는 fresh Depth·양수 표본·프레임 간격·UI 지연을 함께 요구한다. 당시 시작 전 각 조건을 개별 기록하지 않아 **어느 조건이 충족되지 않았는지는 미확인**이다. runner 이후 Depth 콜백이0이라는 사실만으로 Depth 미지원/고장을 결론내릴 수 없다. 독립 코드 검토에서 타이머 수정에 따른 시작 차단 결함은 발견하지 못했다. 정상 장면을 확보한 다음 진단에서는 시작 전 조건별 관측을 함께 확인해야 한다.

첫 비교의 성능 관측과 최종 APK의 lifecycle PASS를 구분한다. 최종 수정본에서 metric 성능 우위를 다시 확인한 것은 아니다. 취소 시험은 실제 이미지 소유 중단을 확인했지만 취소 순간 native invoke 내부였음은 관측되지 않아 그 특정 시점의 실기기 취소까지 입증하지 않는다. A/B 소유 경로는 확인했으며 모든 native 할당의 최대 개수를 전수 계측한 시험은 아니다.

2차 instrumentation 전체337.25초에는 별개 세션인 metric 최대300초와 취소/재진입 시험 약36초가 포함된다. 제품 점검 한 번의 측정 예산을 300초보다 늘린 것이 아니다.

## 사용 중 부하 조절 시험

실제 Android 메인 Handler를 시험용으로181ms 지연시켜 UI 지연 관측→주기 조절→회복을 시험했다. 화면 예산17ms에 대해 실제 probe 지연82ms를 관측했고, 추론 시작 간격이 200ms에서400ms로 늘어났다. 이후 새 정상 관측48개가 쌓인 약24초 동안 점진적으로 회복해125ms가 됐다. 오래된 프레임 계측 재사용 방지, 한 번 소비한 관측 재사용 방지, pause 뒤 예약 콜백 억제도 PASS다.

이 시험의 모델 처리 시간80ms는 정책에 넣은 합성 입력이다. **실제 UI 지연 신호와 정책 연결**을 검증했으며 카메라·Depth·모델 동시 부하, 다른 앱의 특정 자원 점유율, 실제 모델이125ms 간격을 유지한다는 시험은 아니다. 발열·절전·환경 변화·지속 악화 정책은 별도의 회귀 시험으로 확인했다.

## 다음 검증과 근거

1. 사용자가 원본 앱에 로그인한 뒤 필수 점검 PASS → 자동 성능 점검 → 결과 저장·재사용 → 설정 수동 재점검을 확인한다. 로그인과 저장값 복원·계정 변경·화면 전환의 코드는 연결했지만 해당 제품 화면 흐름의 실기기 E2E는 아직 통과한 상태가 아니다.
