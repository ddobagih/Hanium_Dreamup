2026-09-09. **별도 시험 APK의 구현·실행·검증을 완료했다. 원본 사용자 앱과 모델은 교체하지 않았다.** 이름을 몰라도 영역을 만드는 후보 FastSAM 640과 현행 YOLO26n 768을 연결했고, 부분 깊이 처리와 Android 실행 비용을 개선했다. 실제 접근 위험 판정이나 제품 채택을 완료한 결과는 아니다.

- 작은 분리 조각 때문에 본체 거리까지 없어지던 10개 사례에서 **본체의 부분 거리**를 보존했다. 전체 거리로 승격하거나 작은 조각을 삭제하지 않았다.
- 같은 고정 입력 조건에서 snapshot부터 추가 모델·마스크·깊이 처리가 끝날 때까지의 중앙값이 **1,111.6 → 515.1ms**로 줄었다. 모델 호출 자체는 **156.9 → 156.6ms**로 거의 같았다. 출력 복사·중복 검사·할당·정렬 등의 비용이 줄었다.
- 마지막 foreground 시험의 같은 프레임 결합 결과는 순차 **2.30회/초**, 두 GPU 작업 스레드 **2.38회/초**다. 두 모델 각각의 완료 횟수와 결합 횟수를 구분해야 한다.
- 후면이 바닥을 향한 실제 카메라 시험에서는 추적이 PAUSED/INSUFFICIENT_LIGHT였고 유효 깊이가 없었다. **ARCore의 물리거리 정확도, 60fps 깊이, 보행 안전성은 확인하지 못했다.**

## 1. 작은 조각과 부분 깊이 정책

전체 매핑 마스크의 거리 `KNOWN`, 지배 영역의 거리만 확인 `PARTIAL`, 거리 `UNKNOWN`을 구분한다. 가장 큰 원래 depth-grid 연결 영역이 **깊이 격자에 매핑된 마스크 면적의 80% 이상**이고 내부 깊이 표본 조건을 만족할 때 PARTIAL을 허용한다. PARTIAL의 전체 `axialDepthM`/`euclideanRangeM`는 null로 유지하고 `dominant_component_distance`만 별도 반환한다. 모든 연결 성분, 미확인 면적, 더 가까운 작은 성분을 보존한다.

이 범위는 깊이 화면 밖 RGB 영역이나 깊이 픽셀보다 작은 분리 조각까지 측정했다는 뜻이 아니다. 현재 정책은 `risk_eligible=false`이며 접근 위험 안내에 바로 사용할 완성된 판단이 아니다.

| 고정 RGB-D 4장 / GT 53개 | 개선 결과 | 남아 있는 한계 |
|---|---|---|
| FastSAM640, 기존 매칭 47개 | 37 KNOWN + 10 PARTIAL | GT 6개 미매칭 유지 |
| FastSAM768, 기존 매칭 48개 | 35 KNOWN + 13 PARTIAL | GT 5개 미매칭 유지 |
| GT 마스크 자체 53개 | 44 KNOWN + 7 PARTIAL + 2 UNKNOWN | 정답 영역에도 깊이 부족 존재 |
| FastSAM640 전체 제안 207개 | 154 KNOWN + 27 PARTIAL + 26 UNKNOWN | 제안 개수는 정답 객체 개수가 아님 |

기존 KNOWN의 거리값은 유지했다. FastSAM640의 새 PARTIAL 10개에서 본체 값과 GT 마스크 내 센서 Z 중앙값 차이 P95는 0.00839 source-Z 단위다. 이는 동일 센서 자료에서 선택한 픽셀 차이이며 실물 거리 오차가 아니다. UOIS 예시의 미터 관례를 이용했으나 예시별 원단위·카메라 보정의 독립 근거가 부족하므로 물리 정확도에 사용하지 않는다.

## 2. Android에서 줄인 처리 시간

S20 SM-G981N / Android13, 동일 모델과 공개 RGB-D 4장, 입력2Hz, 준비 후5초 워밍업·30초 측정, v4/v6 모두 background·열 상태0→0. FastSAM640 입력은 미리 계산된 동일 tensor여서 이 비교의 FastSAM 전처리 시간은 RGB 변환 성능이 아니다. 현행768은 실제 RGB 전처리를 한다.

| 구간 P50, ms | 초기 시험 v4 | 개선 시험 v6 |
|---|---:|---:|
| FastSAM 모델 호출 | 156.9 | 156.6 |
| FastSAM 출력 읽기 | 155.7 | 10.4 |
| 전체 유한값 검사·후보 필터·NMS | 54.4 | 18.9 |
| 마스크 복원 | 11.9 | 30.7 |
| 깊이 연결·집계 | 323.1 | 188.9 |
| FastSAM 대기 | 421.4 | 107.2 |
| snapshot → FastSAM 완료 | 1111.6 | 515.1 |

현행768 RGB 전처리는 75.1 → 2.4ms였다. 개별 구간 중앙값을 더해서 전체 중앙값으로 계산하지 않았다. 마스크 복원 등 모든 구간이 개별적으로 빨라진 것은 아니며, 처리되는 장면 비중과 실행 상태 영향도 있다. 단일 회차 비교로 장시간 평균 향상률을 확정하지 않는다.

지연값의 모집단은 측정 구간에 입장한 작업으로, 구간 뒤에 끝난 drain도 포함한다. 완료/초는 구간 안에 완료한 작업, 수락/초는 실제 결정 시각의 나이·측정 구간 검사를 통과한 작업만 센다. 지연 시작점은 snapshot의 host 측 캡처 시각이다. live에서는 CPU 카메라 이미지 획득·복사 직전에 기록하며 센서 노출부터 이 지점까지의 앞선 지연은 포함하지 않는다.

30초에 입장한 작업은 양쪽60개였다. 초기에는35개 결합 완료 중25개가 1초를 넘겨 제외됐고10개를 수락했다. 개선 후60개 결합 완료 중 지연 탈락은0개, 측정 구간 뒤 완료1개를 제외한59개를 수락했다. **1초는 이번 시험의 결과 나이 기준**이며 현장 안전 임계값이 아니다. 개선 후1.97회/초는2Hz 입력에 제한된 값이므로 최대 처리량으로 해석하지 않는다.

구현은 출력 FloatBuffer 일괄 복사, 중복 유한값 검사 제거, 전체 NaN/Infinity 검사를 보존한 동치 범위 비교, 입력 버퍼·리사이즈 좌표 재사용, 깊이 계산의 반복 할당·정렬 감소, geometry-only 좌표 캐시, ARCore YUV plane bulk copy다. 깊이값·마스크·시각을 캐시하지 않는다. **새 시험 코드의 초기 구현 대비 개선이며, 원본 앱이 위 배율만큼 빨라졌다는 뜻은 아니다.**

## 3. 순차 GPU와 두 GPU 작업 스레드 비교

최종 v8, 동일 APK, 모델 준비 전 foreground Activity, 공개 RGB-D 실제 RGB 전처리,10Hz 입력,5초 워밍업·40초 측정. 각 장면을50회 입장 동안 유지해 약5초씩 네 장을 순환한다. 네 장의 실제 처리 및 입력 비중은 독립 이벤트 검토 자료에 남겼다. 정적 장면 반복이지 동영상·새 깊이 관측은 아니다. 이 재생에는 ARCore 카메라 획득 비용이 없다.

| 실행 방식 | 현행768 완료/초 | FastSAM+마스크·깊이 완료/초 | 같은 프레임 수락/초 | 결합 결정 나이 P50 / P95 ms | 열 상태 |
|---|---:|---:|---:|---:|---|
| 한 작업 스레드에서 두 모델 순차 GPU | 2.33 | 2.30 | 2.30 | 488 / 544 | 0 → 0 |
| 두 작업 스레드에서 GPU 요청 | 9.03 | 2.38 | 2.38 | 485 / 537 | 0 → 1 |

양쪽 모두 같은 입력 비중이었다. 처리 장면 비중은 완전히 같지는 않으므로 아래에 함께 남긴다. FastSAM 완료는 측정 구간에 입장한 작업 전체(구간 뒤 완료 포함), 수락은 실제 결정이 구간 안인 결과다.

| 장면 | 입력: 순차 / 두 스레드 | FastSAM 완료: 순차 / 두 스레드 | 결합 수락: 순차 / 두 스레드 |
|---|---:|---:|---:|
| OCID_image_0 | 96 / 96 | 25 / 27 | 24 / 26 |
| OCID_image_1 | 100 / 100 | 24 / 24 | 24 / 24 |
| OSD_image_0 | 100 / 100 | 22 / 23 | 22 / 23 |
| OSD_image_1 | 100 / 100 | 22 / 22 | 22 / 22 |

기존768의 결과 빈도를 유지하는 관점에서는 두 작업 스레드 방식이 유망했다. 다만 결합 처리량의 2.30 대 2.375회/초 차이는 작고, 열 종료 상태도 달랐다(순차0, 두 스레드1). 이 차이를 실행 방식의 확정적인 우월성으로 해석하지 않는다. S20의 한 조건에서 관측한 절충 관계다.

`shared_gpu`는 한 소유 스레드가 현행 모델 → FastSAM → 마스크·깊이를 순서대로 수행한다. `separate_gpu`는 두 스레드가 같은 GPU에 일을 요청하고 CPU 후처리를 함께 수행한다. GPU가 두 개 생기는 방식이 아니다. 서로 다른 프레임의 완료 결과는 결합하지 않는다. 따라서 두 완료 FPS를 합치거나 더 빠른 모델 FPS를 전체 FPS로 부르지 않는다.

실제 native 로그에서 현행 모델은477개 중444개 노드가 GPU에 위임됐고 FastSAM은289/289였다. 현행 모델의 일부 CPU 연산과 전후처리는 CPU가 맡는다. CPU fallback 스레드4는 이번 고정 실험 조건이며 기기별 최적 스레드 수를 찾은 결과가 아니다. ARCore 내부 TFLite 로그는 두 모델의 위임 개수에서 제외했다.

최종 두 회차의 모델 준비는 각각 51.4 / 50.8초, 준비·워밍업·측정·종료 전체는 96.8 / 96.1초였다. 회차별5분 상한 안에 끝났지만,40초 측정으로 장시간 발열이나 다른 앱의 자원 경쟁을 모두 검증한 것은 아니다. 이 S20 조건의 비교를 모든 기기의 고정 스케줄로 채택하지 않는다.

## 4. 실제 ARCore 카메라 관측

사용자가 허용한 후면 바닥 방향을 유지했다. ARCore1.54에서 AUTOMATIC/raw depth 지원은 true이고 카메라 설정은640×480/30fps였다. 지원 여부와 실제 유효 깊이 여부는 별개다. 아래 카메라 값은 루프가 관측한 고유 timestamp 빈도이지 센서 전체 발생 FPS가 아니다.

| 시험 | 관측 카메라/초 | 수락 결과/초 | 열 상태 |
|---|---:|---:|---|
| 현행768 단독, 초기 v4 | 19.47 | 6.40 | 0 → 0 |
| 현행768 단독, 개선 v5 | 28.47 | 14.27 | 0 → 1 |
| 두 모델 순차, 개선 v6 | 20.90 | 4.00 | 0 → 1 |
| 두 작업 스레드, 개선 v6 | 12.03 | 3.17 | 0 → 1 |

단독 행은 현행 모델 결과, 두 모델 행은 같은 프레임 결합 결과다. 마지막 두 모델 시험에서는 마스크0개·유효 raw/full depth0개였으므로 물체가 많은 장면의 깊이 계산 성능으로 볼 수 없다. 단독v4/v5도 열 종료 상태가 달라 엄밀한 장시간 동등 조건 비교가 아니다. 공개 재생의 깊이 계산 FPS와 실제 카메라 FPS를 합쳐 제품 전체 FPS를 추정하지 않는다.

## 5. 검증과 발견한 문제

- Python 합성 깊이62시험, Java 정책81사례 대조·66assertion, geometry cache 경계41검사, 캡처 stride/좌표/수명·산술 일치261검사 통과.
- Java 마스크 복원은 고정8장514개가 명시적 float32/crop 기준과 픽셀 일치했다. 유한값 정상84·비정상72·원시 bit pattern1,003,072개 회귀도 통과했다.
- 최종 공개 RGB-D 각 회차에서 휴대폰 원출력, ROI bit mask, 양자화된 같은 깊이 입력의 상태·성분·수치를 독립 비교했다. 상세 판정은 검토 보고서를 따른다.
- 결합 결과의 완료 시각과 실제 채택 결정 시각 사이 대기가 빠져 늦은 결과를 수락할 수 있는 문제를 독립 검토에서 발견했다. 실제 결정 시각으로 나이 검사를 옮기고21assertion 및 이전 구현을 실패시키는 검증을 수행했다.
- v7의4장/10Hz 순환은 latest1과 주기가 맞아 두 장만 FastSAM에 선택됐다. 이벤트 집계는 맞지만 네 장 전체 커버리지 실패는 보존했다. v8은 명시적 장면 유지 옵션을 추가했고 기존 기본값1을 보존했다. APK 변경은 재생 옵션과 버전에 한정했다.
- 원본 모델·설정·학습 체크포인트4개 SHA256은 시작 시점과 일치한다. 원본 사용자 앱의 소스·패키지·계정을 변경하지 않았다.
