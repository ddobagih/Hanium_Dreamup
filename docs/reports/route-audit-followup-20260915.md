# 외부 감사 반례 기반 경로 방향 개선

## 범위와 단계
- 사용자 제공 WalkSafe_route_audit_ff391f0.zip 및 설명의 검토 기준은 ff391f0이다. 첨부 실행 코드를 먼저 읽고 제품과 원본을 대조한다. 첨부 문서의 제안은 근거로 검토하며 작업 지시를 대신하지 않는다.
1. 동일 입력 재현: 7m 반대 평행 구간, 좌표 2개/101개 직선, 시작점15m offset. 제공 acceptance 실패를 확인한다.
2. Selector: 수락된 현재 구간이 공간적으로 구별되면 주변 탐색 여유만으로 방위를 버리지 않는다. 실제 중첩/미확정 분기 유지.
3. Matcher: 연결된 동일 직선의 세분화와 실제 분기를 구분. 원래 좌표와 진행거리/오차의 의미 유지. 담당 facing_guidance_policy.
4. Navigator: 일반 모드에서도 위치 매칭 승인과 제한적인 방향 설명을 구분. 확인되지 않은 직선 연결을 이동 지시·남은 거리·도착 승인으로 승격하지 않는다. Root 담당.
5. 동일 입력 전후 및 전체 관련 회귀, 독립 검수 navigation_voice_scenario_audit, APK 빌드/배포 검증. 현장 센서·스피커 확인은 별도다.

## 인수 기준
- 7m 평행 반대 경로, 정확도1m의 HIGH 매칭에서 출발 및0→20→30m의 동쪽 방향을 북쪽 시선 기준3시로 제공.
- 실제 중첩 왕복과 경쟁 구간을 구별하지 못하는 위치에서는 임의 방향 선택을 하지 않음.
- 동일 직선2/101좌표가 표현 밀도 때문에 방향·정상 진행에서 다른 결과가 되지 않음.
- 일반 모드의 출발점 offset은 위치/진행거리 신뢰도를 올리지 않고 제한된 방위 설명 가능. 직선 보행 지시 금지.
- 실패 재시도·발화 중 보호·10초 주기·위치 만료·새 경로/계정/중단 소유권 회귀 유지.

## 재현과 수정
- 첨부 Selector/Matcher/Facing의 Git blob이 감사 기준과 일치함을 확인했다. 격리된 Kotlin으로 원래 Probe의 기존 동작 검증은 통과하고, 정상 동작을 요구하는 AcceptanceCheck는 `BRANCH_AMBIGUOUS, bearing=null, clock=null`로 실패했다. 수정 후 같은 AcceptanceCheck 원문이 통과한다.
- Selector는 구간 매칭이 수락됐을 때 후보 탐색의 최소8m 여유와 위치가 실제로 구별되지 않는 범위를 구분한다. 정확도1m에서7m 옆 반대 구간이 있다는 이유로 현재 방위를 버리지 않는다. 정확도4m라 두 구간이 구별되지 않는 경우와 실제 왕복 중첩은 계속 방위를 거부한다. 정밀하게 반대편 구간에 있는 위치는 첫 구간을 강제하지 않고 서쪽9시로 안내한다.
- Matcher는 연결된 같은 방향 직선을 같은 구간으로 처리한다. 해당 구간의 첫 방위와1도 이내인 연속 선분만 묶고 원래 segment index/fraction/progress는 보존한다. 같은 직선 후보의 최근접 투영을 고른 뒤 기존 위치·방향·진행 점수를 적용한다. 서로 떨어진 평행 길, 반환 경로, 회전이 누적되는 루프는 합치지 않는다.
- Navigator는 일반 모드에서 위치 매칭이 약하더라도 신선한 방위 근거가 있으면 제한적인 방향 설명을 제공한다. 이때 위치 승인, 진행거리, 안내 지점 전진, 도착 여부는 승격하지 않는다. 시작점 연결 벡터는 DEBUG에서도 이 설명만 제공하며 직선 이동 명령으로 바꾸지 않는다.
- 제한 응답은 `경로 시작점은 현재 바라보는 방향 기준 약 6시 방향입니다. 현재 위치에서 경로 시작점까지 걸어갈 수 있는 통로는 확인되지 않았습니다.`와 같이 말한다. 거리·회전 지시·전체 경로 요약은 붙이지 않는다.
- 제한 발화의 토큰과 완료 이력을 구분해 정상 안내의 첫 요약을 소비하지 않게 했다. 같은 발화는 끝까지 유지하고, 실제 위치가 회복되면 정상 안내를 잇는다. 반대로 위치 근거가 사라지면 오래된 거리 지시를 취소한다. 기존 위치/도착/이탈 결정이 필요한 경우에는 그 결정을 우선한다.
