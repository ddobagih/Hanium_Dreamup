# FastSAM768 전환 실행 보고서

2026-09-09. **0~2단계 별도 APK 전환·성능 비교·회귀 검증 완료**. 기존 YOLO26n768과 함께 사용하는 별도 시험 APK의 결과이며 원본 사용자 앱의 기능 완료 보고서가 아니다. 후면이 바닥을 향한 S20 조건을 유지했다. 원본 모델 교체는 보류했다.

## 현재 완료 범위

- FastSAM768 모델 계약·입력 역할 분리·Android 마스크 복원·깊이 연결·CPU/GPU 분업을 구현했다. 최종 version10 별도 APK를 빌드·설치했다.
- 공개 RGB-D 4장에 대해 실제 S20 GPU 출력에서 얻은 233개 마스크·401개 성분을 검증했다. 167개 KNOWN·33개 PARTIAL·33개 UNKNOWN이다. PARTIAL은 전체 객체 거리로 사용하지 않는다.
- CPU 기준과 Java의 정적 8장·544개 마스크가 일치했다. 실제 휴대폰의 4장·233개 마스크도 독립적으로 일치했다. 동일 공개 reference Z 연결 검사이며 ARCore 물리 정확도 검증은 아니다.
- 동적 MOVi-E 24프레임·지속 객체 ID 10개·RGB/깊이/카메라 자세 자료를 확보했다. 256 원본을 768에 입력한 합성 자료이므로 768 해상도의 우월성이나 실제 미터 정확도를 증명하지 않는다.

## 전환 중 수정한 문제

기존 replay 코드는 크기 768을 기존 YOLO 입력으로 해석했다. FastSAM도 768로 바꾸면 길이가 같은 7,077,888바이트의 다른 전처리 입력을 받을 수 있었다. 이제 PRIMARY/FAST 역할을 명시하며 잘못된 역할은 버퍼를 수정하거나 모델을 실행하기 전에 거부한다. 기존 `input768`은 primary 의미를 유지하고 FastSAM용은 `fastSamInput768`으로 구분한다.

768 크기 조절에서는 기존 실수 bilinear와 OpenCV uint8의 반올림 차이가 드러났다. 채널당 최대 1LSB 차이가 CPU 모델의 마스크 수를 544→543으로 바꾸고, anchor 16개 제거·15개 추가를 만들었다. 이 실패 자료를 보존하고 FastSAM 전처리를 canonical과 맞췄다. 수정 후 실제 Java의 공개 8장과 추가 5개 비율, 총 92,012,544바이트가 기준과 정확히 같다. 기존 primary 전처리도 별도 5개 비율로 보존을 확인했다.

출력 계약은 검출 `[1,37,12096]`, prototype `[1,192,192,32]`이다. 입력·출력 shape/SHA와 실제 로딩 모델의 역할을 시험 결과에 기록한다. 640 decoder·APK·시험 기록은 phase2에 보존했다.

입력 자체가 10Hz이므로 9.9회/초는 기존 모델의 최대 처리 능력 측정값이 아니다. 각 조건 1회이고 열 상태가 다르므로 기종 공통 최적값이나 영구 선택으로 저장하지 않았다. 과거640의 같은 구성은 약2.3~2.375회/초였다. 768은 더 많은 영역과 더 큰 tensor를 처리하므로 이전보다 빨라졌다고 주장하지 않는다.

순차 실행의 FastSAM 단계 P50은 전처리22.5ms, 모델182.4ms, 출력 읽기6.0ms, 마스크 후처리29.0ms, 깊이193.9ms다. 각 단계의 중앙값을 더한 값을 전체 중앙값으로 취급하지 않는다. 순차 실행에서는 CPU 후처리 동안 같은 GPU 소유 스레드가 기존 모델을 실행하지 못한다. 두 GPU 스레드는 기존 모델을 계속 실행하지만 FastSAM 모델 호출이250.6ms로 길어졌다. 이를 근거로 **GPU 모델 연산 + 별도 CPU 마스크/깊이 후처리**를 세 번째 후보로 구현·검증했다.

단계별 시간은 측정 중 접수한 작업의 마지막 drain까지 포함하며, 실제 판정 나이는 거절된 pair도 포함한다. 완료 빈도는 측정 종료 안에 완료한 작업만 센다. 장면별 처리 개수와 단계별 분포를 원자료에서 분리하고, 장면 평균에 같은 가중치를 준 수치도 제공한다. 입력 비중이 같아도 느린 장면의 완료 횟수는 달라질 수 있다.

나이의 원점은 host capture 시각이다. 특히 live의 `capturedElapsedNs`는 `Session.update` 이후 CPU image 획득 직전의 앱 시각이며, 이미지 복사 완료나 센서 노출 시각이 아니다. 센서 노출부터 음성 시작까지의 전체 지연으로 사용하지 않는다.

### version10에서 실제 바꾼 것

깊이 샘플의 인덱스 수집과 정렬을 최적화했다. 정수 밀리미터 자료는 동일 값의 counting sort를 사용하고 작은 표본·드문드문한 범위·실수 깊이는 기존 비교 정렬로 돌아간다. 정책·범위·작은 성분·샘플 개수는 유지했다. 호스트 P50은14.63→8.97ms였지만 **휴대폰의 장면 동일 가중 평균은217.54→210.10ms, 3.42% 감소**였다. 휴대폰 aggregate P50은193.90→183.68ms다. PC의38.7% 개선을 휴대폰 수치로 쓰지 않는다.

새 `shared_gpu_cpu_post`는 한 GPU 소유 스레드에서 두 모델을 실행하고 별도 CPU 스레드가 FastSAM 마스크·깊이를 처리한다. CPU가 후처리하는 동안 기존 모델 호출이 계속 진행된다. FastSAM은 전체 논리 작업1개만 허용해 출력·같은 프레임의 깊이를 덮어쓰지 않는다. CPU 후처리와 공개 시험 자료 기록이 끝나야 다음 FastSAM 작업을 받는다. 새 결과가 생겼다고 오래된 결과의 나이를 갱신하지 않는다.

실제 첫 실행에서 GPU 소유 스레드67과 CPU 스레드68을 확인했다. warmup 포함88개 예약·제출·완료가 일치했고 실패0, 두 스레드는 종료됐다. 보수적으로 계산한 host 호출 구간에서도 기존 모델258회가 CPU 후처리79구간과 약13.99초 겹쳤다. 이는 CPU 후처리와 모델 호출의 겹침 증거이며 GPU 하드웨어 kernel의 동시 실행 측정은 아니다.

첫 분업 실행의 시작 배터리 온도34.1℃는 순차 실행31.4℃보다 높았다. 열 상태도0→2로 올라갔다. 배터리32.4℃·열 상태0까지 냉각한 다음 별도 회차를 수행했다. 두 결과 수락은1.95회/초로 순차1.925회/초와 거의 같았고, 기존 모델 완료는1.95→7.775회/초, 판정 나이P50은557.4→498.1ms로 관측됐다. 분업의 주효과는 기존 모델을 계속 실행하게 하는 것이며 추가 영역 처리량의 대폭 향상은 아니다. 기존 모델만 실행한9.9회/초를 모두 보존한 것도 아니다. 냉각 후에도 시작 온도는 순차31.4℃와1℃ 차이였고 종료 열 상태는1이었다. 자동 최적값으로 채택하지 않았다. 실제5개 결합 실행(v9 순차·분리, v10 순차·분업2회)의 공개8개 tensor와233개 마스크·401개 성분은 모두 일치했다.

## 5분 기기 점검 연결

현재 사용자 앱의 선택기·저장소는 단일 모델 계약이다. 두 모델 SHA/shape·각 전처리/decoder·backend/thread·스케줄에 결속된 조합 프로필로 확장해야 한다. 단일 모델의 검증 완료 기록을 그대로 재사용하지 않는다. 기존 카메라 소유권·취소·결과 검증·채택 순서를 재사용하며 별도 점검 프레임워크는 만들지 않는다.

후보마다5분이 아니라 준비·warmup·비교·정리 전체가5분이다. 개발 시험은 매회 앱 예산280초, host 감시290초, 강제 중지10초를 두어 기록한다. native 호출의 실제 종료가 항상 마감 안에 보장된다는 뜻은 아니다. 중지 실패나 USB 수집 실패가 발생해도 먼저 실행 결과를 파일에 남기도록 runner를 수정했고, 실패 시뮬레이션12경우를 독립 검증했다.

20초 창 3회 지속 악화는 재평가 예약 근거다. 현재 기존 앱의 자동 재시도에는 24시간 간격과 안전한 전경 진입 조건도 있다. 수동 재점검은 간격을 건너뛴다. 조합 연결 시 이 조건과 실제 부하·모델별 완료율을 함께 검증해야 한다. 지금은 새 조합을 `CONFIRMED`로 등록하지 않았다.

### 같은 물체 추적·운동 정책의 실제 제한

실제 앱의 tracker·추정기·메시지 정책 소스를 복사해 JVM에서 직접 호출했다. 원본14개 probe와 기존57개 JUnit, 별도 최소 수정 후보의16개 probe와57개 JUnit을 실행했다. 원본 앱 소스는 수정하지 않았다.

- 카메라 위치는 고정하고 방향만0→30° 회전하면 camera Z가6→5.196으로 줄어 일반 접근 WARNING이 나왔다. 객체 자체가 이동한다는 문구는 아니지만 회전만으로 생긴 거리 감소를 경고하는 문제였다. 시험 후보는 이 좁은 회전 조건의 Z/TTC 근거를 보류하고, 실제 접근·사용자 병진·근거리 STOP·pose 부재 fallback을 유지했다.
- 대표 깊이 성분이 바뀔 때 기존 `invalidateMotionEvidence`는 이후 과거 이력을 다시 사용할 수 있었다. 대신 `markMissed`로 끊으면 ID도 바뀌었다. 시험 후보는 ID를 보존하면서 거리·공간 이력을 지우는 별도 API를 추가했다. 7프레임의 ID 수4→1, 새 깊이4개가 모이기 전 방향 UNKNOWN 유지, 중복 raw depth는 새 표본으로 세지 않는 것을 확인했다.
- 실제 예측666개를 넣은 시퀀스에서 시험 후보의 생성 ID는600→552였다. 여전히 과도하다. 새 ID552개 중496개는 여러 후보가 겹쳐 기존 bbox 연결이 모호한 경우였다. GT 마스크 입력은150→49, GT의 정답3D 중심 입력은49→49로 구분해 원인을 확인했다.
- 실제 예측과 매칭된168건 중 방향을 산출한 것은6건이며 **모두 정지 사례**다. 움직이는 물체가 다가오는 방향을 성공적으로 판별했다는 결과는 없다.

독립 검토에서 첫 수정 후보의 추가 실패도 발견했다. 198ms의 짧은 관측에서 실제0.2m/s 접근이5cm 이내라는 이유로 억제됐고, legacy raw 시각 역행도 새 gate를 통과했다. 첫 후보와 반례를 보존한 뒤, 유효한 독립 공간 이력4개 이상·600ms 이상·단조 증가 시각만 회전 억제 근거로 허용하는 후보v2로 수정했다. 짧은 실제 접근과 시각 역행에서는 기존 접근 판정을 유지한다. 모델·추적 독립 검토 담당이 두 반례를 새 v2에 다시 실행해 해소를 확인했다. 다음 추적 개선은 기존 tracker에 mask 겹침·깊이·pose를 반영한 대응 점수를 선택적으로 공급하고, 명확한 최우선 대응과 모호성 보류를 비교하는 것이다. IoU 임계값만 무작정 낮추지 않는다. 별도 평가 시퀀스에서도 ID 전환·분절·잘못된 접근을 확인하기 전에는 원본 앱의 접근 안내로 채택하지 않는다.

## 실제 ARCore·pose 연결

최종v10의 바닥 방향 live 시험은5초 warmup 뒤15초를 측정했다. 카메라 설정은30fps, 실제 측정 캡처는329회/15초=21.93회/초였다. 기존 모델 완료3.733회/초, FastSAM·동일 시점 결과 수락3.667회/초, 판정 나이P50/P95는329.9/370.5ms였다. 후보78개는 전부 거리UNKNOWN이었고, raw/full 양수 깊이 픽셀은0이었다. 공개4장보다 후보 수와 깊이 격자가 작고 유효 거리도 없는 조건이므로 물체가 많은 실장면 성능으로 확대하지 않는다.

warmup을 포함한 source 생애20.807초의425개 snapshot은24개NOT_TRACKING,1개REFERENCE_STARTED,400개연속 기준 pose였다. 실제 anchor1개 생성·detach1회 성공, session pause/close와EGL close를 확인했다. 이미지·수치 pose·live tensor는 저장하지 않았다. 기준 재설정·재지역화·수치 pose 정확도와 실제 물체 접근은 아직 검증하지 않았다.

이번에는 실제 TRACKING이 관측됐지만 깊이값은 여전히 없었다. 고유 raw timestamp204개와 내부 timestamp ledger 증가를 유효 거리 관측으로 세지 않는다. 초기 availability 조회는UNKNOWN_ERROR였지만 실제 session 생성과 이미지/깊이 획득은 성공했으므로 서로 구분해 기록했다. 유효 깊이60fps나 물리 거리 정확도 통과를 주장하지 않는다.

캡처 단계에서는 YUV→RGB 산술이 source 전체 평균35.90ms로 관측돼 후속 최적화 지점으로 남았다. 이번 코드는 기존 primary RGB 의미를 보존하며 이 산술은 바꾸지 않았다. 추가 최적화도 처리량과 입력 동등성을 함께 검증해야 한다.

## 남은 검증

- 다음 단일 구현: 이름 없는 mask의 중첩을 구분하는 tracker 대응 점수와 모호성 보류를 보완하고 별도 시퀀스에서 검증한다. 현 후보의 높은 ID 교체를 해소해야 한다.
- 기기 선택 연결: 두 모델 조합의 profile·검증·300초 예산·부하 대응 연결은 아직 미구현이다. 이번 읽기 전용 감사로 최소 변경 지점과 현재24시간 자동 재시도 조건을 확인했다.
- 실물 깊이: 유효 깊이와 독립 거리/이동 기준이 필요하다. 합성 깊이의 장면 단위를 ARCore 미터 답지로 사용하지 않는다.
- 원본 앱 통합 및 접근 음성: 위 결과를 근거로 연결한다. 실제 물체 접근과 사용자 전진을 구분해 안내하는 기능은 아직 제품 완료로 표시하지 않는다.

최종 시험 APK는 `kr.co.hanium.dreamup.walksafe.unknownbench`, version10이며 모델 파일은 시험 기기에 별도로 준비됐다. 일반 길안내 사용자 UI가 있는 배포 APK가 아니다. 원본 모델·설정·학습 체크포인트4개와 추적 검토 대상 운영/테스트18개를 보존했다. 실제7회 시험은 각각 준비·측정·종료가5분 안에 끝났고 중지 timeout·결과 수집 실패는 없었다.
