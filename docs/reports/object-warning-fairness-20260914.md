# 여러 객체의 경고 누락 개선 계획과 결과

## 범위와 의도

직전 개선에서 남겨 둔 동급 위험 4개 이상 중 뒤쪽 후보가 계속 안내에서 빠지는 문제를 해결한다. 더 높은 위험도 우선, 실제 전달 완료 기준 간격, 하나의 진행 중 전달, 대기 상한 3개와 기존 신선도·안정성 기준을 보존한다. 모델/768입력/Depth 기준/개발용 우회/서버 설정은 이번 변경 대상이 아니다.

## 단계별 계획

| 단계 | 작업 | 검증 |
| --- | --- | --- |
| 1 실패 재현 | 현재 제품 정책에 동일 4객체를 30초간 반복 입력 | 4번째 전달 0회 재현, 변경 전 코드·원출력 보존 |
| 2 동급 순서 | 실제 완료 이력으로 아직 미전달 또는 오래전에 전달한 동급 객체 우선 | 입력이 계속 같아도 전원이 전달 기회 획득; 높은 단계가 먼저 전달 |
| 3 상태 경계 | 예약·claim·실패·취소·후보 소멸과 새 보행 검증 | 실패를 전달 완료로 오인하지 않음, 현재 없는 후보는 전달되지 않음, 제한과 상한 유지 |
| 4 통합 | Main·Camera 후보 목록 연결 확인, 관련 회귀·다른 인스턴스 검토·APK 빌드 | 실제 호출 경로에서 후보가 미리 잘리지 않음, 추가 지적 수정, APK 결과 분리 보고 |

## 구현 결과

- 현재도 안정성·신뢰도·신선도 검사를 통과한 후보만 평가한다.
- 위험 단계가 높은 후보부터 선택한다. 같은 단계에서는 실제 전달 완료 이력이 없는 후보, 마지막 완료 순서가 오래된 후보, 기존 FIFO 순서로 선택한다.
- 예약·claim·실패·취소는 완료 이력을 갱신하지 않는다. 기존 실제 완료 시각 기반 전역 700ms·트랙 2,500ms 간격과 WARNING/STOP 승격 예외를 유지한다.
- 잠깐 입력에서 빠진 후보는 기존 TTL 1,500ms 안에서 FIFO 위치를 보존한다. 현재 후보가 들어갈 자리가 필요하면 빠진 후보를 먼저 내보내며, 현재 없는 후보는 발화 대상으로 선택하지 않는다.
- 진행 중 전달 1개와 진행 중 항목을 포함한 대기 상한 3개를 유지한다. 새로운 보행·안전 상태 초기화에서도 완료 순서 이력을 정리한다.

## 같은 입력 전후 비교

동일한 4개 STOP 후보를 매 1초, 30초간 입력하고 실제 제품의 claim→confirm API를 호출했다. 시간은 가상 시계이며 휴대폰 스피커 출력 측정은 아니다.

| 항목 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| A 완료 | 10 | 8 |
| B 완료 | 10 | 8 |
| C 완료 | 10 | 7 |
| D 완료 | 0 | 7 |
| 전체 완료 횟수 | 30 | 30 |

새 정책 회귀 7개를 수정 전 실제 정책으로 실행했을 때 3개가 실패했다. 첫 수정은 기존 취소 회귀 1개에서 FIFO 보존 문제를 일으켰고, 위의 TTL 보존·현재 후보 우선권으로 보완했다. 최종 직접 컴파일에서 새 7개와 기존 33개, **40개 모두 통과**했다. 실패 원출력은 덮어쓰지 않고 보존했다.

## 실제 연결 경계

- Main의 `AndroidTactileFrameCoordinator`는 PRIMARY 전체와 신선한 UNKNOWN 전체를 합쳐 정책에 전달한다. 정책에 넘기는 단계에서 후보를 3개로 자르지 않는다.
- `CameraTestFeedbackCoordinator`도 두 source의 신선한 전체 후보를 전달한다. 같은 물체를 양쪽 모델이 검출한 경우의 중복 영역 병합은 그대로 유지한다. 화면 표시 6개 제한은 음성 후보 전달과 별개다.
- **Main의 프레임 간 PRIMARY 추적 최대 3개는 별도의 작업량 제한으로 남아 있다.** 이번 수정은 실제 피드백 정책까지 계속 도달하는 동급 후보의 장시간 배제를 해결한다. 모든 탐지 객체가 음성 후보까지 도달한다고 주장하지 않는다. 추적 상한·우선순위 변경은 추가 처리시간과 객체 ID 안정화 검증이 필요한 별도 개선이다.

## 통합과 독립 검토 결과

- Main/Camera의 실제 coordinator를 대상으로 100ms마다 frame ID·원본 시각이 맞는 신선한 표본을 갱신했다. 4 PRIMARY 또는 3 PRIMARY+독립 UNKNOWN 후보가 반복 전에 모두 전달 기회를 받는지 확인했다. 동일 source 내 후보·서로 다른 source의 중복 병합·STOP 승격·만료·취소·단일 claim·700/2,500ms 간격도 검증했다.
- 위 새 통합 시험 **11개**는 이전 정책에서 **6개 실패 → 수정 정책에서 11개 통과**했다. 제품 호출부 변경은 필요하지 않았다.
- 구현과 다른 인스턴스가 정책을 직접 재컴파일하여 기존·새 회귀 40개 및 별도 경계 7개, **47개 통과**를 확인했다. 지연 완료 8후보, capacity 1·2·3의 진행+대기 상한, STOP 선점, 선택 취소, 재등장·TTL, 대기 중 위험 단계 하락을 추가 검사했고 확정 결함은 발견하지 않았다.
- 최종 Gradle **21 suites / 203 tests, 실패·오류·skip 0**, `:app:assembleDebug` 성공. Main·Camera 전체 Java/Kotlin 컴파일 포함. 이전 730개 전체 시험을 다시 실행한 것은 아니며, 이번 변경의 경고·후보 합침·전달·음성·카메라 관련 범위를 실행했다.
- 이전 검증 소스와 대조했을 때 제품 변경은 `WalkSafeFeedbackPolicy.kt` 하나다. 신규 회귀 파일 3개를 추가했고, 기존 테스트 기대를 낮추거나 변경하지 않았다. 변경하지 않은 모델·Depth 선별의 5,521개 고정 마스크 자료는 이번에는 다시 실행하지 않았다.
- 완료 순서 이력은 보행 중 실제 전달된 고유 track 수에 비례하며 새 보행 reset에서 비워진다. 이는 기존 트랙별 완료 시각·단계 이력과 같은 수명이며, 대기 상한 3개와는 별개다.

## 완료 범위와 다음 단계

4단계의 실패 재현·개선·상태 경계·독립 검토·통합 회귀·APK 빌드를 완료했다. Root가 정책·검증·통합을 담당하고 다른 인스턴스가 호출부 탐색·통합 시험·독립 검토를 맡았다. 휴대폰 스피커·야외 인식·FPS·발열·설치·push는 실행하지 않았다.

다음 개선은 Main의 프레임 간 PRIMARY 추적 3개 예산에서 오래 대기하는 탐지 객체를 어떻게 다룰지 검증하는 것이다. 현재 처리시간·안정성 근거 없이 동시 추적 개수만 늘리지는 않았다. 실제 카메라·음성 확인은 새 APK 설치 후 수행할 수 있다.
