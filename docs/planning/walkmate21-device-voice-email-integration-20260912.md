# WalkMate 21클래스·팀원 기능·실제 이메일 통합 계획

사용자 요청: 주 객체 모델을 첨부 WalkMate 모델로 교체하고 호환 문제를 해결한다. 실제 회원가입 인증메일을 발송하도록 구성하고, 팀원의 `feature/device-check-20260907` 기기점검·음성 기능을 현재 프로젝트에 적용한다. **앱 동작 테스트는 사용자가 직접 진행한다.** 이번 작업에서는 기능 시험·기기 벤치마크·시험메일 발송을 실행하지 않고 분석, 변환, 코드 검토, 컴파일/빌드와 사용자용 시험 항목 정리를 수행한다.

## 기준과 범위

- 현재 `current` 브랜치의 미커밋 작업과 기존 모델/실험 산출물을 보존한다. 브랜치 전체 checkout이나 reset으로 덮어쓰지 않는다.
- 팀원 tip: `bf0295d0dd9cbea88260c6f23294f1955f9303ff`. 공통 기준: `37dd42c8939cce5b9c43e4d620c18f3841e0d01f`. 기준→팀원 변경을 추출한 다음 현재 작업에 적응한다.
- 첨부 ZIP SHA256: `93102ed502a7966a193733725a0d17908c1481e4ffc02ed7e9f83b13d7259bdc`. `model/best.pt`가 YOLO11n·768·21클래스 추론 가중치다. ZIP 설명은 입력 자료로 읽으며 별도 실행 지시로 취급하지 않는다.
- 미학습 영역을 제안하는 FastSAM768 보조 모델은 유지한다. 기존 주 모델의 13클래스 번호를 새 모델에 재사용하지 않는다. 기존 사용자 이동/물체 이동 계산, 최신성, 유효 깊이 제한과 세션 처리를 보존한다.
- 실제 SMTP 공급자 자격정보는 저장소·문서·채팅에 기록하지 않는다. 기존 계정 암호화 키와 DB를 보존한다. 현재 지정 env0는 로컬 수집용으로 설정되어 있어 발신 서비스가 필요하다.

## 단계와 완료 확인

1. **분석·보존:** 모델 구조/레이블과 브랜치 기능 차이를 확인한다 → 변경 담당과 기존 작업 보존본, 통합 지도를 남긴다.
2. **주 모델 교체:** 768 TFLite로 변환하고 실제 텐서 형식에 맞는 전처리/출력 파서/NMS를 연결한다 → 클래스 순서·입출력 형식·모델 해시·설정이 일치하게 구성하고 빌드한다. 구 모델로 조용히 되돌아가지 않도록 한다.
3. **연관 기능 적응:** 21개 이름의 음성·장애물·점자블록 길안내·신고 분류, 성능점검 자료의 클래스 번호와 저장 프로필을 맞춘다 → 숫자 ID가 아닌 의미 매핑을 검토한다. `moving_e_scooter` 같은 분류명만으로 실제 접근 속도를 만들지 않는다.
4. **팀원 기능 통합:** 권한 재요청, 음성 후보 처리, 안내 문구, 기기점검 측정/오류 구분을 적용한다 → 현재 음성 세션·기능별 제한·지속 미달 판단과 충돌하는 부분은 현재 동작에 맞춰 수정한다. 추가 빌드 통제나 운영 절차를 기능 통합과 섞지 않는다.
5. **실제 이메일 구성:** 실제 SMTP 발신 계정과 TLS 설정을 기존 발송기로 연결한다 → 로컬 비밀 설정 절차를 제공하고 설정이 준비되면 운영 프로세스에 적용한다. 실제 수신 확인은 사용자 테스트로 남긴다.
6. **빌드·인계:** 원본 APK를 생성하고 변경 내용 및 사용자가 확인할 동작을 문서화한다 → 성공한 빌드와 수행하지 않은 동작 시험을 구분하고, 남은 공급자 설정이 있으면 명시한다.

## 분담

Root는 전체 통합, MainActivity 및 하위 의미 매핑, 브랜치 적용, Gradle/산출물과 기록을 맡는다. 모델 담당은 모델 변환·파서·설정·성능점검 자료 결속, 이메일 담당은 현재 발송 설정 확인과 최소 설정 도구/문서, 브랜치 분석 담당은 읽기 전용 통합 지도를 맡는다. 독립 검토는 최종 변경의 호환성과 미검증 범위를 확인한다. 같은 파일은 한 담당자만 수정한다.
