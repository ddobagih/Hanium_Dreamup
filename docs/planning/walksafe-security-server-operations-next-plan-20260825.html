Wave 4에는 실제 용량 측정기, 삭제 워커 운영 실행 단위, 관측성, 백업·복원 실행 단위가 포함된다. 순수 구현은 약 10–16 인시, 집중 시험·합류는 약 5–8 인시이며 한 사람이 순서대로 하면 3.5–5일 분량이다. * Wave 5 시간은 일정 약속이 아니다. cloud 계정·도메인·인증서·기기·참여자·독립검토자 확보 전에는 확정할 수 없고, 결함으로 후보가 바뀌면 영향 범위 시험을 다시 실행한다.

다음 한 가지 행동: 종료 정합화와 좁은 재시작 회귀를 서로 다른 작업조에서 동시에 시작한다.

회귀 작업조는 읽기·실행만 하고 결함을 재현한다. 통제 작업조는 현재 진행 중인 작업의 종료와 다음 수정 범위를 정합화한다. 다음 범위의 수정 권한이 확인되면 실제 용량 측정기와 삭제 one-shot 운영화를 즉시 병렬 착수한다.

1. 진행 순서

  1. 두 트랙 동시 시작현재 작업 종료 정합화와 읽기 전용 재시작 회귀를 분리한다.
  2. 저장소 후보 완성좁은 회귀 뒤 실제 용량 측정기, 삭제 one-shot, 관측성·백업 실행 단위를 만든다.
  3. 사전운영·정식 검증실제 환경과 단일 후보를 준비하고 정식 279건·gate 판정·출시 심사를 수행한다.
  4. 승인된 운영 전환GO일 때만 staging→production canary→scheduler·on-call→인계 순서로 연다.
통제 실패를 기능 구현 시간으로 숨기지 않는다.

첫 30분에 단순 snapshot 차이인지 확인하고, 아니면 별도의 통제 정합화 작업 흐름으로 분리한다. 현재 checkpoint는 작업 진행 중이며 HTML 계획서가 다음 제품 수정 권한이나 출시 승인을 대신할 수 없다. 다음 수정 권한이 확인되지 않은 동안 다른 작업조는 읽기 전용 재현·시험 준비까지만 한다.

Wave 4 · 배포 가능한 저장소 후보 만들기

3. 설정 파일만 만드는 것이 아니라 남은 서버 기능을 운영형으로 전환한다

A. 실제 용량 측정기

합성 주입을 현재 서버의 실제 저장공간 측정으로 연결한다

  • 현재 배치 계약의 UPLOAD_DIR filesystem 사용률을 읽는 Backend 측정기 추가
  • 측정 주기와 TTL은 환경값으로 명시하고, 값이 없으면 자동 실행하지 않음
  • 재시작 뒤에도 뒤로 가지 않는 version을 전용 private state에 원자적으로 보존
  • 측정 실패 시 마지막 성공 상태를 기존 TTL까지만 유지하고 이후 503
  • 실제 percent·GiB·경로는 내부 API와 로그에 노출하지 않음

이 측정기는 현재 단일 host·local filesystem 후보용이다. 실제 object storage primary/backup capacity gate를 닫지 않는다.

B. 삭제 워커 운영 실행 단위

로컬 전용 도구를 안전한 수동 one-shot 후보로 만든다

  • staging/production에서 무조건 종료하는 현재 조건을 보안 사전검사와 명시적 실행 모드로 교체
  • 워커 전용 env 예제와 hardened one-shot service 추가
  • 전용 DB 로그인·최소 역할, 0600 env, 0700 journal/quarantine 계약 고정
  • 단일 host·같은 filesystem·maintenance lock 전제를 시작 시 검증
  • batch 상한, timeout, crash reconciliation, 동일 요청 멱등성을 service 명령과 동일하게 시험

자동 timer와 distributed lease는 만들지 않는다. one-shot 후보 검증 뒤 timer는 별도 승인으로 추가하며 실제 자격증명·삭제 실행도 하지 않는다.

C. readiness·health·안전한 관측성

살아 있음, 받을 준비, 실패 추적을 서로 구분한다

  • privacy rate-limit CHECK가 존재·validated 상태이고 정확한 group 집합인지 readiness에 추가
  • 외부 Nginx에는 열지 않는 Gateway 내부 health endpoint 추가
  • 모든 허용 route의 request ID 응답 전파와 완료 이벤트 추가
  • route template·status·latency·5xx·capacity level만 bounded-cardinality로 기록
  • query, 좌표, 본문, token, 계정·삭제 ID는 기록하지 않음

기존 Backend health와 Gateway telemetry.ts를 확장한다. 새 모니터링 framework는 도입하지 않는다.

D. 백업·복원 실행 단위

기존 도구를 재작성하지 않고 반복 실행 가능한 단위로 묶는다

  • 기존 암호화 backup/restore 스크립트의 env, one-shot service, 기본 비활성 timer 초안 추가
  • manifest·서명·무결성·backup age 실패 시 문제를 숨기지 않고 안전하게 중단
  • 격리 PostgreSQL·새 임시 upload dir에서 backup → restore를 실제 1회 실행
  • count·hash·참조·권한만 담은 민감정보 없는 local 실행 기록 생성
  • not-ready·지속 5xx·capacity stale·backup age의 signal→대응 연결표 작성

실제 offsite 저장소·운영 암호키·dashboard 제품·on-call 연결은 대상 환경이 정해진 뒤 한다.

4. 모든 검증이 성공하고 승인된 경우에만 실제 서비스를 연다

Wave 5가 끝났다는 말과 실운영 전환 완료는 같은 뜻이 아니다.

검증 결과가 NO-GO이면 배포하지 않는다. 조건부 승인이라면 승인된 조건 범위만 수행한다. 같은 후보가 사람의 승인을 받고 production 배포·DB 변경·기본 동작·소규모 공개·복귀·경보·삭제 scheduler·인계까지 실제로 통과한 경우에만 실운영 전환 완료로 기록한다.

Wave 5 진입 전에 먼저 고정할 것

운영 대상과 책임
  • cloud 계정·리전·도메인·예산·운영 범위와 공개 대상을 확정
  • 서비스 책임자, 운영 담당자, QA, 보안·개인정보 검토자, 비상 대응자와 대체 연락처 지정
  • 현재 미지정인 독립 검토자를 임의 이름으로 채우지 않음
  • Wave 4와 현재 작업의 종료·변경 권한이 정합한지 확인
저장소 구조 결정
  • Wave 4의 단일 host local 저장소를 운영 승인할지, 실제 object storage로 바꿀지 결정
  • object storage를 선택하면 primary·backup 측정기와 삭제 범위를 별도 구현·시험
  • 결정 전에는 local 측정 결과로 server-capacity gate를 닫지 않음

object storage 전환을 택하면 추가 개발 3–10영업일 이상이 생길 수 있으며 Wave 5 일정에 별도로 반영한다.

5E
출시 판단		 권한 있는 사람이 공개해도 되는지 결정한다. 279건에 포함된 5개 gate 시험과 gate별 독립 판정을 확인한다. 시험 결과보고, 미해결 결함·잔여위험, 정적·의존성·비밀 검사와 승인된 환경의 동적·침투시험, 취약점 신고 채널, 실제 휴대전화 E2E, 이전 버전 복귀, 현장 안전계획을 함께 검토해 GO·조건부 GO·NO-GO 중 하나를 승인한다. 같은 후보에 결속된 출시 준비도 판단과 승인 체크리스트의 실제 서명·시각·증거 참조. gate는 모두 종결되고 waived=false
5F
staging 승격		 GO를 받은 후보를 정식 사전운영 환경에 올린다. 새 backup을 확인하고 migration, issuer 결속, Backend, Gateway, Nginx/TLS 순서로 올린다. 모든 active 관리자 앱의 호환 version을 먼저 확인하고 미갱신 session·device key를 폐기한다. 그 뒤 health·로그인·권한·길안내·신고·삭제의 짧은 smoke와 제한 canary, rollback을 실행한다. 배포 대상·명령·시간·hash, migration 결과, smoke·canary 지표, rollback 결과를 담은 추가 전용 실행 기록
5G
production 전환		 작게 열고 관찰한 뒤 안정적일 때만 확대한다. 승인된 배포 시간대에 fresh backup, 쓰기 중단, migration, service/TLS 검증 후 제한 사용자 canary를 연다. 오류·지연·용량·backup·보안·삭제 지표를 확인한 뒤 계정 삭제 전용 timer를 낮은 batch로 마지막에 활성화한다. 주담당·대체당직 호출과 지원·장애·복구 인계를 끝낸다. production smoke·canary·경보 전달·scheduler 승인/활성화·운영 인계 기록과 3–7일 안정화 관찰. 모두 성공해야 실운영으로 표시

279건 안에 포함된 5개 출시 gate

아래 검증 case 5건은 279건에 포함돼 있으므로 284건으로 더하지 않는다. 다만 case PASS만으로 gate가 자동 종결되지는 않으며, 실제 원자료·전문 검토·제품책임자의 별도 판정이 필요하다.

즉시 중단
  • 후보 hash·환경·설정이 승인본과 다름
  • 정식 시험·gate 미실행/실패, P0/P1 또는 미수용 안전·보안·개인정보 위험
  • backup·격리 restore·migration·smoke·canary·경보 전달 중 하나라도 실패
  • 비밀값·개인정보 로그 노출, 삭제 중복·오삭제·복구 불명확
  • 주담당·대체당직·지원 채널이 실제 호출되지 않음
안전한 복귀
  • 신규 public traffic과 삭제 timer를 먼저 중단하고 journal·quarantine을 보존
  • DB와 호환성이 입증된 구성요소만 이전 승인판으로 되돌림
  • DB 변경이 비가역이거나 미검증이면 구 앱만 억지로 올리지 않고 ingress를 닫아 안전정지 후 restore 또는 수정판 적용
  • 복원 전 삭제 tombstone·영수증을 먼저 재적용하고 이미 유효하게 삭제한 개인정보가 되살아나지 않았는지 확인

5. 팀을 이렇게 병렬로 운용한다

현재 작업 정리 담당 — 제품 파일을 수정하지 않는 독립 작업 흐름

현재 기능 후보의 종료 기록, 변경 snapshot, 다음 수정 범위와 권한을 정합화한다. 예상 2–4시간이며 제품 구현 작업조의 인시와 섞어 보고하지 않는다.

Wave 3·4 기능 구현팀

작업조 A

local 용량 상태

Wave 3의 용량 cache 회전 회귀 뒤 filesystem 측정기, 재시작해도 증가하는 version, TTL·실패·복구 E2E를 구현한다.

인계물: 측정기, 명시적 설정, restart/expiry/down/recovery 시험

작업조 B

삭제 one-shot

현재 로컬 전용 중단 조건을 보안 사전검사 기반 수동 실행 모드로 전환하고 hardened unit/env를 만든다.

인계물: 운영 실행 단위, unit/env, single-host·role·ACL·crash 회귀

작업조 C

상태·관측성·복원

Gateway health와 안전한 request telemetry를 구현하고, 기존 backup/restore를 실행 단위와 대응표로 묶는다.

인계물: health/telemetry, backup unit/timer, 격리 restore 실행 기록

합류 검토자

세 작업조 파일이 합쳐진 뒤 capacity 단계의 실제 집행 범위, Nginx 비노출, systemd 권한, 로그 민감정보, 삭제 멱등성, 문서 상태 표현을 독립 검토한다. 작업조와 같은 영역을 동시에 수정하지 않는다.

Wave 5 실운영 전환팀

릴리스·통제

후보와 승인

릴리스책임자와 제품책임자가 후보 manifest·hash·SBOM, 변경 동결, 출시 판단, 배포 실행 기록을 관리한다.

플랫폼·보안

운영 집과 열쇠

기술책임자와 보안·개인정보책임자가 cloud·DB·storage·TLS·DNS·KMS·secret·최소권한과 key rotation을 맡는다.

배포·데이터

DB 변경과 복귀

릴리스·운영책임자가 설치, migration, backup·격리 restore·rollback, 삭제 timer의 staging 시험과 승인 활성화를 맡는다.

관측·당직

문제 발견과 연락

운영·지원책임자가 live dashboard, 실제 경보 전달, SLI/SLO·error budget, 주담당·대체 연락과 runbook을 맡는다.

정식 QA·안전

279건과 독립검토

QA·기기 QA·접근성·안전 담당과 독립 보안·개인정보 검토자가 정식시험, 현장 안전, 5개 gate와 잔여위험을 판정한다.

현재: 독립 검토자 미지정 — 지정 전에는 출시 차단

제품책임자가 최종 합류 판정을 한다. GO 전에는 production 쓰기, public traffic, production 삭제 scheduler를 켜지 않는다.

7. 오래 끌지 않으면서 증거를 잃지 않는 실행 규칙

계속 진행

  • 기존 코드·스크립트·시험을 우선 재사용
  • 현재 종료 정합화와 다음 기능 개발은 담당·시간을 분리해 기록
  • 작업조별 집중 시험만 개발 중 실행
  • 결함은 재현 → 최소 수정 → 같은 시험 통과 순서
  • 문서·카탈로그·전체 묶음은 코드가 안정된 뒤 한 번 갱신
  • 후보가 바뀌면 새 후보 세대로 다시 고정하고 승인된 영향 시험과 필수 회귀를 재실행하며, 여러 후보의 부분 성공을 합쳐 GO로 만들지 않음
  • N/A는 승인된 적용성 근거와 서명이 있을 때만 허용
  • 실제 실행 결과는 기존 template을 덮어쓰지 않고 후보·환경·수행자·시각과 함께 추가 기록

Wave 4에서는 하지 않고 Wave 5 승인 뒤 수행

  • cloud 자원·실제 storage·DNS·TLS·Secret Manager/KMS 구성
  • 중앙 dashboard, 실제 경보 전달, on-call·대체 연락망 활성화
  • 계정 삭제 전용 scheduler 작성·검토·합성계정 시험·production 제한 활성화
  • 실제 backup을 운영 DB와 분리된 새 환경에 복원하고 재해복구 실측
  • 정식 279건과 gate별 판정, 출시 심사, staging·production 배포
즉시 멈추고 별도로 판단할 조건

비밀값 또는 개인정보가 로그에 나타남, 삭제 작업이 멱등하지 않음, 복원할 수 없는 변경, Gateway health가 외부 ingress에 노출됨, 일반 Backend 역할이 삭제 권한을 얻음, 기존 기능에 P0/P1 회귀가 생긴 경우에는 다음 단계로 넘어가지 않는다.

8. 완료 기준

Wave 3 완료

  • 실제 Gateway stop/start 뒤 refresh 회전·이전 refresh 재사용 탐지·다른 기기 생존 시험이 통과한다.
  • server-capacity를 포함한 7종 암호화 state가 key 회전·재시작 뒤 복호화되고 unknown/compromised key는 거부된다.
  • 컨테이너 nginx -t와 local upstream smoke에서 계정 삭제 세 경로만 도달하고 유사 경로는 차단된다.
  • 현재 작업 종료와 다음 수정 범위가 정합화되기 전에는 Wave 4 제품 파일을 수정하지 않는다.

Wave 4 저장소 완료

  • 명시적으로 설정한 local filesystem 측정기가 실제 상태를 만들고 version은 재시작 뒤 증가하며 failure·expiry 시 문제를 숨기지 않고 안전하게 중단한다.
  • 70·85·95·100 단계에서 signal-only와 실제 집행 범위가 표와 동일하고, 없는 참가자·학습 pipeline 완료를 주장하지 않는다.
  • privacy rate-limit CHECK의 부재·구형 정의·unvalidated 상태가 readiness 503을 만든다.
  • Gateway 내부 health는 loopback에서만 성공하고 외부 Nginx 경로는 계속 차단된다.
  • request ID·route template·status·latency·5xx 이벤트가 나오며 query·본문·token·식별자는 나오지 않는다.
  • 삭제 워커의 운영 후보 수동 one-shot과 전용 env/service가 single-host·최소권한 사전검사, crash recovery, 멱등 시험을 통과한다.
  • 삭제 timer는 없거나 비활성 초안이며 실제 자격증명·삭제 실행 없이 멈춘다.
  • backup env/service/timer가 정적 검사를 통과하고 격리 backup→restore 실행 기록은 로컬 범위로 표시된다.
  • 관련 Backend·Gateway·PostgreSQL 시험, 설정 검사, 링크 검사, git diff --check가 통과한다.

이 완료는 “배포 가능한 저장소 후보지만 아직 적용하지 않음”이라는 뜻이다. 실제 host 적용, 운영 복원 성공, 정식 검증 완료, 출시 가능을 뜻하지 않는다.

Wave 5 사전운영·검증 절차 종료

  • 실제 대상·권한·담당자가 지정되고 하나의 release candidate와 전체 hash가 고정된다.
  • 비공개 정식 시험환경에서 실제 backup의 격리 restore, DB 변경·복귀, 중앙 경보 전달, 합성계정 삭제 scheduler 시험이 통과한다.
  • 정식 279건의 적용 대상에 설명 없는 NOT_RUN이 없고, 실패·N/A·재시험·잔여위험이 모두 승인 근거에 연결된다.
  • 279건에 포함된 5개 gate 시험과 별도 gate 판정이 모두 종결되고 waived=false다.
  • 시험 결과보고, 결함·잔여위험, 적용 보안시험, 실제 휴대전화 E2E, 이전 버전 복귀, 현장 안전 선행조건이 같은 후보에 결속된다.
  • 권한 있는 사람이 GO·조건부 GO·NO-GO 중 하나를 실제로 승인한다.

NO-GO도 정상적인 검증 결과다. 이 경우 Wave 5 검증 절차는 끝날 수 있지만 실운영으로 전환하지 않는다.

실운영 전환 완료

  • GO 또는 허용 범위가 분명한 조건부 GO를 받은 동일 후보만 staging과 production에 배포한다.
  • 모든 active 관리자 앱의 호환 version을 먼저 확인하고, 미갱신 session·device key를 폐기한 뒤 ingress drain → Backend 정지 → migration → issuer 결속 → Backend/Gateway → readiness → ingress 순서를 통과한다.
  • production backup·migration·smoke·제한 canary·rollback 판정이 실제 대상과 시간에 결속된 실행 기록으로 남는다.
  • dashboard 접근권한·데이터 최신성·SLI/SLO·error budget과 주담당·대체채널의 실제 alert fire→delivery→clear가 확인된다.
  • 계정 삭제 전용 timer가 one-shot·합성계정 시험과 별도 승인을 거쳐 낮은 batch로 활성화되고 중복·오삭제·실패 경보가 없다.
  • 3–7일 안정화 관찰과 운영·지원·장애·복구 인계를 승인하고, 실제 상태 원장에 append-only 실행 기록을 연결한다.
위 조건이 전부 실제 증거로 충족되면 그때 외부 사용자 대상 실운영 전환이다.

사전운영 환경만 준비됐거나 정식시험·승인·production canary·당직·scheduler·인계 중 하나라도 남으면 아직 실운영 완료가 아니다.
