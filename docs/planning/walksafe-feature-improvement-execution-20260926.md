이 문서는 현행 작업 순서와 완료 기준이다. 과거 승인 정책·원문·실패 기록을 대체하지 않으며 새로운 통제 시스템을 만들지 않는다. 제품 범위는 Android 사용자 앱, 관리자 앱, Gateway, Backend와 이를 검증하는 도구다.

## 1. 목표와 완료의 의미

**21개 분야 원문 872개와 정지·이동 추가 요구 70개를 현행 코드에 대조하여, 적용되는 실제 기능 결함을 수정하고 직접 시험·필요한 독립 검토·통합까지 끝낸다.**

- 942개를 확정 버그 수로 취급하지 않는다. 중복 요구, 이미 해결된 문제, 조건부 위험, 검증·설계 요구를 구별한다.
- 완료 숫자만 늘리는 정리보다 사용자가 겪는 잘못된 동작의 제거를 우선한다.
- 과거 DONE은 근거와 관련 코드가 유지되는지 필요한 범위에서 확인해 재사용한다. 전 항목을 처음부터 재구현하거나 같은 시험을 무조건 반복하지 않는다.
- 실제 결함은 수정 전 반례와 수정 후 같은 조건의 직접 결과로 닫는다. 구현상 위험이 없는 조건부 항목은 적용 여부와 근거를 명시한다.
- 원문이 요구하는 물리 기기·외부 서비스 검증이 남으면 전체 완료로 표시하지 않는다. 그 항목을 분리하고 가능한 다른 로컬 작업을 계속한다.
- 기능 개선 완료, 전체 제품 검증 완료, 출시 가능은 별개다. 기존 정식 시험·출시 상태를 임의로 바꾸지 않는다.

### 실행 Goal

> 이 계획과 942행 원문 목록을 기준으로 WalkSafe의 실제 기능 결함을 병렬 개선한다. 원문 요구 → 현행 반례 → 최소 수정 → 직접 시험 → 필요한 독립 검토 → 통합 순서로 처리한다. 기존 WIP와 안전·동의·암호화 경계를 보존한다. 원문 밖 요구를 새 완료 조건으로 붙이지 않는다. 소수의 독립 작업을 완료까지 닫고 다음 작업을 채운다. 환경·컴파일·fixture·작성자 오류는 승인 범위 안에서 자율 복구한다. 필수 검증이 남은 항목은 완료로 올리지 않으며, 전체 적용 범위의 구현·검증·통합이 끝날 때만 Goal을 완료한다.

## 4. 병렬 팀과 파일 소유권

- Root 1명: 우선순위, 작업 계약, 파일 소유권, 통합·항목 판정과 사용자 보고. 제품 수정 대기 시간을 문서 작업으로 채우지 않는다.
- 기본 구현 동시 작업은 **4개**. 처음에는 독립 Android 두 영역, Gateway 한 영역, Backend 한 영역으로 구성한다. 이번 로컬 수정 묶음의 검증·리뷰·통합을 끝내면 슬롯을 반환한다. 원문 전체에 외부 검증이 남으면 ID는 PARTIAL로 유지한 채 다음 독립 묶음을 배정한다.
- 독립 검토자는 필요에 따라 1~2명. 안전·위치 안내·인증·동의·개인정보·동시성 변경은 다른 인스턴스가 반례와 수정 범위를 검토한다. 사소한 문구/가역 수정에 고정 팀을 붙이지 않는다.
- 테스트 통합 담당은 한 명이 자원이 큰 실행을 조율한다. 작성자는 자기 코드 재독·집중 시험·실패 복구를 직접 할 수 있다.
- 같은 파일은 한 시점에 한 writer만 가진다. `MainActivity.kt`, `routes.ts`, `accounts.py`, `inference_process.py`, 공용 설정·build 파일은 특히 공유 소유를 금지한다.
- `MainActivity.kt` 변경은 별도 통합 담당 한 명에게 모은다. 다른 Android 담당은 정책/클래스/시험을 독립 수정하고 연결부 변경 요청을 전달한다.
- 여러 Android 빌드·시험은 한 작업트리에서 동시에 실행하지 않는다. Gateway도 `dist`를 쓰는 빌드는 한 명만 실행하며 시험 중 재빌드하지 않는다. Backend 임시 DB/저장 경로는 실행별로 분리한다.
- 구현 슬롯을 늘리기 전에 리뷰 적체·빌드 대기·파일 충돌이 없는지 확인한다. 가능할 때만 최대 6개까지 확대한다. 역할 수와 실행 슬롯을 채우는 것이 목표는 아니다.
- 기존 다른 작업이 재개되면 겹치는 파일 담당을 확인해 충돌을 조정한다. 다른 사용자 작업을 임의로 중단하지 않는다.

단계 4의 원문 확인은 단계 1부터 각 담당이 자기 묶음에서 함께 진행한다. 완성 직전에 847행을 한꺼번에 재조사하는 병목을 만들지 않는다.

## 7. 항목 하나의 짧은 실행 계약

배정 메시지 또는 작업 목록에 다음 여섯 가지면 충분하다. 별도 receipt/builder/hash gate를 만들지 않는다.

1. **원문·사용자 결과:** ID, 원문 위치, 무엇이 잘못되는지.
2. **현재 반례:** 입력/상태/순서, 기대 결과, 실제 실패 또는 재현 계획.
3. **수정 경계:** 단일 writer의 파일 목록과 공유 호출부 담당.
4. **완료 기준:** 원문에서 요구한 정상·실패·취소/경계 사례. 조건을 임의로 확장하지 않음.
5. **직접 검증:** 실행 명령, 환경, 긍정/부정 oracle, 영향받는 인접 시험.
6. **통합 결과:** 동작 변경, 직접 결과, 독립 검토, 남은 필수 범위와 다음 한 작업.

## 8. 검증 운영과 속도 개선

- 시험 환경은 첫 실행 때 한 번 확인해 명령에 명시한다. 현재 기본 작업 경로가 없는 문제를 피하려고 모든 실행에 실제 저장소 경로를 지정한다.
- 실패는 환경/수집/컴파일/fixture/제품/시간초과/외부 증거 부재로 구분한다. 수집·컴파일 실패를 제품 시험 실패나 통과로 세지 않는다.
- 작은 변경마다 수천 개 전체시험을 반복하지 않는다. **새 반례 → 해당 클래스/파일 → 관련 모듈 → 안정된 묶음의 전체시험** 순서다.
- 공유 변경 후에는 영향을 받는 검증을 다시 실행한다. 기존 코호트의 통과 숫자를 새 코드의 통과로 승계하지 않는다.
- 외부 API/플랫폼의 구체 동작이 판단을 바꾸면 현재 공식 문서를 확인한다. 코드에 이미 고정된 프로젝트 계약은 먼저 로컬 소스로 확인한다.
- 독립 검토는 수정 diff, 원문 조건, 직접 결과를 대상으로 한정한다. 검토자가 전체 저장소를 다시 탐색하는 일을 반복하지 않는다. 새 반례는 작성자가 고치고 영향 범위만 재검토한다.
- 실패한 시험의 기대값을 제품 결과에 맞춰 낮추지 않는다. fixture가 낡았다는 근거가 있을 때만 데이터/설정을 보정하며 원래 불변조건은 유지한다.
- 검토 대기 2개 이상이면 새 구현 착수를 줄여 통합을 먼저 끝낸다. 오래된 미완료 항목을 계속 늘리지 않는다.
- 자원 충돌과 리뷰 적체가 없을 때에만 병렬 수를 늘린다. 첫 두 묶음의 실제 시간으로 조정하며 전체 완료 날짜를 추측하지 않는다.
