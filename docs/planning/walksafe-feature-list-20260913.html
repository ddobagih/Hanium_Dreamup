이렇게 나눈 기준

한 화면에서 사용자가 한 번에 끝내는 일을 하나로 묶었습니다. 기기 점검은 내부적으로 카메라·위치·음성·호출어·ARCore 다섯 가지를 재지만, 사용자에게는 "점검을 누르고 기다리는 일" 하나입니다. 반대로 보행은 시작·일시정지·종료·안전중지의 선행조건과 사후조건이 모두 달라 넷으로 나눴습니다. 하나로 묶으면 명세 표의 선행·사후 칸에 여러 상황을 욱여넣게 되어 명세서로서 쓸모가 떨어집니다.

액터가 시스템인 유스케이스가 다섯 개입니다. 위험 탐지와 안전 중지는 사용자가 부르지 않아도 일어납니다. 사용자 액터로 적으면 사실과 다르고, 빼면 제품의 핵심이 명세서에서 사라집니다.

점자블록 경로 보조는 유스케이스에서 뺐습니다. FP-024는 요구 정본에 그대로 남아 있고 1.1 개요에도 설명이 있지만, 사용자가 부르는 조작이 아니라 길안내 안에서 동작하는 보조 신호이므로 2장에서는 다루지 않고 3장 비기능 요구사항에서 설명합니다.

스물한 개 기능은 여기 없습니다. FP-034~054(자료 수집·모델 학습·서버 구조·보안·배포·운영)는 사용자가 조작하지 않으므로 유스케이스가 아니라 3장 비기능적 요구사항으로 보냈습니다.

UC-30은 후속 과제입니다. SW 개발 설계서의 R-09가 API와 화면 제어까지를 범위로 두고 일반 메뉴 연결은 후속 과제로 명시했습니다. 명세서에는 넣되 이번 범위가 아님을 표시했습니다.

설계서의 R 번호와의 대응

총괄이 배포한 SW 개발 설계서(2026-09-07)는 요구를 R-01~R-12로 부릅니다. 학교 양식이 유스케이스 번호를 요구하므로 두 체계를 모두 두고 여기서 잇습니다. 같은 것을 두 번 부르는 것이지 서로 다른 요구가 아닙니다.

2.2 다이어그램을 그릴 때

UCD 열 장을 그리게 됩니다. 각 장에 무엇이 들어가야 하는지만 적어 둡니다.

액터는 셋입니다. 시각장애인 사용자, 지정 관리자, 그리고 시스템. 외부 시스템으로 TMAP과 SMTP 메일이 붙습니다(UCD-07·UCD-01).

포함 관계를 그릴 곳. UC-16 보행 시작은 UC-11 기기 점검 실행과 UC-15 장착 확인을 포함합니다. UC-14 사전 연습 청취는 UC-13 안전 제한 안내 청취를 포함합니다. UC-23 목적지 선택·경로 시작은 UC-22 목적지 검색을 포함합니다. UC-29 손상 점자블록 신고는 UC-20 물체 탐지를 포함합니다. UC-28 음성 명령 실행은 UC-27 호출어 사용을 포함합니다. UCD-10의 UC-32~35는 모두 UC-31 관리자 인증을 포함합니다. UC-10 자동신고 설정 변경은 UCD-09 신고가 아니라 UCD-02 동의·권한·권리에 둡니다 — 신고를 하는 일이 아니라 이미 준 동의를 조정하는 일이기 때문입니다.

확장 관계를 그릴 곳. UC-19 안전 중지는 UCD-05·UCD-06의 어느 유스케이스에서든 확장될 수 있습니다. UC-12 기기 점검 재측정은 UC-11 기기 점검 실행의 확장입니다. UC-25 경로 이탈 대응은 UC-24 경로 진행 안내의 확장입니다. UC-04 다기기 보행 전환은 UC-16 보행 시작의 확장입니다.

첫 실행 순서. UCD-01 → UCD-02 → UCD-03 → UCD-04 → UCD-05 순으로 지나갑니다. 요구 정본 FP-010이 정한 순서이고 실기기 동작과도 같습니다 — 기기 점검이 안전 교육보다 먼저입니다.

근거: docs/deliverables/03-requirements의 요구 68종과 SW 개발 설계서(2026-09-07)의 R-01~R-12. 각 UC의 선행조건·시나리오·예외사항은 2.3 유스케이스 명세에 있습니다. 요구 문서는 DRAFT / NOT_APPROVED이고 인수조건 279건이 모두 NOT_RUN입니다.
