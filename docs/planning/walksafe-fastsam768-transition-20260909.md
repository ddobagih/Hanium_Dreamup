# FastSAM 768 전환 및 이름 없는 객체 접근 안내 통합 계획

2026-09-09. 실행 상태: **0~2단계 별도 APK 전환·CPU/GPU 분업 비교·실기기 회귀 완료 / 조합 자동 선택·추적·원본 앱 통합은 후속**.

아래 기존 현황은 계획 수립 시점의 기준이다. 이후 실행 결과는 [768 전환 보고서](/home/ddobagi/Hanium_Dreamup/docs/reports/walksafe-fastsam768-transition-20260909.md)에 기록한다. 원본 앱의 새 기능 탑재·실물 깊이·접근 안내 완료를 뜻하지 않는다.

## 1. 확정한 선택과 전체 목표

사용자 결정에 따라 추가 영역 검출 모델은 **FastSAM-S 768**로 한다. 기존 사용자 앱의 YOLO26n 768은 유지한다. 보류한 WalkMate 21클래스 모델 교체는 이번 전환과 별개다. 640은 과거 비교 자료로 보존하며, 성능 부족을 이유로 몰래 640으로 내리는 자동 전환을 넣지 않는다.

최종 구성은 다음과 같다.

```text
동일 시각의 카메라 영상·깊이·신뢰도·좌표 정보 확보
  ├─ 현행 YOLO26n 768 → 기존 클래스의 객체 검출
  └─ FastSAM-S 768 → 이름 없는 물체 후보 영역
           ↓
원본 영상 좌표 복원 → 같은 관측의 깊이 연결
           ↓
시간에 따른 동일 객체 추적·기존 검출과 중복 정리
           ↓
카메라 자세·물체 위치 변화로 상대 접근과 객체 자체 이동 구분
           ↓
유효 거리·방향·접근 근거·결과 나이에 따른 기존 안내 체계 연결
```

입력 해상도가 같아도 두 모델의 연산·출력 구조·전처리는 별개다. 첫 전환에서는 각 전처리를 정확히 유지한다. 전처리 공유는 그 뒤의 선택적 최적화이며, 이미지 크기만 같다는 이유로 입력 tensor를 공유하지 않는다.

범위는 현행 13개 출력 클래스에 한정되지 않는 **영역 후보와 접근 판정**이다. 모든 학습에서 보지 못한 물체를 반드시 검출한다는 목표로 바꾸지 않는다. RGB 화면 흔들림 보정/EIS는 별도 과제로 두되, 객체 운동의 원인을 구분하는 데 필요한 카메라 pose 보정은 운동 판정 단계에 포함한다.

### 이번 조사에서 확인한 입력 혼입 위험

`ReplayFrameSource.prepared(id, size)`는 현재 640만Fast 입력으로 보고768은primary 입력으로 반환한다. FastSAM 크기만768로 바꾸면 primary의 nearest 전처리 입력을 FastSAM의 bilinear 입력 대신 받는다. 둘 다7,077,888bytes라 길이 검사만으로 찾을 수 없다. 따라서 **모델 역할 분리와 전처리의 의미 일치 검사가 모델 파일 교체보다 먼저**다.

## 4. 그대로 이어갈 구현과 제한

- v8의 GPU 소유 스레드 원칙, float buffer 일괄 복사, 전체 유한값 검사, 재사용 배열과 resize 축 계산, 깊이 geometry-only 캐시, YUV plane bulk copy를 이어간다.
- latest pending1/inflight1, 같은 snapshot의 결과 결합, 실제 채택 시각 age 검사, foreground 선행, 장면 유지 재생을 보존한다. 서로 다른 시각의 mask와 최신depth를 섞지 않는다.
- 깊이 정책 `KNOWN/PARTIAL/UNKNOWN`과 모든 연결 성분 보존을 유지한다. PARTIAL의 전체 거리 필드는null이다. 작은 가까운 성분을 버려 성능이나 성공률을 높이지 않는다.
- 입력 해상도 증가로 ARCore 자체의 해상도·정확도가 증가했다고 해석하지 않는다. 768 mask의 어느 깊이 픽셀을 선택하는지를 다시 확인한다.
- 신경망 두 개의 특징 연산을 공유하는 구조 변경, 재학습, NPU 런타임 전환, 양자화는 첫768 전환에 섞지 않는다. 이번 최적화는 먼저 기존 FP32 결과를 보존한다.
- 원본 앱의 기존 모델·로그인·경로 안내 등은 전환 초기에 유지한다. 별도 시험 경로가 확인된 뒤 단계적으로 연결한다.

## 6. CPU·GPU 배분과 재평가 계획

### 역할과 후보

CPU는 카메라 입력 준비·마스크 복원·깊이 계산·추적·스케줄링을 맡고 GPU는 지원되는 모델 연산을 맡는다. 실제 잔여 CPU 연산도 계측한다. CPU/GPU 사용률을 임의의 고정 퍼센트로 나누거나 CPU4가 모든 기기에 맞다고 가정하지 않는다.

1. 기존768과FastSAM768을 **한 GPU 소유 스레드에서 순차 실행**하는 기준을 만든다.
2. **각 모델을 별도 GPU 소유 스레드에서 실행**해 CPU 후처리와 겹칠 수 있는지 비교한다. 같은 GPU의 경쟁·메모리 증가·다른 시각 결과의 단독 완료까지 측정한다.
3. GPU 우선으로 비교하되 미지원·결과불일치·실측 이점 부족이면768의CPU 실행 후보를 확인한다. 필요할 때만 혼합backend 후보를 추가하고 후보 조합을 무제한 확장하지 않는다.
4. CPU 스레드는 이용 가능한 프로세서 힌트 범위의 **모든 정수값을 후보로 허용**한다. 1/2/4/8로만 제한하지 않는다. 모든 값을 반드시 시험한다는 뜻은 아니며 측정 예산 안에서 유망한 후보와 인접 정수를 탐색한다.

결정 기준은 모델 호출FPS 하나가 아니라 **기존 모델 결과 간격, FastSAM 결과 나이, 독립 깊이 관측 간격, 추적·음성·UI 영향, 메모리·열 상태**다. 이번 해상도768 선택은 유지하며, 그 안에서 실행 방식을 조절한다.

### 최대5분과 재평가 시점

- 앱의 **기기 성능 점검 한 번 전체가 최대 300초**다. 모델 준비·워밍업·유효 표본·교체·정리 시간을 예산에 포함한다. 모든 후보를 순서대로300초씩 실행하는 점검을 만들지 않는다.
- 기존768 cold 준비가 약76초였으므로 고정15초 준비 시간 등을 가정하지 않는다. 남은 시간과 실제 모델 초기화 시간을 보고 후보 수를 줄인다. 예산 안에 확인한 최선과 미시험 후보를 구분한다.
- 개발용 A/B 실험도 회차별300초 이내로 계획한다. 앱의 최초 점검과 별도 개발 반복 실험을 구분하고, 순서 반전·비슷한 시작 열 상태·동일한 장면 비중으로 원인을 확인한다.
- **최초 사용, 모델/전처리/decoder/런타임·기기 환경 변경, 수동 재점검** 때 기존 profile 결속을 검증해 재평가한다. profile은 두 모델의 조합과 실행 방식에 결속한다.
- 사용 중에는 매 프레임 interpreter를 새로 만드는 대신 결과 지연·대기·추적 품질에 따라 작업 접수 빈도를 빠르게 조절한다. 열뿐 아니라 다른 작업의 경쟁·절전·메모리·카메라/깊이 상태도 본다.
- 재벤치마크는 기존 `RuntimeLoadMonitor`의 **20초 창3개 연속 악화** 감지 방식을 출발점으로 삼아 두 모델별 지표에 맞춰 검증한다. 각 창의 최소 유효 표본 조건을 지키고, 입력만 있고 완료가 끊기는 경우는 별도 즉시 진단한다.
- 지속 악화는 재평가 예약 근거이고 즉시 무거운 벤치마크 실행 명령은 아니다. 열/절전 상태가 안정되고 앱이 전경이며 안내·카메라 자원 전환이 가능한 시점에 수행한다. 기존 재시도 제한·세대/소유권 검사를 재사용한다.
- transient 부하로영구 설정을 덮어쓰지 않는다. 조절로도 유효 정보를 만들 수 없으면 해당 기능의 신뢰 상태를 낮추고 기존 검증된 안내 정책에 연결한다. 640 자동강등이나 근거 없는 전체 앱 중지로 처리하지 않는다.

## 7. 깊이·영상·접근 검증 방법

### 서로 대체할 수 없는 네 종류의 근거

| 자료 | 검증할 것 | 그 자료만으로 주장하지 않을 것 |
|---|---|---|
| 합성 mask/depth/pose·시간 시퀀스 | 경계 조건, 좌표 변환, 시각·ID·상태 전이 | 실제 인식률·거리 정확도 |
| 기존 공개 정적 RGB-D 4장 | 768 마스크 → 같은 센서 Z 연결과 회귀 | 동영상 연속 추적·ARCore 물리 정답 |
| 객체 ID가 있는 정답 동영상 | 누락, ID전환·분절, 가림·재등장 | RGB만으로 미터 거리 정답 |
| 실제 raw depth/confidence·pose와독립 거리/이동 기준 | 실제 깊이 가용성·거리와 접근 오차 | 모든 기종·모든 조도/재질에서의 보장 |

필요한 영상은 객체이름보다 **프레임별 영역·같은 객체 ID**가 중요하다. 깊이까지 평가하려면 RGB-D 시각/좌표 정합과 단위·보정 정보가 있어야 한다. 실제 ARCore가 내놓은 값은 독립적으로 측정한 거리/운동 기준과 비교한다. 답지 없는 RGB 영상은 동작관찰용으로 분리한다.

휴대폰은 사용자가 허용한 바닥 방향 조건을 유지한다. 밝은 대상 장면이 아직 불가능하면 공개 동적 자료·합성 시퀀스를 먼저 진행하고 실물 검증만 남겨 둔다. 바닥 방향 시험을 반복해 유효 거리 검증으로 표시하지 않는다.

### 필수 동적 시나리오

1. 카메라 정지 + 객체 접근: 상대 거리 감소와 객체 자체 이동을 확인한다.
2. 사용자 전진 + 정지 객체: 접근 위험은 별도 평가하되 “객체가 다가온다”로 잘못 분류하지 않는다.
3. 제자리 카메라 회전·짧은 흔들림: 화면 이동·camera Z 변화만으로 접근 안내를 만들지 않는다.
4. 옆으로 통과하거나 멀어지는 객체: 일시적 거리 감소와 충돌 가능 경로를 구분한다.
5. 교차·가림·다시 등장·mask 분할/합침: ID가 다른 물체로 바뀌며 속도가 튀는지 확인한다.
6. Raw Depth 중복/누락·tracking PAUSED·세션 재시작·결과 지연: 독립적인 새 깊이와 속도 관측을 구분하고 불확실 상태로 전환한다.
7. PARTIAL의 대표 성분 변경: 서로 다른 조각의 거리를 이어 가짜 급접근을 만들지 않는다.
8. 기존 모델과 FastSAM이 같은 물체를 잡음: 중복 안내를 막되 겹친 다른 물체의 위험을 삭제하지 않는다.

거리 감소만으로 “객체 자체가 이동한다”를 확정하지 않는다. 미터 속도 계산에는거리 정의·좌표계·관측 시각·pose 품질과 일관된 물체 영역이 필요하다. camera Z와직선거리를 섞지 않는다. 정상적인 pose 변화는 좌표 보정에 사용한다. pose 기준계 재설정·불연속·추적 품질 상실 또는 객체 ID·대표 성분 변경 시에는 해당 시계열을 재초기화한다. 단순 `거리÷거리감소속도`도 측면 통과를 포함한 모든 상황의 충돌 시간으로 표시하지 않는다.

### 평가 지표와 수락 기준을 정하는 시점

영역 R50/R75·누락, 거리P50/P95 오차·가용률, ID 전환·분절·복구 시간, 접근 오탐/누락·안내 지연을 분리한다. 전처리/모델/마스크/깊이/대기/음성시작 지연도 나눈다. 화면 갱신·모델 완료·신선한 결과 수락·고유 depth 관측은 서로 다른 빈도다.

정확한 위험 허용 수치는 보정용 시퀀스에서 먼저 정하고 별도 평가 시퀀스에 고정 적용한다. 속도 목표는 임의로 60fps나 2fps로 고정하지 않고 **감지 거리·상대 접근 속도에서 확보되는 시간 안에 실제 경고가 시작되는지**로 정한다. 관측 → 음성 시작의 전체 지연에 사용자 반응 시간과 거리 불확실성 여유를 함께 고려한다. 기존 1초 age gate는 768 계측의 초기 비교 설정으로만 재사용하며 위험 안내 기준으로 승격하지 않는다.

## 8. 병렬 분담과 산출물

| 담당 | 소유 범위 | 병렬 가능한 작업 |
|---|---|---|
| 모델·마스크 담당 | phase3 모델 계약 / decoder / 768 canonical 자료 | Android 입력 연결과 병렬, shape 계약 선행 공유 |
| Android실행 담당 | phase3 loader/replay/전처리/worker/빌드 | decoder·깊이 시험과 병렬; 일반 앱 Main은 후반 단일 담당 |
| 깊이·추적 담당 | 깊이 회귀·추적/pose 관측 설계 | 초기에는 768 깊이 자료·동적 시퀀스 준비, 운동 정책은 별도 단계 |
| 테스트·독립검토 담당 | 정답 자료·입력 혼입/시각/수명/계측 검토 | 개발자와 독립적으로 결과 재계산·실패 사례 확인 |
| Root | 통합 계획·ADB·설치·기기 시험 직렬 실행·최종 판정/기록 | 같은 휴대폰 동시 시험·같은 파일 동시 수정 금지 |

이번 계획을 위한 Android 전환 항목 조사와 독립 인수 조건 검토는 기존 두 담당이 읽기 전용으로 수행했다. 위 표는 앞으로의 구현 분담이며, 현재 구현이 착수됐다는 뜻이 아니다. 새 계층이나 범용 다중 모델 플랫폼을 만드는 대신 현재 두 모델에 필요한 작은 계약으로 시작한다.

예정 산출물은 **768 별도 시험 APK, 768 입력/출력·mask·깊이 회귀 자료, 단계별 지연·부하 그래프, 연속 추적/접근 평가 자료, 원본 앱 통합 APK와 검증 보고서**다. 이전 640의 APK·소스 스냅샷·원출력·실패 기록은 그대로 보존한다.

## 9. 계획 수립 시점에 완료한 것

- 사용자 768 결정을 반영한 전체·단계 계획 수립.
- 현행 모델 파일·SHA·출력 형상·640 고정 decoder·역할이 섞일 replay 경로·기존 부하 모니터를 읽어 계획과 대조.
- 별도 담당의 Android 변경 범위·운동 판정 인수 조건 검토 반영. 정상 pose 변화와 기준계 재설정을 구분하도록 최종 문구 보완.
- 새 실행·새 성능 향상·실물 깊이·접근 판정 통과를 주장하지 않음. **다음 실행 단계는 0~1의 768 계약·입력 역할·decoder 전환**이다.


## 10. 실행 후 확정한 후속 순서

0~2단계에서 v10까지 구현하고 실제7회 시험을 완료했다. 추가영역과깊이는5개결합실행의233마스크·401성분에서일치했다. CPU/GPU분업은순차대비기존모델완료1.95→7.775회/초와결정나이557.4→498.1ms로관측됐지만, 추가영역수락은약2회/초이고열상태차이가있어자동최적값으로채택하지않았다.

새동적시험은영역탐지보다ID연속성이먼저해결돼야함을보였다. 다음단일구현은기존tracker의이름없는mask대응점수에mask겹침·깊이·pose를선택적으로연결하고모호한연결을보류하는시험이다. 임계값을일괄완화하지않고별도평가시퀀스로ID전환·분절·접근오류를확인한다. 조합기기점검연결은기존선택/저장/부하구조를확장하되잘못된프로필채택을막는출력·연속성조건과함께검증한다.

실제바닥방향에서ARCore anchor생성/해제와연속pose는확인됐지만양수깊이는0이다. 물리거리·움직이는물체접근검증과원본앱의새접근음성활성화는남아있다. 상세수치·실패·수정후검증·담당과원자료는위실행보고서에연결했다.
