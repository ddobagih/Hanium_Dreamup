3. 긴급 오류 복구 (Wave 1): 허용 후 4–6시간

서버·데이터 작업조와 외부 요청 경로 작업조가 동시에 진행한다. 각 변경과 집중 시험은 약 2–3시간, 합류 뒤 기본 연결 확인은 약 1–2시간이며 자동 검사 대기는 별도다.

서버·DB · 변경 기능 집중

개인정보 요청의 첫 INSERT 503 제거

결과: 동의·삭제 요청이 저장소 오류(503)가 아니라 정상 처리되고, 요청 한도 초과만 429가 된다.

  • 기존 migration은 고치지 않고 현재 head 202608150002 뒤 successor를 추가한다.
  • ck_actor_rate_limit_events_group을 다시 만들며 기존 5개 값과 privacy를 모두 허용한다.
  • Backend의 expected Alembic head와 migration 안내를 함께 갱신한다.
  • 빈 DB upgrade와 기존 행이 있는 DB upgrade를 모두 검증한다.

핵심 파일: 기존 rate-limit migration, readiness, PostgreSQL rate-limit test

수용 기준

  • privacy 12회까지 저장되고 13회째 429
  • PostgreSQL store를 실제 켠 동의·삭제 API가 503을 내지 않음
  • 저장소 장애 시 기존 fail-closed 503은 유지
요청 중계·외부 경로 · 변경 기능 집중

계정 삭제 3경로를 Nginx에서 Gateway까지 연결

결과: 요청·상태·기기증거가 외부 ingress를 통과하고, 닮은 경로나 잘못된 ID는 계속 404다.

  • base exact location 1개와 anchored request-ID regex location 2개를 추가한다.
  • 본문 상한은 요청 4 KiB, 상태 GET의 edge 방어 상한 1 KiB, 기기증거 16 KiB로 둔다. Gateway는 status GET의 실제 body를 계속 거부한다.
  • product boundary를 기존 5개 API에서 8개 API로 맞추고 /privacy/rights는 별도 유지한다.
  • 날짜가 붙은 과거 5-route checker는 고치지 않고 신규 current ingress test를 추가한다.

핵심 파일: Nginx 예시, 제품 경계, 신규 test_walksafe_android_gateway_ingress_current.py

수용 기준

  • 16·128자 ID는 전달, 15·129자·잘못된 문자·후행 slash·추가 segment는 404
  • 허용된 8개 API와 rights만 loopback Gateway로 전달
  • catch-all 404, no-store, access-log 차단 경계 유지

두 작업조가 합쳐진 뒤

  1. 현재 결함을 의도적으로 고정한 진단 test를 historical 판정으로 옮긴다. 기능을 다시 깨뜨리는 assertion만 successor remediation test로 교체한다.
  2. 실패·성공 smoke를 분리한다. 잘못된 capability로 Nginx 기본 404와 Gateway JSON 오류를 구분하고, 격리 DB의 유효한 actor/capability로 Backend·PostgreSQL까지 도달해 503·404가 사라졌는지 본다.
  3. 기술 시험을 먼저 통과시킨다. 변경 기능 집중 시험 후 서버 기능 자동 검사를 실행하고, 긴 통제 검사는 별도 작업으로 보낸다.

4. 로컬 핵심 기능 구현 (Wave 2): 병렬 1–1.5일

실제 데이터 삭제와 용량 상태 전달을 서로 다른 작업조가 동시에 만든다. Wave 1 후반부터 준비를 겹치면 Wave 1·2 전체 경과는 1.5–2일이며, 1명이 순서대로 하면 2.5–3일이다.

서버 신고 데이터 격리 삭제 · Wave 2

상태 표시가 아니라 실제 서버 데이터 삭제

결과: 해당 계정 세대의 신고 기록·종속 정보·암호화 파일을 격리 환경에서 실제로 지우고, 삭제 요청과 감사 기록은 보존한다. 이를 계정 전체 삭제 완료로 부르지 않는다.

  • 신규 account_deletion_worker.py를 수동 one-shot·단일 host·제한 batch로 실행해 pending server-owned 항목을 조회한다.
  • 기존 subject-generation fence를 잡아 동시 ingest와 삭제를 직렬화한다.
  • 일반 API 역할의 server-owned terminal 전이 권한을 회수하고, 전용 최소권한 역할만 검증된 물리 삭제 manifest와 결속해 상태를 바꾸게 한다.
  • DB 변경에는 전용 역할의 삭제·상태전이 권한과 별도 DSN 설정 계약을 넣는다. 실제 계정 비밀 배치와 예약 실행은 Wave 4 이후다.
  • 기존 retention의 maintenance lock, backup 확인, row lock, 파일 identity/hash, recovery journal·재시작 reconcile primitive를 재사용한다.
  • 하나의 crash-safe deletion manifest를 서버 inventory evidence로 매핑하고, 실제 저장 위치가 없는 항목은 근거와 함께 NOT_APPLICABLE로 둔다.
  • 신규 maintenance script로 실행하며 API process와 runtime DB role에서 분리한다.
  • 학습·백업·기기 등 외부 증거가 필요한 항목은 임의 완료하지 않고 EXTERNAL_PENDING을 유지한다.
  • tombstone, 삭제 request·item·event, consent ledger와 3년 보존 completion receipt는 삭제하지 않는다.

수용 기준

  • reports·종속 report_image_objects·저장 객체 삭제와 보존 ledger 유지
  • 동시 ingest 차단, 부분 실패, 재시작, 중복 실행과 최소권한 role 거부를 테스트
  • 일부 저장소 실패 시 completion receipt 미발급
  • 서버 삭제 뒤에는 overall PARTIAL·receipt 없음, 외부 항목까지 terminal인 경우에만 전체 완료

근거: 현재 삭제 상태 머신, 기존 통합 test

용량 상태 전달·집행 · Wave 2

70·85·95·100% 서버 용량 상태

결과: 시험용 용량 정보를 서버에서 앱까지 전달하고 단계별 제한을 확인한다. 상태가 없거나 만료되면 새 원본·자동 생성은 안전하게 보류한다.

  • Backend 내부 상태 producer·endpoint에 version, observed_at, expires_at, level, coarse reason을 둔다.
  • Gateway는 기계 자격증명으로 제한시간이 있는 내부 조회를 수행하고 암호화된 last-known snapshot을 보관한다. 조회 실패는 세션 상태 전체를 5xx로 만들지 않고 capacity만 만료·부재로 표시한다.
  • 새 공개 route 대신 query 없는 GET /api/field-session에 공개 가능한 coarse snapshot만 넣고 OpenAPI를 갱신한다. ?devices=true 응답은 건드리지 않는다.
  • Android에 별도 capacity 모델·인메모리 admission과 앱 시작·네트워크 재연결 조회를 연결한다. 실측 전 임의 polling 주기는 만들지 않는다.
  • 이번에는 70% 경고 event와 85·95·100% 정책 판정 결과까지 구현한다. 실제 참가자 등록·원본 session·학습/자동신고 pipeline에 대한 운영 집행은 각 소유 기능과 합쳐질 때 별도 완료한다.
  • 만료되지 않은 기존 자료와 단말 안전 기능은 용량 때문에 삭제·중단하지 않는다.
  • 정식 만료 대응은 단말 byte 상한 안에서 암호화 보관 후 재연결 시 재판정하는 것이다. 현재 persistent queue는 비활성이므로 이번 최소 기능은 신규 raw·automatic 생성만 fail-closed 보류하고 정책 완료를 주장하지 않는다.
이번 최소 기능과 실제 운영 수집기의 경계

이번 범위는 상태 형식·시험용 수집기·전달·Android 해석과 인메모리 제한까지다. 실제 GCS 주·백업 수집기, 영속 암호화 queue·30일 retry, 유효 시간은 cloud·단말 부하·offline 실측 뒤 별도 완료한다.

수용 기준

  • 합성 collector로 69→70→85→95→100과 하향 복구 상태 전이
  • 전달 E2E와 70 경고 event·85/95/100 정책 판정 시험을 분리해 확인
  • 앱 시작·재연결 조회와 오래된 버전·주입한 TTL 만료·수집기 장애에서 인메모리 fail-closed 동작
  • 서버 임계값을 휴대전화 queue 임계값으로 복사하지 않음

정책 근거: 보안·운영 설계

여기까지가 로컬 핵심 기능 완료선이다.

기존 세션·키·DB·업로드·AI·서비스 준비 상태는 새로 만들지 않는다. 필요한 활성화와 집중 시험만 Wave 3에서 4–6시간 동안 진행하며 Wave 2 완료를 막지 않는다.

5. 병렬 팀 구성과 파일 충돌 방지

작업조 A
서버·데이터 개인정보 DB 변경 → 삭제 작업 프로그램 → rate-limit 준비 상태. Privacy service·migration·PostgreSQL 시험 경로만 소유한다.
작업조 B
외부 요청 경로 Nginx 삭제 경로 → 제품 경계 → 현행 진입 경로 시험만 맡는다. Gateway/OpenAPI는 필요 없이 고치지 않는다.
작업조 C
용량·앱 용량 상태 모듈·내부 endpoint, Gateway cache·OpenAPI, Android 해석과 시험을 맡는다. 작업조 B의 변경이 합쳐진 뒤 Gateway 파일을 편집한다.
작업조 D
운영·품질 Wave 1·2에서는 계약 읽기 전용 검토와 합류 뒤 실패·성공 연결 시험만 맡는다. 지표·경보·백업 훈련은 핵심 완료 뒤 별도 운영 작업으로 진행한다.
병합 규칙

제품 수정 허용 뒤 승인된 SHA에서 각 작업조의 별도 작업 폴더를 만든다. backend/app/main.py, OpenAPI 생성물, 공용 test runner·catalog·checkpoint는 통합 담당만 합친다. DB 통합시험과 Gradle 작업은 작업조별 격리 환경이 없으면 직렬 실행한다. 변경 기능 집중 시험이 통과한 commit만 통합 브랜치에 차례로 합친다.

시간 추정은 Wave 1의 작업조 A·B, Wave 2의 작업조 A·C에 각각 1명 이상 배정되는 조건이다. 1명이 순서대로 하면 핵심 기능에 2.5–3일이 걸린다.

8. 후속 기능 점검과 별도 운영 준비 (Wave 3·4)

Wave 3 · 4–6시간

기존 보안 기능의 로컬 집중 점검

  • 장기 세션·기기·refresh 재사용 탐지를 1 replica 전제에서 활성화하고 재시작 시험
  • 개인정보 key rotation·recovery를 실제 KMS가 아닌 격리 fixture로 확인
  • DB·업로드·AI 격리를 큰 입력·악성 corpus·장애 복구로 집중 확인
  • 서비스 준비 상태에 새 rate-limit DB 제약 drift 확인을 연결

완료 표시는 LOCAL_INTERNAL_PASS다. 실제 운영 활성화·키 회전·복구 완료를 뜻하지 않는다.

Wave 4 · 저장소 작업 1–2일

운영 설정과 사전 환경 인계

  • Gateway·Backend 상태 확인, request ID 전파, route·status·latency·5xx 지표 설정
  • 준비 상태·지속 5xx·용량·감사 기록·백업 age의 dashboard·경보 설정
  • 암호화 backup timer와 격리 restore dry-run 결과 기록
  • 삭제 작업의 unit/timer/env·OS ACL·claim lease 설정 초안과 사전 환경 점검

실제 secret 배치, on-call 경보 수신, 생산 backup·restore, 삭제 scheduler 실행은 환경 권한이 있어야 하며 1–2일 저장소 작업의 완료 주장에 넣지 않는다.

사전 운영 환경에서만 따를 직렬 전환 순서
  1. 후보 code·artifact·migration·Nginx를 설치하고 hash 고정
  2. 실제 사전 backup을 만들고 검증하며 현 DB head 확인
  3. 외부 요청을 닫아 drain하고 Gateway·Backend 쓰기를 정지
  4. migration 사전 확인 후 적용하고 새 head·CHECK 확인
  5. 필요 시 issuer bind 또는 기존 binding 확인 후 Backend 시작·ready 확인
  6. Gateway 시작 후 내부 실패·성공 연결 시험
  7. nginx -t 후 외부 삭제 경로 활성화
  8. 15–30분 404·429·5xx·준비 상태 관찰
현재 deploy 파일은 예시이며 실제 적용 증거가 아니다.

운영 반영에는 별도 사전/실제 운영 host, TLS·DNS, Secret Manager/KMS, 중앙 로그·경보, offsite backup, Android 서명·배포 권한이 필요하다. migration 뒤 privacy 행이 생성되면 구 CHECK로 downgrade하지 않고 ingress를 닫은 뒤 roll-forward한다.

9. 로컬 핵심 기능 완료 기준 (Wave 2 종료)

2026-08-25 완료 표시는 INTERNAL_TARGETED_VERIFIED다. 배포·실제 삭제 운영·정식시험·출시 승인을 뜻하지 않는다.

집중 검증 결과

Backend 단위·계약 96개, 실제 PostgreSQL 통합 47개, Gateway 전체 97개, Android 전체 1,016개, repository·제품 경계 29개가 모두 통과했다. 삭제·용량 구현은 독립 재감사에서 P0/P1 잔여 없음으로 판정됐다.

  • 개인정보 동의·삭제 첫 요청이 PostgreSQL rate limiter 때문에 503이 되지 않는다.
  • 계정 삭제 3경로의 실패 probe는 Gateway에서, 유효한 성공 probe는 Backend·격리 DB까지 도달하며 유사 경로는 차단된다.
  • 격리 DB·임시 암호화 저장소에서 대상 reports·cascade 종속 정보·대응 .wse가 실제 삭제되고 ledger는 보존된다. 일반 API는 물리 삭제 없이 server item을 완료할 수 없다.
  • 서버 삭제 범위 뒤 전체 상태는 PARTIAL이며 외부 증거 전에는 완료 기록이 없다. 남은 서버 식별자료는 목록별 판정 전까지 계정 전체 삭제 완료에 포함하지 않는다.
  • 합성 70·85·95·100% capacity snapshot이 Backend→Gateway cache→Android parser로 전달되고 단계별 정책 판정·만료 실패 격리가 작동한다.

후속 기능 점검·운영 준비의 별도 완료 기준

  • 장기 세션·개인정보 ledger·DB·업로드·AI 격리는 재작성 없이 로컬 집중 시험을 통과하고 LOCAL_INTERNAL_PASS로 표시된다.
  • Backend/Gateway 상태 확인, 최소 지표·로그, 경보·backup timer 설정과 격리 restore dry-run 결과가 버전 고정된다.
  • 합성 capacity 상태의 지표·경보 설정과 단계별 정책 판정 연결 시험이 통과한다.

이 완료 기준에 포함하지 않는 것

  • 실제 cloud·production 자원 생성, 인증서·KMS·on-call 채널 provisioning
  • 삭제 작업의 실제 운영 계정·secret, scheduler 실행, 생산 backup 정책과 전체 서버 inventory 판정
  • 실제 GCS primary/backup collector·자동 갱신, Android persistent encrypted queue·30일 retry, 실측 전 TTL·polling 확정
  • 85% 참가자 등록·95% 원본 session·100% 학습/자동신고 pipeline의 실제 운영 집행
  • 외부 학습·백업·기기 저장소의 삭제 증거가 없는 항목을 임의 완료 처리
  • 279개 정식시험, 외부 보안·개인정보 검토, release eligibility 승인
  • 요구가 확인되지 않은 다중 replica shared store, 전면 tracing, 새 framework 도입
