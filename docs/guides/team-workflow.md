# WalkSafe 팀 작업 흐름

이 문서는 기능 분담부터 검토·인수인계까지의 공통 절차입니다. Goal 활성화, 정책 승인, 산출물 상태 전환의 정본이 아니며 저장소 [`AGENTS.md`](../../AGENTS.md), [프로젝트 체크포인트](../control/walksafe-project-continuation-checkpoint.json)와 checkpoint가 가리키는 focus Goal 계약이 우선합니다. hash로 봉인된 과거 재개 안내서의 상태·gate 명령은 현행 절차로 실행하지 않습니다.

## 1. 작업 선택

1. [프로젝트 가이드](project-guide.md)에서 제품 경계와 완료 판단을 확인합니다.
2. [프로젝트 체크포인트](../control/walksafe-project-continuation-checkpoint.json)의 focus, ready frontier, `next_action`을 확인합니다.
3. [수정 백로그 r026](../control/audits/walksafe-implementation-remediation-backlog-20260812-r026.json)에서 선행 의존성과 남은 Gap을 확인합니다.
4. [기능 구현·분담 목록](../planning/walksafe_feature_implementation_catalog.html)에서 분야·우선순위·상태를 좁히고 담당 충돌을 확인합니다.
5. 현재 실행 권한이 없는 Goal이나 외부 증거가 필요한 항목은 구현 완료로 잡지 않습니다.

기능 목록의 상태는 팀 탐색용 요약입니다. 정책과 현재 실행 leaf를 바꾸지 않습니다.

## 2. 기능 분담표 사용

[기능 구현·분담 목록](../planning/walksafe_feature_implementation_catalog.html)은 검색, 분야·상태·우선순위 필터, 실제 담당자, 완료 표시를 제공합니다.

- 실제 담당자와 완료 표시는 현재 브라우저에 저장됩니다.
- 팀 공유 전에는 `분담 정보 저장`으로 JSON을 내보내고, 한 사람이 기준 파일을 관리합니다.
- 다른 팀원은 `분담 정보 불러오기`로 같은 snapshot을 사용합니다.
- 완료 체크는 분담 진행 표시일 뿐 Goal 완료, 정식 시험 PASS, 출시 승인이 아닙니다.
- 같은 세부 기능을 여러 사람이 맡으면 코드·테스트·문서 소유 범위를 먼저 나눕니다.

## 3. 작업 범위 선언

구현 전에 다음 내용을 짧게 기록합니다.

- 기능 ID와 사용자에게 보이는 결과
- 변경할 모듈과 파일 범위
- 바꾸지 않을 정책·통제·외부 시스템 경계
- 성공 조건과 실패 입력
- 실행할 자동 검사와 사람이 확인할 항목
- 실기기·외부 공급자처럼 이번 작업에서 실행하지 못하는 검증

작업 계획은 `단계 → 검증 방법` 형태로 작성합니다. 해석이 둘 이상이면 구현 전에 팀과 결정합니다.

## 4. 브랜치와 변경

- 시작 전에 원격 `current`와 로컬 기준을 확인하고 기존 사용자 변경을 보존합니다.
- 한 브랜치는 하나의 기능 또는 결합이 필수인 작은 변경 묶음을 다룹니다.
- 브랜치 이름은 기능 ID를 알 수 있게 `feature/<기능-ID>-<짧은-설명>`, 결함은 `fix/<기능-ID>-<짧은-설명>`, 문서는 `docs/<주제>` 형태를 권장합니다.
- 주변 코드 정리나 unrelated refactor를 섞지 않습니다.
- 비밀값, 사용자 원자료, 운영 로그, 로컬 환경 파일을 커밋하지 않습니다.
- 통제 파일이나 기존 승인 산출물을 바꿔야 하면 먼저 [`AGENTS.md`](../../AGENTS.md), 현재 checkpoint와 focus Goal의 event-scoped 결속 계약을 확인합니다.

폴더와 파일 배치는 [저장소 가이드](repository-guide.md), 도구 준비는 [개발 환경 가이드](development-environment-guide.md)를 따릅니다.

## 5. 구현과 검증

1. 현재 코드 지도와 실제 source·OpenAPI·lock·runtime config, 기존 구현 패턴, 기존 테스트를 읽습니다. 역사 snapshot README는 현행 실행 계약으로 사용하지 않습니다.
2. 요청한 기능을 만족하는 최소 변경을 구현합니다.
3. 실패 입력 또는 회귀를 재현하는 테스트를 추가하거나 기존 검증 경로를 확장합니다.
4. 가장 작은 관련 검사를 먼저 실행하고, 통과하면 영향 범위에 맞는 상위 계층 검사를 실행합니다.
5. 사용자 동작, API, 설정, 산출물 상태가 바뀌면 해당 소유 문서를 갱신합니다.
6. 변경 파일과 검증 결과를 해당 날짜의 단일 daylog에 통합합니다.

테스트 분류와 대표 명령은 [테스트 가이드](testing-guide.md), 도구 상태와 부작용은 [스크립트 가이드](scripts-guide.md)를 확인합니다.

## 6. 자체 검토

검토 요청 전에 다음을 확인합니다.

- 변경한 모든 줄이 기능 범위와 직접 연결되는가
- 정책 기준선과 사용자 안전 경계를 약화하지 않았는가
- 인증·권한·개인정보·오류 응답이 fail-closed인가
- 테스트가 성공 경로뿐 아니라 거부·복구 경로를 포함하는가
- 새 파일과 링크가 실제 경로에 존재하는가
- 내부 테스트 PASS를 실기기·현장·운영 PASS로 표현하지 않았는가
- 정식 시험 `279/279 NOT_RUN`, gate 5개 `NOT_RUN`, `NOT_ELIGIBLE` 경계를 허위로 올리지 않았는가

## 7. 독립 검토와 병합

작성자와 다른 검토자가 최소한 다음을 확인합니다.

- 요구사항·정책·기능 ID 추적
- 변경 범위와 선행 의존성
- 코드·테스트·문서의 일치
- 보안·개인정보·안전 회귀
- 실행 명령, 결과, 미실행 범위의 구분

검토 지적을 반영한 뒤 관련 검사를 다시 실행합니다. 병합 설명에는 변경 목적, 주요 파일, 검증 명령과 결과, 남은 `NOT_RUN`·blocker를 짧게 남깁니다.

## 8. 인수인계

작업을 넘길 때 다음 형식을 사용합니다.

```text
기능 ID / 범위:
현재 결과:
변경 파일:
통과한 검사:
실행하지 않은 검사:
남은 위험·blocker:
다음 한 가지 행동:
```

`완료`라는 표현은 그 기능의 승인된 완료 조건이 실제 증거로 충족됐을 때만 사용합니다. 그렇지 않으면 `내부 구현`, `부분 구현`, `검증 대기`, `NOT_RUN`처럼 범위를 명시합니다.
