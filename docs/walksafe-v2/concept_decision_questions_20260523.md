## 1. 사용자/접근성

- 주 사용자는 전맹 보행자, 저시력 보행자, 보호자 동행 사용자 중 누구인가? — TTS/진동/화면 정보량이 달라진다.
- 휴대폰 착용 방식은 목걸이 고정인가, 손에 들고 쓰는 방식도 지원하는가? — 카메라 각도와 위험 예측 기준이 달라진다.
- 사용자가 화면을 거의 보지 않는다는 전제를 유지하는가? — 버튼/UI 최소화와 음성/진동 중심 설계가 달라진다.
- 위험 알림의 1차 채널은 TTS인가, 진동인가? — 소음/이어폰 미착용 상황의 fallback이 달라진다.
- TalkBack/스크린리더가 우선 읽어야 하는 상태는 위험, 신고, 위치, 음성 명령 중 무엇인가? — aria-live 충돌을 줄이는 기준이 된다.
- 음성 꺼짐 상태에서도 긴급 위험은 강제 TTS를 허용하는가? — 사용자 통제권과 안전성의 우선순위가 달라진다.
- 위험 안내를 들은 사용자의 기대 행동은 정지, 천천히 이동, 우회, 발밑 주의 중 무엇인가? — 경고 문구와 risk level 매핑이 달라진다.
- 앱의 1차 가치는 보행 보조인가, 시설물 신고 수집인가? — 자동신고 침묵 정책과 위험경고 빈도가 달라진다.
- 일반 사용자에게 confidence, model_key, source 같은 디버그 정보를 보여줄 것인가? — 투명성과 인지 부담 사이의 선택이다.
- 실폰 검증 환경은 TalkBack on/off, 이어폰/골전도, 실외 소음 중 어디까지 포함하는가? — 완료 기준이 달라진다.

## 2. 자동신고

- 자동신고 대상은 `unified_walksafe:damaged_tactile_block`을 primary로 두고 legacy `custom_tactile:damaged_tactile_block`을 fallback 허용으로 유지한다.
- `tactile_damage_area`는 계속 보조 정보로만 둘 것인가, inference 응답에서도 숨길 것인가? — 프론트 표시와 운영자 검수 정보량이 달라진다.
- 점자블록 손상은 기본적으로 위험 경고가 아니라 시설물 신고로 보는가? — TTS 반복 여부가 결정된다.
- 자동신고는 GPS가 없으면 계속 보내지 않을 것인가? — 위치 없는 신고 품질과 누락 사이의 선택이다.
- 음성 요청 신고는 GPS가 없어도 저장 시도하는가? — 사용자 명시 요청 우선 정책이 결정된다.
- 2026-07-02 결정: 자동/음성 신고 중복 후보는 같은 class, 10m, captured_at 전후 1분 기준으로 본다.
- 2026-07-02 결정: 중복 후보여도 저장하고 `duplicate_candidate` tag와 후보 ID를 남긴다.
- 2026-07-02 결정: 사용자가 명시적으로 신고를 요청했고 중복 후보이면 "이미 신고가 된 상태입니다"라고 안내한다.
- 자동신고 성공/실패를 사용자에게 완전 침묵시킬 것인가, 진동/화면 상태는 허용하는가? — 접근성 경험이 달라진다.
- 자동신고에 최소 연속 frame, bbox 크기, confidence 조건을 추가하는가? — 오탐과 미탐 균형이 달라진다.
- 음성 신고가 자동신고 cooldown을 우회하는 정책을 유지하는가? — 같은 건 반복 신고 허용 여부가 결정된다.
- 신고 취소 기능을 제공하는가? — 삭제/상태변경 API와 UI가 필요하다.
- 신고 이미지는 전체 프레임, crop, 둘 다 중 무엇을 저장하는가? — 개인정보와 운영자 판단 품질이 달라진다.
- fake-v2는 계속 실제 저장을 막는가? — 데모 데이터 혼입 방지 기준이다.

## 3. 음성명령

- 음성 명령은 버튼 눌러 녹음 방식으로 고정하는가, wake word/항상 듣기도 목표인가? — 배터리와 개인정보 리스크가 달라진다.
- “신고해줘” 명령은 확인 없이 바로 저장하는가? — 오인식 시 잘못된 신고가 생길 수 있다.
- “신고 취소” intent를 만들 것인가? — 자동/음성 신고의 취소 범위를 정해야 한다.
- intent confidence threshold `0.7`을 유지하는가? — 오인식 실행과 재질문 빈도가 달라진다.
- 녹음 최대 길이 5초를 유지하는가? — 짧은 명령과 긴 목적지 입력 지원 범위가 달라진다.
- STT는 로컬 서버, 브라우저 Web Speech, 클라우드 STT 중 무엇을 우선하는가? — 오프라인성, 비용, 개인정보, 지연시간이 달라진다.
- transcript 원문을 저장하는가? — intent 개선과 개인정보 정책이 충돌한다.
- 낮은 신뢰도/unknown일 때 몇 번까지 재질문하는가? — 보행 중 반복 안내가 위험할 수 있다.
- `repeat_last`가 반복할 마지막 상태는 위험, 위치, 신고 중 무엇을 우선하는가? — 상태 덮어쓰기 정책이 필요하다.
- “음성 꺼” 명령 직후 한 번은 “음성 안내 꺼짐”을 말해도 되는가? — 사용자 기대와 일관성을 정해야 한다.
- TTS 속도/문장 길이/톤은 어떤 기준으로 고정하는가? — 보행 중 이해 가능성이 달라진다.
- 목적지 설정/길안내 음성 명령은 MVP에 포함하는가, 후순위인가? — 구현 범위와 사용자 기대가 달라진다.

## 4. 위험경고/예측

- 위험의 정의는 단순 객체 존재가 아니라 경로 차단과 접근/충돌 가능성 중심이다. 지면 낙상 위험은 현재 MVP의 별도 경고 카테고리에서 제외한다.
- 점자블록 손상 중 어떤 경우만 즉시 경고하는가? — 현재 report-only 정책의 예외가 필요할 수 있다.
- 일반 객체는 COCO allowlist만 볼 것인가, 킥보드/공사물/포트홀은 별도 모델로 볼 것인가? — 모델 구조가 달라진다.
- COCO class명을 그대로 말하는가, 한국어 위험 문구로 매핑하는가? — 사용자 이해도가 달라진다.
- bbox area growth, stable frame, TTC 기준값을 어떻게 정하는가? — 오경고/미경고에 직접 영향이 있다.
- 3~5초 궤적 예측을 MVP에 넣는가, 장기 비전으로 두는가? — IMU/depth/path segmentation 범위가 달라진다.
- heading만 쓸 것인가, DeviceMotion 속도/가속도까지 쓸 것인가? — 경로 차단 판단 정확도가 달라진다.
- depth 정보 없이 bbox 변화만으로 접근 위험을 추정해도 되는가? — 실제 거리 오판 가능성이 있다.
- 손상 점자블록과 일반 객체 위험이 동시에 있을 때 어떤 알림을 우선하는가? — TTS 충돌 방지가 필요하다.
- 같은 class 기준 경고 cooldown을 유지하는가, 객체별/위치별 cooldown으로 바꾸는가? — 반복 경고 억제 방식이 달라진다.
- risk level별 TTS/진동/화면 색을 어떻게 다르게 할 것인가? — 사용자 행동 유도가 달라진다.

## 5. 모델/데이터

- 최종 제품 모델 구조는 tactile 3-class + COCO general인가, 기존 4-class 위험 모델인가? — API/schema/발표 기준이 갈린다.
- Stage1 `best.pt`를 MVP 후보로 확정하는가, 통합 후보로만 두는가? — 배포 문구와 설정이 달라진다.
- 자동신고 threshold는 0.50 high-F1/high-recall 쪽인가, 0.75 precision 보수 쪽인가? — 오탐과 누락의 균형이다.
- “정확도 90%”는 mAP, image-level F1, precision, recall, field success rate 중 무엇인가? — 성능 목표와 보고서 기준이 달라진다.
- bbox mAP와 별도로 image-level presence 평가를 정식 기준으로 삼는가? — 자동신고 목적에는 presence가 더 맞을 수 있다.
- 직접 촬영 데이터를 학습에 사용할 때 동의/비식별/라이선스 기준은 무엇인가? — 데이터 확장 가능성이 달라진다.
- COCO general 모델은 inference-only로 둘 것인가, fine-tune할 것인가? — 일반 객체 경고 품질 개선 방식이 달라진다.
- 서버 `.pt` 추론을 우선하는가, 브라우저 ONNX도 계속 목표인가? — 지연시간/배포/오프라인 전략이 달라진다.
- 학습 산출물과 데이터셋은 계속 local-only인가, 재현용 manifest만 GitHub에 올리는가? — 협업 방식이 달라진다.

## 6. 프론트 UX

- 홈 화면은 계속 카메라 중심 보행 보조 화면인가, 온보딩/설정 화면을 추가하는가? — 진입 UX가 달라진다.
- v2 모드에서 수동 신고 버튼을 숨기는가, 비활성 안내로 두는가? — 사용자가 직접 신고 가능하다고 오해할 수 있다.
- 자동신고 상태 메시지를 사용자에게 보여주는가, 운영/디버그용으로 숨기는가? — 침묵 정책과 UI가 충돌할 수 있다.
- 감지 개수, confidence, detector mode를 항상 보여주는가? — 데모에는 좋지만 보행자에게 과할 수 있다.
- bbox overlay는 모든 detection, alertable/reportable만, 또는 디버그 모드에서만 표시하는가? — 화면 복잡도가 달라진다.
- 권한 요청 순서는 카메라/위치/방향/마이크 중 무엇부터인가? — 초기 이탈과 기능 실패 대응이 달라진다.
- 위치 안내는 위도/경도인가, 주소/랜드마크인가? — 실제 사용자 효용이 달라진다.
- 진동 패턴은 현재 구현값을 유지하는가, 사용자 테스트로 확정하는가? — 구분 가능성이 달라진다.

## 7. 백엔드/API

- v1 `/detect`, `/reports`를 계속 유지하는가, v2로 수렴하는가? — 유지보수 비용과 호환성이 달라진다.
- `/reports`, `/uploads`, status patch에 인증/권한을 붙이는가? — 운영 데이터 노출 리스크가 크다.

- 신고 상태는 `new/reviewed/resolved` 3개로 충분한가? — 오신고/중복/기관제출 상태가 필요할 수 있다.
- 상태 변경 이력 테이블을 만들 것인가? — 감사/운영 추적 기준이 달라진다.
- 이미지는 local upload로 충분한가, object storage가 필요한가? — 배포/백업/공유 방식이 달라진다.
- 서버가 EXIF 제거/blur를 수행해야 하는가? — 개인정보 노출을 줄이는 기준이다.
- `/reports/export`에 주소, 검토자, 제출상태, 접수번호를 넣는가? — 기관 제출 가능성이 달라진다.
- rate limit/spam 방지를 사용자/기기/IP 기준으로 둘 것인가? — 자동신고 오작동 대응이 필요하다.
- voice server와 backend server를 합칠 것인가, 분리할 것인가? — 배포/장애 격리 방식이 달라진다.

## 8. 운영자/공공기관 제출

- 운영자는 팀 내부, 복지관, 지자체 담당자 중 누구인가? — admin UI와 용어가 달라진다.
- `reviewed`는 기관 제출 가능 상태인가, 단순 검토 완료인가? — 상태 의미가 달라진다.
- `resolved`는 보수 완료, 오신고 종료, 중복 처리 중 무엇을 뜻하는가? — 통계 해석이 달라진다.
- 2026-07-10 결정: 공공기관 신고는 관리자 검수·필터 후 CSV 다운로드와 수동 외부 신고로 처리한다. 자동 API 연동은 범위 밖이다.
- 제출 대상 기관은 안전신문고, 국민신문고, 지자체 도로관리 부서, 시설관리자 중 어디인가? — payload와 인증 방식이 달라진다.
- 제출 전 필수 검수 항목은 이미지, 위치 정확도, confidence, 중복, 개인정보 중 무엇인가? — admin workflow가 달라진다.
- 제출 단위는 개별 신고인가, 위치 클러스터 묶음인가? — 기관 업무 부담이 달라진다.
- 제출 후 접수번호/처리상태를 저장하는가? — 별도 submissions 계층이 필요할 수 있다.
- fake/source=server 데이터를 운영자 내부 export 기본 필터에서 자동 제외하는가? — 데모 데이터 혼입 방지 기준이다.
- 히트맵/GeoJSON/지역별 통계를 제공하는가? — PostGIS/API 범위가 달라진다.

## 9. 개인정보/법적 리스크

- 카메라/위치/마이크 동의를 어떤 문구와 시점에 받는가? — 온보딩/법적 고지가 필요하다.
- 신고 이미지에서 얼굴/차량번호/상호/주소를 blur하는가? — 개인정보 리스크가 달라진다.
- GPS 좌표를 그대로 저장/제출하는가, 운영/공개용으로 흐리게 처리하는가? — 보수 정확도와 위치정보 보호가 충돌한다.
- 신고 이미지/위치 데이터 보존 기간은 얼마인가? — cleanup 정책과 사용자 권리 대응이 필요하다.
- 사용자가 본인 신고 삭제를 요청할 수 있어야 하는가? — 삭제 API/운영 절차가 필요하다.
- 음성 transcript/audio는 저장하지 않는가? — 품질 개선과 개인정보 보호 사이 결정이다.
- 수집된 신고 데이터를 모델 재학습에 사용할 것인가? — 별도 동의/비식별 절차가 필요하다.
- 앱이 위험을 놓쳤을 때 책임 고지를 어떻게 할 것인가? — 보행 보조/참고용 disclaimer가 필요할 수 있다.
- 미성년자/학교/병원/주거지 주변 이미지 처리 기준을 따로 두는가? — 민감 위치 필터링 기준이다.

## 10. 오프라인/장애대응

- 오프라인에서 shell만 열리면 충분한가, 탐지/신고 queue까지 지원하는가? — IndexedDB/retry 구현이 필요할 수 있다.
- 네트워크가 없을 때 자동신고를 저장했다가 나중에 전송하는가? — 중복/위치/시간 정책이 필요하다.
- `/detect/v2` 서버가 죽으면 fake-v2로 fallback하는가, 탐지를 중단하고 명확히 알리는가? — fake를 실제 안전 판단처럼 쓰면 위험하다.
- voice server가 죽으면 브라우저 STT fallback을 쓰는가, 음성명령을 비활성화하는가? — 접근성 핵심 장애 대응이다.
- 카메라 권한 거부 시 위치/음성만 가능한 모드를 제공하는가? — 기능 축소 UX가 필요하다.
- 위치 권한 거부 시 자동신고를 계속 막는가? — 신고 품질과 사용자 기대가 충돌한다.
- 마이크 권한 거부 시 대체 조작은 무엇인가? — 접근성 fallback이 필요하다.
- 배터리/발열이 심할 때 detection interval을 줄이는가? — 실폰 사용성이 달라진다.
- 서버 응답 지연/timeout 기준은 몇 초인가? — 보행 중 대기 위험을 줄여야 한다.
- PWA 업데이트/cache versioning 정책은 무엇인가? — 오래된 UI/API contract가 남을 수 있다.
