| 항목 | 값 |
|---|---|
| 문서 ID | ART-DOC-MANUAL-001 |
| 충족하는 산출물 유형 | DOC-02, DOC-03, DOC-04 |
| 버전 | 0.4.0 |
| 생명주기 상태 | Draft |
| 기준일 | 2026-07-22 |
| 내용 책임자 | 문서통제담당 |
| 검토자 | 프로젝트관리자, 기술책임자 |
| 승인자 | 프로젝트책임자 |
| 승인 상태 | 미승인 — 사람 검토 필요 |

> 이 문서는 실제로 적용할 통제 규정의 정식 초안이다. 정책 기준선 승인은 끝났지만 이 문서 자체는 아직 승인되지 않았다. 따라서 현재 상태는 Draft이며, “산출물 작성 완료”나 “출시 가능”을 뜻하지 않는다.

## 1. 이 규정이 필요한 이유

WalkSafe에는 기획서, 요구사항, 설계, 코드, 시험 결과처럼 성격이 다른 자료가 많다. 파일이 많아질수록 다음 문제가 생기기 쉽다.

- 같은 이름의 파일 중 무엇이 최신인지 알기 어렵다.
- 계획과 실제 시험 결과가 섞여, 하지 않은 시험을 완료한 것처럼 오해할 수 있다.
- 한 정책을 바꿨는데 관련 요구사항·설계·시험 문서가 예전 내용으로 남을 수 있다.
- 자동 생성 파일을 직접 고쳐 다음 생성 때 수정 내용이 사라질 수 있다.

이 규정은 각 자료에 고유 ID, 책임자, 상태, 버전, 위치와 연결 관계를 붙여 이런 문제를 막는다. 사람은 [README.md](README.md) 또는 [artifact-register.html](artifact-register.html)에서 현재 상태를 읽고, 자동화는 `artifact-register.json`을 사용한다.

## 2. 적용 범위와 현재 경계

## 3. 공통 개념

### 3.1 유형과 실제 산출물

- **산출물 유형**은 “무엇을 만들어야 하는가”를 나타낸다. 예: `DLV-REQ-01`은 SRD 유형이다.
- **산출물 인스턴스**는 실제 파일이나 기록 한 개를 나타낸다. 예: `ART-REQ-01-001`.
- **제품 요구사항**은 제품이 해야 할 원자적 동작이다. 예: `REQ-001`. 산출물 유형 ID와 섞어 쓰지 않는다.

한 파일이 여러 산출물 유형을 충족할 수 있다. 이때 관리대장에는 유형마다 행을 하나씩 만들고, 같은 파일 안에서 담당 장을 `coverage_anchor`로 구분한다.

### 3.2 서로 다른 세 가지 상태

한 개의 “완료” 표시로 모든 의미를 대신하지 않는다.

| 상태 축 | 답하는 질문 | 예 |
|---|---|---|
| 생명주기 | 작성·검토·승인 단계가 어디인가? | Planned, Draft, In Review, Approved, Baselined, Superseded, Archived |
| 신선도 | 현재 정책·코드와 맞는가? | Current, Stale, Unknown |
| 검증 | 자동 검사나 사람 검토가 끝났는가? | Not Run, Structure Checked, In Review, Verified, Failed |

예를 들어 문서가 `Approved`여도 상위 정책이 바뀌면 신선도는 `Stale`이 될 수 있다. 자동 구조 검사를 통과해도 사람이 승인하지 않았다면 생명주기는 `Approved`가 아니다.

### 3.3 필수와 조건부

- `REQUIRED`: 현재 범위에서 반드시 작성한다.
- `CONDITIONAL`: 활성 조건이 실제로 생겼는지 먼저 판정한다.
- `N/A`: 조건부 유형을 적용하지 않기로 승인했으며 근거가 있는 경우에만 쓴다.

조건부 항목을 단지 귀찮거나 자료가 없다는 이유로 N/A 처리하지 않는다. 담당자, 판정일, 근거와 승인자를 관리대장에 남긴다. 전체 257개 중 조건부는 109개다. 승인된 현재 범위에서 21개는 활성, 87개는 적용 여부를 확인할 예정이며, WS-16 한 개만 Web/PWA 재승인 전까지 비활성이다. 이 비활성 판정도 삭제가 아니라 근거와 재검토 조건을 관리한다.

### 4.2 ID와 파일명

| 대상 | 규칙 | 예 |
|---|---|---|
| 유형 ID | `DLV-<범주>-<2자리 번호>` | `DLV-TST-23` |
| 표시 코드 | `<범주>-<2자리 번호>` | `TST-23` |
| 인스턴스 ID | `ART-<범주>-<2자리 번호>-<3자리 일련번호>` | `ART-TST-23-001` |
| 기준선 ID | `<종류>-<제품>-<이름>-<버전>` | `PB-WALKSAFE-FEATURE-POLICY-1.0.0` |
| 변경요청 ID | `CR-<4자리 일련번호>` | `CR-0001` |
| 증거 ID | `EVD-<4자리 일련번호>` | `EVD-0001` |

정본 파일명은 소문자 영문, 숫자와 하이픈만 사용한다. 확장자 앞에 `final`, `최종`, `진짜최종`, 사람 이름을 붙이지 않는다. 상태와 버전은 파일명 복제 대신 관리대장과 Git 이력에서 관리한다. 외부기관이 정한 파일명은 바꾸지 않고 `external_source`에 원본 이름과 hash를 기록한다.

### 4.3 버전과 날짜

- 문서 본문 버전은 `MAJOR.MINOR.PATCH` 형식을 사용한다.
- 날짜는 `YYYY-MM-DD`, 시각은 시간대가 포함된 ISO 8601 형식을 사용한다.
- 같은 기준선 안에서 오탈자나 설명만 고치면 PATCH를 올린다.
- 승인 의미나 요구 범위가 바뀌면 MINOR 이상을 올리고 변경요청을 연결한다.
- 호환되지 않는 큰 정책·구조 변경은 MAJOR를 올린다.

### 4.4 자동 생성 파일

`artifact-register.json`, `artifact-change-log.json`, `00-control/README.md`, `artifact-register.html`, 상위 `docs/deliverables/README.md`는 `scripts/build_walksafe_control_bootstrap.py`에서 생성한다. 생성 파일을 직접 고치지 않는다. 입력 카탈로그·승인 manifest·생성기를 고친 후 다시 생성하고 `--check`로 일치 여부를 확인한다.

0~12의 정식 초안·원장·증거를 새로 만들거나 갱신한 뒤에는 이 생성기를 마지막으로 다시 실행한다. 생성기는 계획된 정본 경로의 실제 파일과 Draft manifest를 재스캔해 `canonical_path`, 장 위치, SHA-256, Draft/In Review 상태와 보조 JSON·view를 연결한다. 파일이 있다는 사실만으로 Approved, Baselined 또는 시험 PASS로 올리지 않는다.

### 4.5 후보·생성본·증거·보관본 이름

정본 문서는 상태를 파일명에 반복하지 않고 안정적인 의미 이름을 사용한다. 반면 특정 시점의 후보·파일 목록·실행 증거처럼 서로 다른 바이트를 함께 보존해야 하는 파일은 역할과 revision을 이름에 넣는다.

| 구분 | 이름 규칙 | 예 |
|---|---|---|
| 승인 전 후보 | `<대상>-candidate-<YYYYMMDD>-r<3자리>` | `walksafe-artifact-baseline-candidate-20260722-r001.json` |
| 파일 목록·지문 기록 | `<대상>-manifest-<YYYYMMDD>-r<3자리>` | `walksafe-requirements-manifest-20260722-r001.json` |
| 실행 증거 | `<시험·사건 ID>-evidence-<YYYYMMDD>-r<3자리>` | `tc-fp-035-01-evidence-20260722-r001.json` |
| 검토용 생성 보기 | 정본 또는 후보와 같은 stem의 `.md`·`.html` | `...-review-20260722-r001.html` |
| 대체된 승인본 | 기존 이름과 바이트를 바꾸지 않고 새 manifest의 `supersedes`로 연결 | 이전 기준선 manifest 그대로 보존 |
| 보관 묶음 | `<대상>-archive-<YYYYMMDD>-r<3자리>` | `walksafe-project-archive-20260722-r001.json` |

`final`, `최종`, `진짜최종`, `new`, `copy`처럼 비교 기준이 없는 접미사는 사용하지 않는다. 생성 보기는 `generator`, 입력 파일과 SHA-256을 기록하고 직접 편집하지 않는다. 실행 증거에는 실행 ID·대상 build·환경·시각을 함께 기록하며, 단순 계획이나 빈 템플릿에는 `evidence` 이름을 붙이지 않는다.

### 4.6 이름·위치 변경 절차

1. 변경요청에 이전 경로, 새 경로, 변경 이유와 영향받는 산출물 ID를 기록한다.
2. `rg`와 관리대장의 상·하위 링크로 Markdown 링크, JSON 경로, manifest, 생성기, 시험과 외부 참조를 모두 찾는다.
3. 새 경로를 적용하고 카탈로그·DOC-01·DOC-05·manifest·생성기를 같은 변경에서 갱신한다.
4. 생성기 `--check`, JSON·링크·anchor·SHA-256 검사를 통과시킨다.
5. 이전 승인본은 삭제하거나 덮어쓰지 않고 새 인스턴스의 `previous_instance`·`supersedes`에서 연결한다. 승인되지 않은 중복 초안만 영향 확인 뒤 정리한다.
6. 외부 시스템의 링크를 즉시 바꿀 수 없다면 기존 위치를 임시 호환 경로로 유지하고 제거 조건·담당자·기한을 변경요청에 남긴다.

## 5. DOC-03 검토·승인 절차

### 5.1 역할

| 역할 | 책임 |
|---|---|
| 작성자 | 근거를 확인해 초안을 작성하고 미결정을 숨기지 않는다. |
| 내용 책임자 | 내용의 정확성, 범위와 갱신 시점을 책임진다. |
| 검토자 | 사실, 일관성, 추적성, 안전·개인정보 영향을 확인한다. |
| 정식 승인자 | 검토 결과와 미해결 위험을 보고 승인·반려를 명시적으로 결정한다. |
| 외부 서명자·발행자 | 인수서·동의서처럼 외부 효력이 필요한 원본을 서명하거나 발행한다. |

AI와 자동화는 초안 작성, 누락 검사와 view 생성을 도울 수 있지만 작성 책임자·검토자·승인자를 대신하지 않는다. 승인자 필드가 비어 있거나 승인 기록이 없으면 승인으로 간주하지 않는다.

1인 개발 체계에서는 프로젝트책임자가 최종 승인자 역할을 함께 맡을 수 있다. 다만 인수 확인서처럼 독립 주체가 필요한 기록, 개인정보·안전 독립 검토와 남은 gate는 스스로 통과했다고 기록할 수 없다.

### 5.2 상태 전이

```text
Planned → Draft → In Review → Approved → Baselined
                     ↑            ↓
                     └─ Rework ← Rejected

Baselined → Superseded → Archived
```

- `Planned`: 실제 산출물·실행 증거는 아직 없다. 문서 묶음 안에 작성 조건·실행 절차·빈 템플릿이 있어도 결과나 정본이 생긴 것으로 보지 않는다.
- `Draft`: 내용은 있으나 공식 검토 전이거나 수정 중이다.
- `In Review`: 지정 검토자가 확인 중이다.
- `Approved`: 지정 승인자가 해당 버전을 승인했다.
- `Baselined`: 승인본과 구성 파일의 hash를 manifest로 고정했다.
- `Superseded`: 더 최신 기준선으로 대체됐다.
- `Archived`: 운영상 사용하지 않으며 보존만 한다.

상태를 건너뛰지 않는다. 자동 생성 성공만으로 `Approved`나 `Baselined`가 되지 않는다.

### 5.3 검토 순서

1. 작성자는 필수 내용, 입력 근거, 연결 ID와 미결정 항목을 채운다.
2. 자동 검사는 ID 중복, 누락, 경로, count, hash와 생성 재현성을 확인한다.
3. 내용 책임자는 현재 정책 기준선과 실제 구현 사실을 구분했는지 확인한다.
4. 지정 검토자는 사실·일관성·추적성 및 담당 분야 위험을 검토한다.
5. 작성자는 지적사항을 반영하고 변경 이력에 남긴다.
6. 승인자는 승인 범위, 버전, 미해결 위험과 효력 시각을 기록한다.
7. 기준선 대상이면 manifest로 파일 집합과 SHA-256을 고정한다.

반려나 보류는 실패를 숨기는 상태가 아니다. `blocker`에 사유, 해결 책임자와 목표일을 기록하고 Draft로 되돌린다.

### 5.4 승인 기록의 최소 내용

- 승인 대상 인스턴스 ID, 문서 버전과 SHA-256
- 승인자 이름·역할과 확인 가능한 신원 근거
- 승인 또는 조건부 승인이라는 명시적 결정
- 승인 일시와 효력 범위
- 미해결 예외·위험·waiver와 만료일
- 대체하는 이전 기준선 또는 `null`

메신저 문장이나 대화로 승인받았다면 원문을 통제 사본으로 보존하고, 정규화 방식과 원문 hash를 함께 기록한다.

### 5.5 현재 반드시 남겨 둘 gate

다음 다섯 항목은 정책 기준선 승인과 별개다. 상태를 자동으로 바꾸거나 면제하지 않는다.

1. 휴대전화 대기자료의 실제 용량 한도
2. 서버 용량상태를 휴대전화에 전달하는 규칙
3. 무가림 원본 수집의 출시 전 독립 검토
4. 실제 클라우드 저장비 측정
5. 관리자 휴대전화 분실 복구훈련

이 항목들이 닫히기 전에는 각각 연결된 사용자시험·통합시험·TST-22·REL-02를 승인할 수 없다.

## 6. DOC-04 기준선·버전 관리 규칙

### 6.1 기준선이란

기준선은 “이 시점에 무엇을 승인했는가”를 다시 확인할 수 있도록 승인 대상 파일, 버전, SHA-256, 승인 기록과 상호 관계를 manifest로 묶은 것이다. 단순히 폴더를 복사하거나 파일명에 `final`을 붙인 것은 기준선이 아니다.

### 6.2 기준선 종류

| ID 접두어 | 대상 |
|---|---|
| `PB-` | 제품·기능 정책 |
| `CB-` | 프로젝트 관리·헌장 |
| `RB-` | 요구사항 |
| `DB-` | 설계 |
| `BB-` | 빌드·구현 형상 |
| `VB-` | 시험·검증 |
| `RLB-` | 릴리스 |
| `HB-` | 인수·이관 |

### 6.3 기준선 생성 절차

1. 대상 문서가 `Approved`인지 확인한다.
2. 요구→설계→코드→시험의 실제 인스턴스 링크에 고아와 모순이 없는지 확인한다.
3. 대상 파일을 byte 단위로 읽어 SHA-256을 계산한다.
4. 기준선 ID, 버전, 승인 기록, 파일 경로·hash와 생성 시각을 manifest에 기록한다.
5. 검증 도구로 파일 집합과 hash를 다시 확인한다.
6. 관리대장의 `baseline_id`와 상태를 갱신한다.

현재 DOC-01~05는 Draft이고 지정 검토자의 공식 검토가 시작되지 않았으므로 별도 DOC 기준선은 만들지 않는다.

### 6.4 변경과 stale 전파

승인·기준선 문서를 직접 덮어쓰지 않는다. 변경이 필요하면 다음 순서를 따른다.

1. `CR-` 변경요청에 이유와 요청자를 기록한다.
2. 영향을 받는 상·하위 산출물, 요구, 시험, 위험과 외부 기록을 찾는다.
3. 영향을 받는 기존 인스턴스의 신선도를 `Stale`로 바꾸고 차단 범위를 기록한다.
4. 새 Draft 버전을 작성해 검토·승인한다.
5. 새 기준선을 만들고 이전 기준선을 `Superseded`로 연결한다.
6. 변경 이력과 관리대장을 함께 갱신한다.

정책·수치·지원환경·모델·외부 API·법률 의무·보존기간이 바뀌면 stale 영향 분석을 반드시 수행한다. 링크된 산출물이 자동으로 새 내용에 맞아졌다고 가정하지 않는다.

### 6.5 생성물과 외부 원본

- 생성물에는 생성기 경로·버전, 입력 hash와 생성 시각을 기록한다.
- 외부 원본에는 발행자·서명자, 발행·서명 시각, 원본 위치와 SHA-256을 기록한다.
- 생성물의 보기 형식과 외부 원본을 사람이 편집한 정본처럼 취급하지 않는다.
- hash가 달라지면 이유를 확인하기 전까지 검증 상태를 `Failed` 또는 `Unknown`으로 둔다.

### 6.6 승인 기준선의 부분 정정

승인된 정책이나 요구의 한 문장만 바로잡더라도 기존 기준선 파일을 직접 고치지 않는다.

1. 변경요청에 기존 문장, 정정 문장, 정정 근거와 영향 산출물을 기록한다.
2. 기존 기준선 파일·지문은 그대로 두고 별도의 정정 후보와 영향분석을 만든다.
3. 정정에 의존하는 문서는 `정정 지시 포착·묶음 승인 대기`로 표시하며, 정정이 이미 승인된 것처럼 쓰지 않는다.
4. 승인 패키지는 기존 기준선 ID·지문, 정정 후보 ID·지문, 새 유효 버전과 영향 산출물 파일을 함께 결속한다.
5. 사람이 정확한 일괄 승인문을 승인한 뒤에만 새 정책 버전과 하위 문서 기준선을 순서대로 효력화한다.
6. 중간 단계가 실패하면 이전 승인 기준선을 유지하고 하위 문서 전환을 시작하지 않는다.

FP-035 이동통신망 문구 정정도 이 절차를 사용한다. 이번 Draft에는 사용자가 이미 준 정규화 문장을 반영하지만, 새 일괄 승인 전까지 기존 정책 기준선 1.0.0의 바이트와 승인 상태는 바꾸지 않는다.

## 7. 보안·개인정보·보존

- 비밀번호, API key, private key, 복구코드와 인증서 비밀값을 문서나 관리대장에 넣지 않는다.
- 서명 원본과 불필요한 개인정보·위치·영상·음성은 Git 저장소에 넣지 않는다.
- 민감 원본은 암호화된 통제 저장소에 보관하고, Git에는 승인된 최소 책임 메타데이터와 저장소 참조 ID·SHA-256·접근권한·보존정책만 연결한다.
- 민감 원본의 실제 저장 위치는 공개 README에 쓰지 않고 접근 통제된 참조 ID를 사용한다.
- 개인정보가 있는 산출물은 `personal_data`와 `confidentiality`를 표시한다.
- 보존기간과 삭제 조건이 승인되지 않았다면 임의 값을 넣지 않고 blocker로 남긴다.
- 외부 공개 전에는 비밀정보·개인정보·라이선스·안전 고지를 별도로 검토한다.

## 8. 관리대장 갱신 시점

다음 일이 생기면 DOC-01과 DOC-05를 같은 변경에서 갱신한다.

- 산출물 생성·이름 변경·이동·삭제·대체
- 담당자·검토자·승인자 변경
