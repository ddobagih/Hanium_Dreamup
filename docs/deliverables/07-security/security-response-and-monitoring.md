# WalkSafe 보안 대응·모니터링

> Draft 산출물: SEC-15, SEC-16, SEC-17, SEC-18, SEC-19  
> 문서 버전: 0.1.0 · 상태: Draft · 승인: 미승인  
> 승인 입력: 현재 유효 기준선 `PB-WALKSAFE-FEATURE-POLICY-1.0.1` (`PB-WALKSAFE-FEATURE-POLICY-1.0.0`은 historical component로만 참조)  
> 출시 상태: `NOT_ELIGIBLE` · 남은 gate: 5개 `NOT_RUN`, 면제 없음

## 이 문서를 읽는 방법

보안 위험·취약점·예외·사고·외부 신고·감사기록을 어떻게 접수하고 추적하며 닫는지 정합니다.

`Draft`는 작성 가능한 정책·절차·명세를 적었다는 뜻이며 실제 시험 통과나 외부 승인을 뜻하지 않습니다. 역할명은 책임을 나타내며 서로 다른 사람이 이미 배정됐다는 뜻이 아닙니다. 1인 개발 단계에서는 가짜 검토자를 만들지 않고, 독립 검토가 필요한 항목은 실제 검토자가 참여할 때까지 미승인으로 둡니다.

## 공통 통제 경계

- 현행 정식 제품은 Android 사용자 앱과 별도 비공개 Android 관리자 앱입니다.
- Web/PWA는 재승인 전까지 레거시 참고 범위입니다.
- 위치·영상·음성·서명 등 민감 원본은 Git에 넣지 않습니다. Git에는 통제 저장소 ID, SHA-256, 접근등급, 보존기한과 판정만 둡니다.
- 구조검사 통과는 구현 완료·시험 통과·출시 가능을 의미하지 않습니다.


## 운영 원칙

사건·취약점·예외 원장은 append-only로 관리합니다. 발견 전 상태와 수정 뒤 상태를 덮어쓰지 않고 별도 시각·근거를 남깁니다. 관리자 화면이나 관측 기능만 고장 난 경우 실시간 보행 자원을 침범하지 않게 해당 기능을 멈추고 내부 경보를 남기며, 실시간 안전기능을 믿을 수 없을 때만 사용자에게 이유를 알리고 전체 안전정지합니다.

### 포함 내용과 완료 기준

**반드시 들어갈 내용:** - 취약점 ID·출처<br>- 자산·버전·환경<br>- 심각도·악용가능성<br>- 소유자·기한·상태<br>- 수정·완화·증거<br>- CVE·결함·릴리스 연결<br>- register 개설 기준선·opened_at과 source_security_evidence_id가 있는 취약점 row

**완료 판단:** - 다음 핵심 내용이 근거·버전과 함께 구체적으로 작성되어 있다: 취약점 ID·출처, 자산·버전·환경.<br>- 필수 내용에 공란·암묵적 가정이 없고 미결정은 소유자·기한이 있는 차단 항목으로 표시되어 있다.<br>- 상위 입력과 요구·설계·코드·시험·변경요청의 해당 추적 링크가 유효하다.<br>- 지정 검토자가 사실·일관성·추적성을 확인하고 승인자가 명시적으로 승인했다.

### 갱신·대체·폐기

- 갱신: - 자산·위협·데이터 처리·취약점·권한·법규 변경<br>- 연결된 상위 기준선·사용자 승인 결정·외부 의무 변경<br>- 검토에서 사실 오류·누락·stale 판정 또는 유효기간 만료
- 검토 주기: 변경 발생 즉시. 보안 정책·원장은 활성 프로젝트 동안 최소 월 1회, 실행 증거는 새 build·기기·환경·도구 결과마다 검토합니다.
- 변경: 정책·명세는 변경요청과 영향분석 뒤 새 버전을 만들고 이전 승인본을 `Superseded`로 보존합니다. 원장은 과거 행을 지우지 않고 상태변경 행을 추가합니다. 실행 증거는 손으로 고치지 않고 새 입력 형상으로 다시 생성합니다.
- 보존·폐기: 프로젝트 생명주기와 종료계획을 따릅니다. 개인정보·외부 원본은 SEC-07 보존표와 통제 저장소 삭제 영수증을 따르며 Git에 원본을 보관하지 않습니다.

### 취약점 처리 원장

정본 원장은 [registers/vulnerabilities.json](registers/vulnerabilities.json)입니다. 현재 행이 0개인 것은 “취약점이 없음”이 아니라 아직 정식 scan·침투시험 결과를 수입하지 않았다는 뜻입니다.

새 발견사항은 출처, 영향받는 정확한 build·commit·component, 심각도 근거, 재현조건, 민감하지 않은 증거 위치, 조치 담당과 기한을 기록합니다. 수정 뒤 같은 조건으로 재검증하고 evidence hash를 연결하기 전에는 `CLOSED`로 바꾸지 않습니다.

3. **격리:** 의심 세션·키·계정을 폐기하고 필요한 경우 신규 보행 세션을 차단합니다. 활성 사용자는 안전정지 절차로 종료합니다.
4. **보존·조사:** 로그·build·설정·hash를 읽기 전용으로 보존합니다. 원본 접근은 사건 범위와 승인자를 기록합니다.
5. **복구:** 검증된 정상 버전·키·backup만 사용하고 삭제 영수증을 먼저 다시 적용합니다.
6. **통지·후속:** 법률상 또는 사용자의 즉각 행동이 필요한 경우 대상자에게 정해진 기한 안에 알리고 원인·영향·재발방지를 기록합니다.

숨은 공용 비밀번호나 검증되지 않은 우회 경로는 사고 복구수단으로 사용하지 않습니다.

| 등급 | 판단 예 | 즉시 자동·수동 조치 | 종결 조건 |
|---|---|---|---|
| SEV-1 | 활성 사용자 안전 위해, 관리자 계정 탈취, 민감 원본 광범위 노출 | 신규 보행 차단, 영향 세션·키 격리, 증거보존, 책임자 호출 | 영향범위·원인·복구·필요 통지·재발방지와 재검증 완료 |
| SEV-2 | 제한된 권한·자료 노출 또는 핵심 기능 장애 | 영향 기능 격리, 확대 감시, 안전하지 않으면 전체 정지 | 수정·재검증과 잔여위험 승인 |
| SEV-3 | 사용자 안전과 민감자료에 직접 영향 없는 제한 장애 | 기록·우회·다음 업무시간 조사 | 원인·조치·회귀시험 연결 |

지원시간 밖에도 SEV-1 경보를 버리지 않고 자동 안전조치와 증거보존을 수행합니다. 실제 연락수단·당직·법정 통지시간은 운영 전에 지역·서비스 의무를 확인해 승인하고, 현재 준비되지 않은 채널을 운영 중이라고 쓰지 않습니다.

### 2026-07-27 연락·지휘·통지·훈련 보완

#### 현재상태와 발동

- 기록 기준일 현재 이 문서에 연결된 실제 production 배포나 확인된 보안사고 기록은 없습니다. 이는 `NO_CONFIRMED_INCIDENT_RECORD_AT_AUTHORING_TIME`이며 사고가 절대 없었다는 보증이 아닙니다.
- 실제 사고 처리, 사용자·기관 통지, production 복구를 수행했다고 주장하지 않습니다.
- 의심 사건은 개인정보 노출, 계정·session 탈취, secret 노출, 비인가 관리자 작업, 안전기능 변조·중단, 원본 queue 유실·과다보존, audit 훼손 또는 외부 신고가 접수되면 발동합니다.

#### 1인 프로젝트 지휘와 연락

| 기능 | 현재 담당 | 사고 중 책임 |
|---|---|---|
| Incident Commander·제품 결정 | 프로젝트책임자 김민호 | 등급 확정, 서비스·시험 중지, 외부 통지 판단 승인 |
| 보안·개인정보 대응 | 보안·개인정보책임자 김민호 | 격리, 영향범위, 증거보존, 개인정보 영향 분석 |
| 기술 복구 | 기술책임자 김민호 | key·session 폐기, 정상 build·설정 복원, 회귀검증 |
| QA·기록 | QA책임자 김민호 | 사건 timeline, 조치 확인, 종료조건과 postmortem 기록 |

한 사람이 여러 기능을 맡는 사실을 숨기지 않습니다. 각 기능별 판단 시각·근거·행동을 사건 기록에서 별도 행으로 남겨 자기승인 위험을 보완합니다. 외부 독립성이 필요한 개인정보·법률 판단은 즉시 결론내리지 않고 `REVIEW_REQUIRED`로 표시합니다.

실제 연락처·복구코드는 Git에 기록하지 않습니다. 내부 최초 연락은 프로젝트에서 이미 사용하는 직접 연락 채널을 사용하고, 외부 신고자는 배포 전에 설정할 개인정보 권리요청 URL을 사용합니다. 운영 연락 채널 ID `SEC-CONTACT-PRIMARY`와 백업 복구 채널 ID `SEC-CONTACT-RECOVERY`의 실제 값·접근권한·시험 영수증은 Git 밖 통제 저장소에 두어야 합니다. 김민호가 최초 실제 사용자시험 전에 이를 provisioning하고 분실 복구훈련에서 확인하며, 미완료 시 `GATE-SINGLE-ADMIN-RECOVERY-DRILL`이 사용자시험을 차단합니다.

|---|---|---|

위 시간은 내부 대응 목표이며 법정 통지기한이나 외부 SLA를 대신하지 않습니다. 지원시간 밖에는 가능한 자동 차단·증거보존을 먼저 수행하고 담당자가 확인하는 즉시 timeline을 이어갑니다.

#### 격리·증거·복구 규칙

1. 유출 의심 secret·session은 원문을 복사하지 않고 fingerprint와 폐기 시각을 기록합니다.
2. 영향을 받은 Android build, backend build, model, config, DB migration과 정책 version을 사건 기준선으로 고정합니다.
3. log export는 최소권한 read-only 위치에 보존하고 수집자·시각·source·SHA-256·보존기한을 chain-of-custody에 기록합니다.
4. 정확 위치·영상·음성 원본은 사건에 필요한 최소 범위만 별도 통제 저장소에서 열람하고 Git·일반 issue에 첨부하지 않습니다.
5. 복구는 검증된 정상 형상, 새 secret·session과 필요한 삭제 receipt를 사용합니다. 원인과 격리 범위가 불명확하면 안전기능을 자동 재개하지 않습니다.
6. 사용자 앱 재개는 기술 복구, 개인정보 처리상태, 핵심 회귀시험과 사용자 안전정지 해제가 모두 확인된 뒤 명시적으로 수행합니다.

#### 훈련과 postmortem

|---|---|---|---|

훈련은 실제로 실행한 날짜·참여자·입력 형상·관찰 결과·미달 항목·재시험을 별도 evidence로 남길 때만 완료 처리합니다. 실제 사고와 SEV-1/2 훈련은 5영업일 안을 내부 목표로 blameless postmortem 초안을 작성하고, 재발방지 action마다 소유자·기한·검증방법을 지정합니다.

이 보완으로 SEC-17 대응계획의 제출 내용은 작성됐습니다. 실제 incident, 연락 채널 provisioning, 훈련, 법률 통지 검토 또는 production 승인 완료를 주장하지 않으며 기존 2026-07-22 승인 snapshot과 seal 이력은 변경하지 않습니다.

정책 artifact는 `IN_SCOPE_DRAFT`, 외부 신고 channel은 `NOT_OPERATIONAL`입니다. 공개 beta 전에 다음 schema와 실제 channel 결속을 승인해야 하며 주소·SLA를 임의 생성하지 않습니다.
