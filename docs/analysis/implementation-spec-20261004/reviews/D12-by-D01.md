# D12 관리자 앱 명세 독립 표본 검토 — D01

[판정]

- 7개 핵심 기능과 대응 정책·8개 Mermaid 원본을 코드와 대조했다. 문서 보완 4건 및 후속 도표 노드 충돌 1건을 작성자가 수정했고 영향 부분을 재확인했다. 이번 표본에서 미해결 필수 문서 수정 사항은 없다.
- 제품 실행·테스트·빌드·APK·기기·실제 서버 검증은 수행하지 않았다. Mermaid는 원본 흐름과 조건만 읽었으며 렌더 결과 검증은 Root 범위다.
- 45개 기능 전체의 정확성·누락 없음 또는 관리자 운영 기능의 배포 활성화를 보증하지 않는다.

[수정 요청과 재확인]

- RV-D12-D01-01 · 문서 진입조건/도표 오류 · 해결: F019에 `현재 검수 draft가 APPROVED`일 때만 grant 요청이 가능함을 추가했다. 서버 기존 판정이 APPROVED라는 뜻과 구분했다. 기존 정상표시→무조건 cleanup→승인 사용으로 오해할 수 있던 도표를 정상 확인 경로와 별도 lifecycle cleanup으로 나눴다. 근거 `AdminBoundaryActivity.java:1995-2000,2131-2241`.
- RV-D12-D01-02 · 문서 시점 정확화 · 해결: F015의 background에서 pending 허가 제거 표현을 수정했다. `suspendForBackground:289-295`는 generation·lock을 바꾸며 `resumeLocalSession:308-327`가 clear한다. 실행 중 작업이 stale로 끝날 때 `LocalOperation.close:450-453`도 clear할 수 있지만 단순 background 즉시 메모리 소거와는 다르다.
- RV-D12-D01-03 · 필수 입력정책 누락 · 해결: F038/P038에 reason1..500, expectedRevision≥0, canonical UUID idempotencyKey, 선택 TRAINING revision과 정확 일치 조건을 추가했다. 근거 `AdminRawCollectionModels.java:145-155`, `AdminBoundaryActivity.java:4907-4911`.
- RV-D12-D01-04 · 허용 ID 범위 누락 · 해결: F004/P004에 대소문자 무관 `-shared` 접미사 거부를 추가했다. regex를 통과해도 추가 거부가 존재한다. 근거 `AdminSecurityHttpClient.java:1175-1183`.
- RV-D12-D01-05 · 후속 도표 노드 충돌 · 해결: F038에 보강한 입력검증 노드 `C`가 기존 중단 경계 `C`를 재정의하던 것을 `INPUT`으로 분리했다. 수정 원문에서 서로 다른 라벨·edge를 확인했다. 제품 코드 문제는 아니다.

[기존 관찰과 실행 한계]

- 기존 R-D12-007/D14 R8의 재인증 이후 `step_up_verified_at` 전달 단절 가능성은 F015 notes에 이미 명시되어 있다. 이 검토는 클라이언트 호출 순서를 확인했으며 서버 D14/D09 경로를 재검토하거나 403을 동적으로 재현하지 않았다. 해결된 제품 결함이라고 처리하지 않는다.
- release 운영 기능 false는 정적 설정 사실이다. 앱 KeyStore/PIN, 토큰 실제 발급, 보호 API, FLAG_SECURE, 파일 저장·삭제, 원본 이미지 표시, 학습 증거의 실물 적합성은 이번에 실행·관찰하지 않았다.
- 테스트 파일의 존재나 기존 기록을 이 검토의 실행 결과로 세지 않았다.

[미검토]

- 나머지 F002-003, F005, F007-014, F016-018, F020-030, F032-037, F039-045는 기능 단위 독립검토를 수행하지 않았다. 일부는 위 표본의 공유 helper로 읽었지만 검토 완료 범위로 확대하지 않는다.
- 보안·복구·기기키 회전·proof parser·전체 HTTP client·SAF·검수/전달 미확정 journal·삭제후속·사고·감사·접근성·텔레메트리의 모든 분기, 전체 테스트, 서버 권위 구현, 모든 추가 state/sequence 도표는 미검토다.
- Mermaid 렌더/시각 회귀 및 최종 Markdown 연결 검증, 전체 분야 통합·완료 판단은 Root가 담당한다.
