Gateway 연결 실패 크래시

서버에 닿지 않으면 첫 실행에서 앱 프로세스가 종료된다. 단위 테스트 1,012건이 모두 통과하는 상태에서 에뮬레이터 실행으로만 드러난 결함. 같은 패턴이 로그인 경로에도 있어 함께 고쳤다. 2026-08-19 발견·수정, 커밋 606abe2.

증상

debug APK를 설치하고 실행하면 화면이 뜨지 않고 프로세스가 사라진다. Gateway 서버를 띄우지 않은 상태에서 100% 재현된다.

원인

첫 실행 통합 동의 요청이 백그라운드 실행자에서 Gateway를 호출하는데, 예외를 두 가지만 잡았다.

gatewaySessionExecutor.execute {
    try {
        val confirmation = call.execute()
        ...
    } catch (_: CancellationException) {
    } catch (_: RuntimeException) {     // ← 여기까지만
    }
}

실제로 던져지는 예외의 계층은 이렇다.

ConnectException→ SocketException→ IOException→ Exception

IOException은 checked exception이라 RuntimeException이 아니다. 두 catch 어디에도 걸리지 않고 실행자 스레드의 uncaught handler로 올라가 프로세스를 죽인다.

HTTP 오류는 왜 괜찮았나 IntegratedConsentHttpException과 GatewaySessionHttpException은 둘 다 IllegalStateException을 상속한다. 즉 RuntimeException 계열이라 잡혔다. 서버가 4xx·5xx를 주는 경우는 처리됐고, 서버에 닿지 못하는 경우만 빠져나갔다. 그래서 서버를 띄운 환경에서는 드러나지 않는다.

수정

MainActivity.startIntegratedConsentRequest의 catch 한 곳을 넓혔다. 처리 로직은 건드리지 않았다.

- } catch (_: RuntimeException) {
+ } catch (_: Exception) {

기존 RuntimeException 블록이 이미 올바른 fail-closed 처리를 하고 있었기 때문에 본문을 새로 쓸 필요가 없었다. 재시도 표시, UI 갱신, integratedConsent=blocked:server_confirmation_failed 상태, 그리고 "동의 선택 저장에 실패해 새 허용 항목을 열지 않습니다" 음성 안내가 그대로 IOException에도 적용된다.

CancellationException catch가 앞에 있으므로 취소 경로의 동작은 바뀌지 않는다.

같은 계열의 두 번째 결함 — 함께 수정

onGatewaySessionButtonClicked(MainActivity.kt:6962)가 동일한 패턴을 갖고 있었다.

  • 실행자 블록 안에서 gatewaySessionClient.login(과 logout(을 호출한다
  • catch는 RuntimeException과 RejectedExecutionException 둘뿐이었다
  • GatewayFieldSession.login() 안에는 catch가 0개이고, HTTP 오류만 GatewaySessionHttpException으로 감싼다

같은 방식으로 catch를 Exception까지 넓혔고, 되돌려 확인하는 절차도 동일하게 거쳤다.

런타임 재현은 하지 못했다 에뮬레이터에서 GATEWAY 로그인 버튼을 눌러 재현을 시도했으나 크래시가 나지 않았다. login()이 소켓 작업 전에 actorId를 먼저 검증해 invalid_named_actor를 던지는데, 이는 RuntimeException 계열이라 기존 catch에 걸린다. 서버 없는 첫 실행 상태에서는 유효한 actor id를 갖출 수 없어 실제 연결 시도까지 도달하지 못했다. 이 수정의 근거는 정적 경로 분석이며 런타임 증거가 아니다. 첫 번째 결함과 달리 "고쳤더니 안 죽더라"를 확인하지 못했다.

MainActivity에 catch (_: RuntimeException)이 8곳 남아 있다. 네트워크를 감싸는 것은 없고 JPEG 인코딩·저널·큐 정리 등 파일·메모리 작업이라 별도 판단이 필요하다.

왜 단위 테스트로 못 잡았나

이 결함이 있는 상태에서도 단위 테스트 1,012건이 전부 통과했다. MainActivity는 JVM에서 인스턴스화되지 않아 소스 텍스트 검사로만 검증되는데, 기존 검사 중 어느 것도 catch 절이 다루는 예외 계층을 확인하지 않았다.

실기기·에뮬레이터에서 실제로 실행해야만 드러나는 종류다. 이번 회귀 테스트는 소스 텍스트 방식이라 같은 함수의 재발만 막는다. 다른 실행자 블록에 같은 실수가 생기는 것은 여전히 막지 못한다.
