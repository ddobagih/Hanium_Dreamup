## 브랜치와 파일 소유

새 작업 폴더에서는 다음처럼 출발할 수 있다. 이미 작업 중인 폴더에서는 먼저 변경분을 보존하고 `temp`를 가져온다.

```bash
git clone --branch temp https://github.com/ddobagih/Hanium_Dreamup.git
cd Hanium_Dreamup
# 사용자
git switch -c work/part-a-walking
# 팀원은 자기 폴더에서 work/part-b-services 사용
```

- 두 담당은 각자 브랜치에서 작은 ID 묶음을 구현하고 `temp`에 순차 통합한다. 동시에 같은 `temp`에 직접 변경을 밀어넣지 않는다.
- 사용자 A가 `MainActivity.kt`를 단독 수정한다. 팀원 B의 계정·음성·신고 연결은 ID, 입력/결과 계약, 호출 지점, 최소 패치, 확인 방법을 A에게 전달한다. ID의 주담당은 B로 유지한다.
- A: `device`, `depth`, `inference`, `feedback`, 보행·위치·방향 navigation. B: 계정·네트워크·음성 입력·신고·RAW·암호화·서버·관리자. session/navigation의 세부 예외는 각 파트에 명시했다.
- 공통 `app/build.gradle.kts`, `AndroidManifest.xml`, 모델 설정·asset 배치·CI·검증 스크립트는 B가 단독 수정한다. A는 필요한 변경을 요청한다.
- 같은 컴퓨터·같은 checkout이면 Android 빌드는 한 번에 하나만 실행한다. 서로 다른 컴퓨터의 별도 checkout은 각자 빌드할 수 있다.
- 운영 키·개인 데이터·현장 원자료는 별도로 보관한다. `work/`의 로컬 임시 빌드·시험 자료를 통째로 커밋하지 않는다.

## 단계와 검증

| 단계 | 할 일 | 확인 방법 |
|---|---|---|
| 1. 작은 묶음 선택 | 원문·현행 코드·최신 잔여 대조. 미정합은 결함/조건부/이미 해결/해당 없음 분류부터 수행 | 해당 ID의 성공 조건과 실제 반례 또는 적용하지 않는 근거 확보 |
| 2. 기능 개선 | 같은 원인의 ID만 묶어 최소 수정, 파일 소유와 양쪽 계약 합의 | 동일 반례 재실행, 정상·거부·복구 경로 직접 시험 |
| 3. 연결 | B provider/API/schema → 각 담당 모듈 → A Main/출력/보행 런타임 | 실제 consumer/provider 호출과 취소·계정/보행 전환·늦은 응답 시험 |
| 4. 통합 | 필요한 독립 검토·인접 회귀·APK 확인, 작은 묶음을 temp에 반영 | 기존 실패 대비 신규 실패 구분, 결과와 소스 기준 기록 |
| 5. 필수 실제 검증 | 원문상 필요한 기기·현장·SMTP/TMAP·운영·복구 증거 확보 | 환경·기기·입력·기대·실제 결과를 남김. 없으면 PARTIAL 유지 |
| 6. 상태 반영 | 각 담당이 완료 후보와 근거를 제출하고 통합 담당이 원장/집계를 함께 반영 | ID 중복/누락과 성공 조건 충족 확인. 표의 상태만 바꿔 완료 처리하지 않음 |

각 묶음은 `ID / 기준 커밋·파일 / 실제 변경 / 직접 시험 / 독립 검토 / 미검증·잔여 / 다음 작업`으로 인계한다. 기능 원장과 정식 시험·출시 기록은 별개다. 과거 Goal graph·불변 gate 자료는 이번 협업 준비를 이유로 재작성하지 않는다.
