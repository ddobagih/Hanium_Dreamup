## 핵심 원칙

이 앱의 실제 주 사용자는 화면을 계속 보는 사용자가 아니다. 카메라 프리뷰와 bbox는 데모, 저시력 사용자, 모델 디버깅에는 필요하지만 핵심 인터페이스는 음성 안내, 진동, 스크린리더, 큰 터치 영역이어야 한다.

따라서 Figma UI는 아래 질문에 통과해야 한다.

1. 카메라 화면을 보지 않아도 현재 위험 상태를 알 수 있는가?
2. 스크린리더만으로 음성 안내 켜짐/꺼짐, 위치 상태, 신고 가능 여부를 알 수 있는가?
3. 위험 발생, 신고 성공, 신고 실패가 `aria-live` 또는 TTS/haptic으로 전달되는가?
4. 모델 미구현/fake 상태를 실제 보행 안전 기능처럼 오해하게 만들지 않는가?
5. 관리자 화면보다 보행자용 첫 화면이 명확히 우선인가?

## PDF에서 가져와야 할 아이디어

프로젝트 PDF의 원래 아이디어는 단순 카메라 앱이 아니다. 다음 요구를 UI 기준에 반영해야 한다.

- 스마트폰 카메라와 센서로 1인칭 시점의 보행 위험을 실시간 감지한다.
- 점자블록 파손/단절, 방치 킥보드/자전거, 공사 장애물, 포트홀 같은 실제 보행 위협을 우선한다.
- 화면 직접 조작이 어려운 상황을 전제로 STT/TTS 기반 음성 인터페이스를 지향한다.
- IMU/GPS로 사용자의 이동 방향과 위치 정확도를 보조하고, 충돌 가능성이 높은 위험만 안내해 인지 과부하를 줄인다.
- 불량 인프라 감지 시 이미지, 위치, 센서 정보를 신고 데이터로 축적한다.
- PWA는 설치 부담을 줄이고, 저신호 환경에서도 기본 동작을 유지해야 한다.

2026-05-12 당시 1차 구현은 모델과 STT가 완성되지 않았으므로, Figma에서는 이 기능들을 실제 완료 기능처럼 보이면 안 됐다. 대신 `모델 연결 대기`, `음성 명령 준비 중`, `데모 탐지`처럼 상태를 명확히 분리했다.

## 현재 Figma v3에서 괜찮은 점

- 첫 화면이 마케팅 랜딩이 아니라 보행 보조 화면이다.
- `WalkSafe Assist`, 현재 위험 상태, GPS, 방향, 음성 토글, 신고 버튼이 한 화면에 모여 있다.
- 신고 버튼과 음성 토글이 큰 터치 영역으로 보인다.
- `DEMO` 표기가 작아져서 fake detector가 과도하게 제품 기능처럼 보이지 않는다.
- Figma AI 로그 기준으로 위험 배너 `aria-live`, 음성 토글 피드백, report snapshot, GPS 위도/경도 표시, 카메라 `aria-hidden` 문제를 수정한 것으로 보인다.
- 색상은 위험/안전/상태 의미가 어느 정도 분리되어 있다.

## 반드시 보완할 점

### 1. 음성 우선 구조가 더 명확해야 한다

현재 화면은 시각적으로는 정돈되어 있지만, 실제 사용자는 카메라 프리뷰와 bbox를 계속 볼 수 없다. 첫 화면의 의미 순서는 `위험 상태 -> 음성 안내 상태 -> 신고 가능 여부 -> 위치/방향 -> 카메라`가 되어야 한다.

Figma annotation에 아래 접근성 이름을 명시한다.

| 요소 | 접근성 이름 기준 |
| --- | --- |
| 위험 배너 | `현재 위험: 공사 장애물, 신뢰도 76퍼센트. 전방 주의.` |
| 안전 상태 | `현재 감지된 위험 없음. 탐지 대기 중.` |
| 음성 토글 | `음성 안내 켜짐` 또는 `음성 안내 꺼짐`, `aria-pressed` 포함 |
| 신고 버튼 ready | `현재 위험 신고. 공사 장애물, 신뢰도 76퍼센트.` |
| 신고 버튼 disabled | `현재 위험 신고 불가. 감지된 위험이 없습니다.` |
| GPS 상태 | `위치 수신됨. 정확도 약 8.5미터.` 또는 `위치 권한 필요. 위치 없이 신고 가능.` |
| 카메라 장식/bbox | 스크린리더에서 반복 낭독되지 않게 숨김 |

### 2. 카메라 프리뷰는 필요하지만 주 신호가 아니어야 한다

카메라 화면은 모델 입력과 저시력/데모 확인에 필요하다. 하지만 시각장애인용 앱에서는 bbox 위치를 읽는 것보다 “무슨 위험인지, 어느 방향을 조심해야 하는지, 지금 신고할 수 있는지”가 더 중요하다.

수정 기준:

- bbox 라벨보다 위험 상태 배너와 TTS 문구가 우선이다.
- 카메라 loading/error 텍스트는 시각적으로만 보이지 말고 스크린리더 live region에도 들어간다.
- 카메라 프리뷰가 실패해도 사용자가 현재 앱 상태와 다음 행동을 알 수 있어야 한다.

### 3. `/admin` 진입은 보행자 화면에서 낮은 우선순위여야 한다

Figma Make 미리보기에서 `관리자` 링크를 눌렀을 때 `/admin` route가 안정적으로 관리자 화면으로 전환되는지 확인되지 않았다. 보행자용 MVP에서는 관리자 화면이 있더라도 메인 화면의 핵심 조작보다 눈에 띄면 안 된다.

수정 기준:

- `/admin` route가 실제로 관리자 화면을 렌더링하는지 확인한다.
- route가 불안정하면 메인 화면에서 `관리자` 링크를 제거하고, 구현 단계에서 별도 URL로만 접근한다.
- 관리자 화면은 발표/운영 검증용이며 보행자 사용 흐름보다 우선하지 않는다.

### 4. 신고와 재연결 버튼의 사고 터치를 줄여야 한다

보행 중 사용자는 손이 흔들리고 화면을 정확히 보기 어렵다. `현재 위험 신고`는 하단 큰 버튼으로 유지하되, `카메라/센서 재연결`은 신고 버튼과 시각적으로 너무 비슷하거나 너무 가까우면 안 된다.

수정 기준:

- 신고 버튼은 primary action으로 유지한다.
- 재연결은 secondary action으로 분리하고, 위험 신고와 혼동되지 않게 낮은 강조도를 사용한다.
- 신고 불가 상태에서는 비활성 이유를 버튼 내부 또는 바로 아래에서 읽을 수 있어야 한다.

### 5. 상태 variant를 더 많이 남겨야 한다

정상 화면 하나만 예쁘게 만들면 구현 중 접근성 결함이 생긴다. Figma에는 최소한 아래 상태 frame 또는 component variant가 있어야 한다.

| 상태 | 필수 여부 |
| --- | --- |
| 정상 대기 | 필수 |
| 위험 감지 | 필수 |
| 음성 안내 꺼짐 | 필수 |
| 카메라 준비 중 | 필수 |
| 카메라 권한 거부 | 필수 |
| GPS 대기/거부 | 필수 |
| 모델 연결 대기 | 필수 |
| 신고 전송 중 | 필수 |
| 신고 성공 | 필수 |
| 신고 실패 | 필수 |
| 관리자 목록 | 선택 |
| 관리자 상세 | 선택 |

### 6. fake detector 상태는 더 엄격히 분리해야 한다

모델 학습 중인 현재 단계에서 fake detector는 UI/API 연결 확인용이다. 실제 보행 안전 판단, 성능 수치, 최종 시연의 정확도 근거로 쓰면 안 된다.

수정 기준:

- 시각 표기는 작은 `DEMO`로 충분하다.
- 스크린리더에는 `데모 탐지 모드`라고 읽히게 한다.
- 신고 데이터의 `source`는 `fake`로 유지한다.
- Figma 화면에 `AI가 실제로 위험을 감지했습니다`처럼 오해 가능한 표현을 쓰지 않는다.

## Figma AI에 다시 줄 수정 프롬프트

```text
docs/design/figma_ui_handoff.md, docs/design/DESIGN.md, docs/design/figma_make_accessibility_review.md 기준으로 현재 WalkSafe Assist 버전 3 UI를 수정해줘.

가장 중요한 점은 이 앱이 시각장애인/저시력 보행자가 쓰는 웹앱이라는 거야. 화면은 보조이고, 실제 핵심 인터페이스는 TTS 음성 안내, 진동, 스크린리더, 큰 터치 영역이야.

수정 기준:
1. 첫 화면의 정보 우선순위를 위험 상태 -> 음성 안내 상태 -> 신고 가능 여부 -> 위치/방향 -> 카메라 순서로 재정리해줘.
2. 카메라 프리뷰와 bbox는 유지하되, 스크린리더가 카메라 장식 요소를 반복해서 읽지 않게 annotation을 남겨줘.
3. 위험 배너는 role="alert", aria-live="assertive" 기준으로 설계하고, 안전/GPS/신고 상태는 aria-live="polite" 기준으로 설계해줘.
4. 음성 토글은 aria-pressed 상태와 "음성 안내 켜짐/꺼짐" 피드백이 명확해야 해.
5. 현재 위험 신고 버튼은 disabled/ready/submitting/success/error 상태를 모두 만들어줘. disabled 상태에는 왜 신고할 수 없는지 문구가 있어야 해.
6. 카메라 권한 거부, GPS 권한 거부, 모델 연결 대기, 신고 실패 상태 frame을 따로 만들어줘.
7. /admin 화면이 실제로 보이는지 확인해줘. 불안정하면 보행자 메인 화면에서 관리자 링크를 눈에 띄게 두지 말고 별도 route로만 접근하게 해줘.
8. 모델은 아직 학습 중이므로 fake detector를 실제 AI 탐지 완료처럼 표현하지 말고 "DEMO"와 "데모 탐지 모드"로 분리해줘.
9. 화면 문구는 한국어로 유지하고, 터치 영역은 최소 48px, 주요 신고 버튼은 64px 이상으로 잡아줘.
10. 장식용 hero, gradient blob, 제품 소개 섹션은 넣지 마. 이건 랜딩 페이지가 아니라 보행 중 쓰는 안전 도구야.
```

## 구현 인계 기준

Figma 수정본을 코드로 넘기기 전에 아래를 확인한다.

1. VoiceOver/TalkBack 순서에서 위험 상태와 신고 버튼이 카메라 장식보다 먼저 읽힌다.
2. 위험 발생 시 한 번만 강하게 알리고, 같은 위험 반복에는 쿨다운이 있다.
3. 음성 안내를 끄면 더 강한 진동 또는 화면 상태로 보완한다.
4. **[HISTORICAL - 현재 폐기]** GPS가 없어도 신고 흐름은 막지 않고 `missing_location` 같은 운영 플래그로 넘긴다.
5. 신고 버튼을 누르는 순간의 탐지 이벤트 snapshot을 사용한다.
6. `POST /reports`에 필요한 `metadata`와 `image` 흐름이 화면 상태와 맞다.
7. 모델 미연결 상태는 오류가 아니라 `모델 연결 대기`로 보인다.
8. 관리자 화면은 업무형 신고 검토 화면이고, 보행자용 첫 화면보다 우선하지 않는다.

현재 v2 정책에서는 GPS가 없으면 신고를 저장하지 않는다. 위 4번은 Figma v3 당시 제안으로만 보존하며 구현 기준으로 재사용하지 않는다.
