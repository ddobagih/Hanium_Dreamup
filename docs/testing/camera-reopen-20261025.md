## 카메라 부하 수정 당시 코드에서 확인한 점

- 기기점검 결과와 CPU/GPU 선택 기록은 별도다. 저장 점검 결과를 복원하는 경로가 CPU/GPU 속도 비교를 매번 다시 실행하는 구조는 아니다.
- 현재 기기의 선택 기록은 `baseline_rejected`, CPU 4 threads다. 이는 CPU/GPU 속도 비교 성공 기록이 아니다. 원래 기록을 만든 APK·불일치한 개별 시험 영상은 이 기록만으로 알 수 없다.
- 최초 점검은 홈 진입 전에 모델 준비를 기다리고, 저장 결과 복원은 홈 진입 뒤 비동기 모델 준비를 시작할 수 있다. 이 차이가 심한 지연을 일으키는지는 실제 홈 조건에서 추가 확인해야 한다.
- 수정 전 카메라 테스트 화면은 동시 추론만 막고, 완료 뒤 다음 프레임의 추론을 즉시 시작했다. 기존 측정 시간 기반 `AdaptiveInferencePacingPolicy`를 재사용해 작업 사이에 여유 시간을 두었다. 이미지 미획득·큐 거절·예외·세대 전환의 티켓 반납을 연결하고, 이미지 반납이 실패해도 `busy`를 해제하도록 했다. 센서 기준·모델·CPU/GPU 선택·기존 품질 검사는 유지했다.
- 정책이 기록하는 전체 작업 시간은 캡처·큐 대기·전처리·추론·worker 완료까지다. Main 화면의 실제 게시·렌더 완료 지연을 측정한 값은 아니다.
