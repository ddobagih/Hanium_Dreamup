## Two device APIs disagree with themselves on this handset

- `ArCoreDepthCapabilityDeviceTest` on SM-A716S: `availability=SUPPORTED_INSTALLED`,
  `declaredDepthFeature=false`, `automaticDepthSupported=true`. The `com.google.ar.core.depth`
  system feature is not declared while a live session supports depth, so the feature query is a
  false negative. Commit `37dd42c` had already removed that query; this is the measurement behind
  that change.
- The device check first failed with `KOREAN_TTS_UNAVAILABLE`. Added
  `KoreanTtsVoiceInventoryDeviceTest` to find out why: the default engine `com.samsung.SMT` answers
  `setLanguage(ko)=0` (available) while exposing **zero** Korean `Voice` objects, and still exposed
  zero after the user updated its Korean voice data to "최신 버전". `com.google.android.tts` on the
  same handset exposes 9 Korean voices, 5 of them offline. The probe reads only the system default
  engine, so the check blocked a phone that had usable offline Korean speech installed.
- Setting `tts_default_synth` to Google let the check pass. That is a workaround, not a fix: the
  probe has no fallback to another installed engine. Recorded as out of scope in the design; the
  device setting can be reverted with `adb shell settings delete secure tts_default_synth`.
- The two findings are mirror images — ARCore's feature flag is a false negative, Samsung's
  `setLanguage` a false positive. A single API answer is not evidence of device capability.

## Device check judged against what it actually measures

- Enumerated what the check proves. Of five measured items only the wake phrase (real user speech,
  per-word Vosk confidence ≥ 0.60) and Korean TTS (real WAV synthesis, offline voices only) prove
  what they claim. GPS accepts 100 m against the walk gate's 15 m and does not block at all; the
  camera passes on one frame of five with no latency ceiling; device resources read system booleans
  and admit `SEVERE` thermal throttling. Distance is confirmed as API support only
  (`evidence=DEPTH_API_SUPPORT_ONLY`), with the real measurement deferred to walk start.
- Decided the product policy: an unapproved device gets nothing but re-measurement. The present
  `LIMITED` fallback is a testing convenience. Re-measurement stays available while unapproved,
  which is what makes approval evidence collectable at all.
- Corrected an error in my own framing during the discussion. Per-model human field measurement is
  not a prerequisite; the app is the instrument and the human signs. What cannot be automated is
  the risk decision, not the measurement. The device check therefore precedes approval rather than
  following it.
- Wrote `docs/superpowers/specs/2026-09-08-device-check-threshold-tightening-design.md` with the
  target values and where each is borrowed from: GPS 100 m → 15 m from the official environment
  profile, one-frame-of-five → ten frames at 80 % from `RuntimeMetricPreflight`, thermal `CRITICAL`
  → `SEVERE` from the already-computed `thermalThrottled`, TTS output existence → minimum duration.
  Nothing in it was measured; the value changes wait for a connected device and land together.

## Release now refuses unapproved runtime safety thresholds

- `WalkRuntimeSafetyCoordinator.productionThresholdProfile` is `null`, so `FRAME_AGE_EXCEEDED` and
  `INFERENCE_LATENCY_EXCEEDED` cannot fire. Ten of the twelve safe-stop causes are
  threshold-independent and still latch.
- The fail-open is deliberate and locked by
  `productionProfileAllowsSafeTestFlowWithoutApprovedTimingThresholds`, which asserts that
  `inferenceLatencyMs = Long.MAX_VALUE` still allows output. Left that behaviour alone: the two
  thresholds are derived from walking speed, hazard distance and reaction time, and enforcing an
  invented number would be worse than enforcing none.
- What was wrong is that the gap was silent. `configured` exists and no product code reads it, and
  the build said nothing, while a release already refuses to exist without a gateway origin.
- Added `validateWalkSafeRuntimeSafetyThresholds` on `preReleaseBuild`. It reads the same
  declaration the runtime reads, so filling the value releases the guard with no second edit.
  Verified by running `assembleRelease` and watching it fail with the intended message, and
  `assembleDebug` still succeeds. Full `testDebugUnitTest`: 2017 tests, 12 failures, all of them
  the existing macOS `AndroidReportQueueStoreTest` baseline; no new failures.
- The threshold numbers themselves stay `[NOT_APPROVED: 추론 지연 상한]`. The user declined to set
  them now because recognition latency varies with conditions; that discussion is deferred.
