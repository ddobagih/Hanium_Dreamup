## Every voice command was dead on this handset while 2113 unit tests passed

- The platform recogniser returns confidence 0 here, so `selectAndroidVoiceAction` always declines
  (`MIN_VOICE_CONFIDENCE = 0.55`) and `assessPlatformVoiceCandidate` is the only path a command can
  act through. That is the designed compensation, not a fault.
- That policy required one to three hypotheses because the HOME intent asks for three.
  `EXTRA_MAX_RESULTS` is a hint Android never promised to honour and Google returns four on this
  device, so a correctly recognised "도움말" was discarded before agreement was examined:
  `FINAL_RECEIVED confidence=ZERO result_count=4`, `COMMAND_CANDIDATE_PARSED matched=true`,
  `PLATFORM_CANDIDATE_POLICY disposition=INVALID_FINAL`.
- Removed the upper bound. The rule worth keeping is "never claim agreement while discarding
  alternatives", and the agreement check already enforces it over however many hypotheses arrive, so
  a fourth one raises the bar rather than invalidating the answer. Hypotheses that never reach us
  are still reported by `hasAdditionalAlternatives`.
- Naming a dish was answered with "음성 후보를 하나로 확정하지 못했습니다", which describes hypotheses
  that disagree. Nothing had disagreed and nothing had parsed, so the walker is told that repeating
  themselves may work. Split that case out as `UNRECOGNIZED` and joined it to the state-aware hint
  added this morning; that hint had been added to the branch this device never takes.
- Verified both ways on the device after rebuilding: 도움말 → `PREVIEW_ONLY matched=true`, help
  spoken; 김치찌개 → `UNRECOGNIZED matched=false`, "못 알아들었습니다. 목적지를 말하거나 도움말이라고
  말씀해 주세요." Commit `0c4103c`.
- `PlatformVoiceCandidatePolicyTest` asserted four agreeing hypotheses were `INVALID_FINAL`. That is
  the third existing test today to have recorded a defect as a contract, after the mounting wording
  and the walk-control spacing. All three described what the code did, not what the device does.

## A one-time permission grant locks the app shut permanently

- Not fixed. After a reinstall the app showed `앱 실행 불가` on every launch.
  `dumpsys package` showed location, camera and microphone `granted=false, flags=[... ONE_TIME]`:
  the grants were "이번만 허용", which Android revokes when the process ends.
- `requestInitialAppEntryPermissionsIfNeeded` (`MainActivity.kt:18647`) returns early whenever
  `PREF_INITIAL_APP_PERMISSION_REQUEST_COMPLETED` is set, checking the permissions but never asking
  for them again. The flag intends to record "we asked"; what it records is "they were granted",
  and a one-time grant separates the two. The dialog says "앱을 다시 실행한 뒤 모든 필수 권한에
  동의해 주세요" while restarting is exactly what removes the chance to agree.
- Recovered by granting from Android settings, which is not a route a blind walker can be expected
  to find from a dialog that names no setting. Same shape as the `새 경로 요청` defect fixed this
  morning: the app asks for something it will not then accept.

## Other findings left open

- On a zero-confidence handset every command outside the preview set resolves to
  `CONFIRMATION_REQUIRED`, so 길안내 종료, 신고해 and 다음 안내 알려줘 need the screen. Refusing to
  end navigation on an unscored transcript is defensible; requiring sight to do it is the part worth
  a decision.
- The explicit-report disclosure is 126 characters and names "운영 문안 승인 전 빌드에서 승인한
  WalkSafe 테스트 서버", which is artifact-management state rather than anything a walker can act
  on. It is gated behind `BuildConfig.DEBUG && WALKSAFE_REPORT_QUEUE_ENABLED` so no release build
  speaks it. Rewording waits on a comparison with `RQ-FP-046-001` and the consent copy.
