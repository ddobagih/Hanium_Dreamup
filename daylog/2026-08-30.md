## 아직 막혀 있는 것 — 3단계 동의

- 서버 체인은 완성됐으나 **실제 온보딩은 여전히 3단계를 못 지난다**. `RQ-FP-010-001`이 동의(3)를
  가입(4)보다 앞에 두는데, 동의 저장은 Gateway 세션을 요구하고 세션은 4~8단계가 만드는 계정을
  요구한다. 순서 요구와 신원 요구가 서로를 막는다.
- 신원 관문은 네 겹이다. `currentReporterUserId()` → `gatewayLoginActorIdOrNull()` →
  `session.isUsableFor()` → `PermissionSessionPolicy.isAuthenticatedFor()`. 마지막 것을 `ACTIVE`로
  만드는 유일한 경로도 첫 실행 완료를 요구한다. 의도된 다층 방어다.
- 두 번 시도했고 두 번 되돌렸다.
  - 클라이언트 세션 요구 완화(`0a65a05`): Gateway가 이 제어면의 GET만 무인증으로 열고 PUT은 인증된
    field actor를 요구하므로 401 `gateway_auth_required`로 거부됐다. control secret은 쓰기에서
    세션을 대체하지 않는다. 조사 결과를 호출부 주석으로 남기고 가드는 복원했다.
  - 신원 fallback 2곳 완화: Gateway는 세션을 발급했으나 앱이 즉시 버렸다. 네 번째 관문 때문이다.
    동작하지 않는 인증 완화를 남기지 않으려고 전부 되돌렸다.
- 남은 안은 Gateway가 로그인 전 동의 PUT을 설치 단위로 결속하는 것이다. Gateway README가 이미 그렇게
  설계돼 있다고 적어놨으나 코드에는 없다. 다만 actor는 라우트 인가·원장 결속·백엔드 전달 세 곳에
  흘러가고, 특히 `syncConsentToBackend`가 actor assertion을 요구해 로그인 전에는 백엔드 전달도 막힌다.
  `installation_id`가 요청 본문에 있어 라우트가 본문을 읽어야 하는 구조 변경도 따라온다.
- **팀 확인 필요**: Gateway가 인증되지 않은 호출자를 대신해 설치를 actor로 백엔드에 보증해도 되는가.
  설치 제어비밀이 인증 역할을 하므로 논리는 서지만 신뢰 경계를 옮기는 판단이다.

## 규모 판단 실패 기록

같은 문제에서 네 번 연속 규모를 잘못 봤다. 매번 한 겹이 더 있었다.

1. 클라이언트 가드만 풀면 된다 → 서버가 401
2. Gateway 엔드포인트를 만들면 된다 → 3단계가 그대로 막힘
3. 함수 두 곳만 완화하면 된다 → 네 번째 관문
4. A-3는 한 분기다 → 세 곳 + 본문 파싱 구조 변경

이 저장소가 신원 없이 진행되는 것을 여러 겹으로 막도록 만들어져 있다. 다음에 이 경로를 건드릴 때는
한 겹을 확인했다고 끝났다고 보지 말 것.

## 추가 — 보행 화면 이식과 첫 실행 UI 개편

「다음 작업」 1번을 그대로 진행했다. 먼저 병합된 `runtimeControls`를 다시 실측했다. 팀이

`gatewayVoiceStatusText`가 늘어 release 기준 자식은 14개가 아니라 17개였다.

ver2와 코드가 어긋난 곳은 다섯이었다.

1. ver2가 「미정: 음성 명령 중 상태」로 비워 둔 자리를 팀의 `gatewayVoiceStatusText`가 이미 채웠다.
   미정 마커 대신 실물을 넣었다. 미정 5개 → 4개.
2. ver2 「음성 명령」은 코드에서 「서버 음성 명령」이다. 브리프 1순위 규칙대로 코드 문구를 남겼다.
3. 이탈 안내가 `contentDescription`에만 있어 눈으로는 보이지 않았다. warning 색 본문으로 내보냈다.
4. 보행 화면 버튼에는 WS 팔레트가 아예 걸려 있지 않았다. 색을 입히는 곳은 온보딩 헬퍼 한 곳뿐이었다.
5. `WS_COLOR_WARNING`이 없어 새로 넣었다. 나머지 색 토큰 5개는 실측값이 정확히 일치했다.

### 마감이 안 된 진짜 이유

첫 판은 구조만 옮기고 「이식 완료」라고 보고했는데, 화면은 여전히 초안과 딴판이었다. 원인은 테마다.
`android:style/Theme.Material`의 기본 버튼 드로어블이 인셋·각진 모서리·가운데 정렬을 함께 들고 오므로,
`backgroundTintList`만 바꾸면 낡은 버튼에 색만 칠한 것이 된다. 이 파일이 카드에 이미 쓰던
`GradientDrawable` 방식을 버튼에 가져오지 않은 것이 전부였다.

적용 지점도 틀렸다. 버튼은 헬퍼 40개와 맨손 `Button(this)` 30개, 두 갈래로 만들어져 있어 만드는
자리마다 손대면 반드시 빠지는 것이 생긴다. 이미 두 오버레이의 트리를 훑고 있는
`applyAccessibleControlDefaults` 한 곳에서 마감하도록 바꾸고, 낱개로 나열했던 목록은 지웠다.

- `CompoundButton`은 제외했다. `CheckBox`가 `Button` 하위라 네모난 버튼 면을 뒤집어썼다.
- 입력칸은 어두운 바탕에서 거의 보이지 않는 기본 밑줄 대신 테두리 있는 면으로 바꿨다.
- 여백을 아무도 지정하지 않은 세로 묶음에만 그룹 간격을 준다. 팀 계정 컨트롤이 붙어 있었다.
  휴리스틱이므로 천장을 `ponytail:` 주석으로 남겼다.

### 보행 화면

7구역 + 구분선, 짝을 이루는 행동은 2열, 주 행동은 80dp 반전 면이다. `navigationStatusText`는 지우지
않고 DEBUG 컨테이너로 옮겼다. 갱신 호출부가 19곳이라 표시 위치만 옮기는 편이 작다.

주 행동은 비활성일 때도 다른 버튼보다 밝게 둔다. 첫 실행 미완료·ARCore 확인 중이 대부분의 시간인데
공용 비활성 색을 쓰니 80dp짜리가 화면에서 가장 흐려져 크기로 만든 위계가 뒤집혔다. 에뮬레이터로
보지 않았으면 못 잡았을 것이다.

### 보행 화면이 자기 화면을 갖게 했다

`showVerifiedSurfaces = mayUseWalk || renderStage == COMPLETE` 때문에 보행이 가능해지는 순간
환경·장착·기기점검·우선사용자 교육이 영구히 화면에 남아, 보행 화면은 늘 긴 스크롤의 꼬리였다.
이제 `walkReadinessControls` 한 덩어리로 묶여 한 줄로 접힌다.

접기는 `walkSafetyOutputsAllowed() && isStartupCapabilityConfirmed()`가 모두 참일 때만 제안한다.
하나라도 보행을 막고 있으면 펼친 채 두고 토글 자체를 내주지 않는다. 사용자가 보행할 수 없는 이유를
접어 치울 수 있으면 안 된다. 사용자가 직접 접은 선택은 강제 펼침과 따로 기억한다.

### 미리보기가 눈이 멀어 있었다

전 단계를 훑다가 발견했다. **제품 결함이 아니라 도구의 문제다.** 미리보기는 `firstRunPreviewStage`
하나만 바꾸고 화면은 `renderStage = firstRunPreviewStage ?: snapshot.stage`로 그리는데, 팀이 새로
붙인 표면들이 `renderStage` 대신 실제 `snapshot.stage`를 보고 있었다.

- 계정 UI: 실제 단계가 계속 1단계(=계정 단계)라 어느 단계를 미리봐도 이메일·비밀번호가 안 사라졌다.
- `mayTrain`·`mayCheckDevice`: 실제 단계가 1단계라 `false`. 제목만 바뀌고 컨트롤은 통째로 숨어
  권한·기기점검·교육 단계가 제목 한 줄 + 검은 화면이 됐다.

표시 판정 세 곳을 `renderStage`로 통일했다. 활성화·증거 생성·신원 판정은 그대로 `snapshot`만 본다.

미리보기 순회도 SMS 시절 12단계를 돌고 있었다. 그중 4개는 이메일 대체 이후 어느 경로로도 지나가지
않는다. 실제 제품 흐름인 `EMAIL_ACCOUNT_V4` 6단계와 완료 화면으로 바꿨다.

### 첫 실행 뼈대

- 진행 표시를 맨 위로 올렸다. 고지 토글 아래에 있어 어디까지 왔는지가 부차 정보처럼 보였다.
- 펼치기·접기·전문 보기 토글 8개를 테두리만 있는 부차 면으로 내렸다. 채운 토글 둘이 화면 맨 위에서
  본문을 눌러, 그 단계에서 할 일이 세 번째로 눈에 들어왔다.
- DEBUG 미리보기 컨트롤을 제목과 컨트롤 사이에서 맨 위로 뺐다.

### 검증

- Android 유닛 1,311건 중 11건 실패. `origin/current` 단독도 같은 11건이 실패한다. 신규 0건.
- `compileReleaseKotlin` 통과(`WALKSAFE_SOURCE_COMMIT`·`WALKSAFE_GATEWAY_ORIGIN` 필요).
- 에뮬레이터로 첫 실행 10화면과 보행 화면을 전부 눈으로 확인했다. 스크린샷 묶음은 저장소 밖이다.
- 기존 정적 테스트 여섯이 깨졌다. 전부 오버레이 자식 순서나 구역 경계를 문자열로 고정한 것이라
  **요구는 그대로 두고 읽는 위치만 옮겼다.** 팀 테스트가 문자열로 고정한 줄과 부딪힌 곳에서는
  내 쪽을 양보했다(온보딩 머리말 번호, 이탈 뷰 이름).

### 남은 것

- **TalkBack 낭독 순서를 듣지 않았다.** 접근성 트리 구조는 정적 테스트로 고정했지만 스크린리더로
  직접 확인하지 않았다. 주 사용자가 시각장애인인 제품이므로 실기기에서 한 번 들어야 한다.
- 준비 표면이 접힌 상태는 못 봤다. 에뮬레이터가 첫 실행을 완료할 수 없어 항상 강제 펼침이다.
- 2단계는 제목이 인증번호를 입력하라고 하는데 입력칸이 「새 계정 만들기」 뒤에 접혀 있다. 팀이 만든
  흐름이라 임의로 바꾸지 않았다. 팀 확인 대상이다.

### 상태 문구 정리

준비 표면 세 덩어리가 「무차별 나열」로 보인다는 지적을 받았다. 실제로 그 문구는 이미 타입이 있는
글이었다 — 「설명 문단 / 상태 / 원인: / 다음 행동:」 네 부분이고 라벨이 문자열 안에 그대로 들어 있다.
그런데 전부 같은 크기·같은 색으로 찍혀서 어디가 상태이고 어디가 할 일인지 눈으로 구분되지 않았다.

`applyWsStatusText`가 그 구조를 읽어 span 으로 입힌다.

- 「원인:」 바로 앞 줄이 상태 줄이다. 굵게·1.15배로 세우고, 「사용 불가」·「제한」·「교정 필요」면
  warning 색, 나머지는 emphasis 색을 준다.
- 「원인:」·「다음 행동:」·「확인 완료:」·「기기 점검:」은 라벨만 굵게 하고 내용은 본문 색으로 둔다.
- 나머지 설명 문단은 0.94배로 낮춘다.
- 세 덩어리는 각자 테두리 있는 카드 면을 갖는다. 경계가 없으면 한 벽으로 읽힌다.

**문자열은 한 글자도 바꾸지 않았다.** 요구와 테스트가 이 문구를 고정하고 있고, `contentDescription`
도 원문 그대로 두어 TalkBack 은 지금처럼 한 덩어리로 읽는다. 회귀 테스트가 이 두 가지를 고정한다.

### 글꼴

시스템 한국어 글꼴(Noto Sans CJK KR)을 쓰고 있어 굵기 대비가 약했다. Pretendard v1.3.9 를 번들했다.

- `res/font/` 에 OTF 3종(Regular·Medium·Bold, 합 4.5MB). TTF 는 같은 굵기가 2.7MB씩이라 OTF 를 썼다.
- `AppTheme` 의 `android:fontFamily` 로 모든 텍스트 위젯의 기본 글꼴을 잡는다.
- 코드에서 굵기를 지정하던 `Typeface.create("sans-serif-medium", …)` 세 곳을 `wsTypeface()` 로 바꿨다.
  그대로 두면 그 자리만 시스템 글꼴로 되돌아가 한 화면에 두 글꼴이 섞인다. 회귀 테스트가
  `sans-serif-medium` 이 다시 나타나면 실패한다.
- SIL Open Font License 1.1 이다. 전문을 `apps/android/licenses/pretendard-OFL-1.1.txt` 에 넣었다.
  OFL 은 예약 글꼴 이름을 지키고 라이선스를 함께 배포할 것을 요구한다.
- debug APK 는 88.5MB 로 변화가 없다시피 하다. release 는 별도 확인이 필요하다.
- 접근성 최소 글자 크기 판정(`MIN_INTERACTIVE_TEXT_SP`)은 글꼴과 무관하게 그대로다.

### 동의 화면 두 곳을 같은 형태로

사용자가 참고 화면(전체 동의 → 항목별 체크 + 그 자리 약관 상자 → 확인)을 보여 주며 「이런 식의
회원가입 화면을 얘기한 것」이라고 지적했다. 그때까지 내가 한 것은 기존 위젯의 위계·마감이었고 구조는
그대로 뒀으므로, 지적이 맞다.

두 화면 모두 항목별 원문을 이미 갖고 있어 지어낼 필요가 없었다.

- 계정 가입 동의: `accountConsentDisclosure` 한 덩어리에 `[필수] …:` / `[선택] …:` 라벨이 들어 있다.
- FP-013 통합 동의: `INTEGRATED_CONSENT_DISCLOSURE_KO` 에 `1. 신고·진단용 raw v2:` 식으로 번호가 있다.

`documentClauseOrNull(원문, 라벨, 구분점)` 로 잘라 쓴다. 못 찾으면 `null` 을 돌려 호출부가 원문 전체를
보이게 한다 — 지어낸 문구로 때우지 않는다.

- 항목마다 체크(또는 허용/거부 버튼) + 조항 상자. 상자는 높이를 132dp 로 제한하고 안에서 스크롤한다.
  낭독은 잘리지 않는다. TalkBack 은 보이는 만큼이 아니라 텍스트 전체를 읽는다.
- 맨 위 전체 동의. 한 번에 켜되 개별 항목은 그대로 각자 바꿀 수 있다.
- 필수 진행 상태를 문장으로 알린다(`refreshAccountConsentSummary`). **참고 화면은 확인 버튼을 잠가
  남은 것을 알리지만 잠긴 버튼은 눌러도 아무 말을 하지 않는다.** 주 사용자가 화면을 보지 않으므로
  버튼은 살려 두고 남은 항목을 live region 문장으로 알린다. 필수 판정 자체는
  `SignupConsentSelections.requiredGranted` 그대로다.

이 과정에서 기존 버그가 하나 드러났다. `RAW_SOURCE_COLLECTION` 조항을 「원본 수집」으로 찾고 있었는데
문서가 쓰는 이름은 「신고·진단용 raw v2」다. 항상 못 찾아 그 항목만 문서 전체가 실렸다. 카드 안에
접혀 있을 때는 눈에 안 띄다가 상자로 바꾸니 드러났다.

### 가입을 두 화면으로

「로그인·새 계정 창과 이용약관 동의 창이 서로 다른 페이지여야 하지 않나」는 지적을 받았다. 맞다.
항목별 조항 상자를 넣고 나니 한 화면에 로그인 입력·약관 6항목·가입 정보가 세로로 다 붙어, 조항
여섯 개를 지나야 이메일 칸에 닿았다.

`AccountSignupStep`(CONSENT, DETAILS)을 두고 가입을 두 화면으로 나눴다.

- 약관 화면: 전체 동의 + 6항목 + 조항 상자 + 「동의하고 계속」. 이메일·비밀번호 칸은 내린다.
  그 화면에서 할 일은 동의뿐이다.
- 가입 정보 화면: 이메일·비밀번호·생년월일 + 「이메일 인증번호 받기」.
- 인증번호는 그다음 단계(ACCOUNT_CREATED)가 이미 자기 화면으로 그린다.

**단계 enum 을 새로 만들지 않았다.** 표시 단계일 뿐이라 `FirstRunOnboardingStage`, 증거, 영수증,
상태기계는 그대로다. 가입 창을 닫으면 CONSENT 로 되돌아간다. 팀이 고정한 컨테이너 순서
(`accountSignupControls` 를 accountAccessControls 안에 두는 것)도 그대로다.

안내 문장도 화면을 따라간다 — 약관 화면에서는 「약관과 개인정보 처리에 동의하세요…」, 가입 정보
화면에서는 기존 「가입 정보를 입력하고 인증번호를 받으세요.」

검증 중 `AndroidPrivacyDeletionAccountDeletionTest` 1건이 한 번 실패했다가 `--rerun-tasks` 클린
재실행에서 통과했다. 플레이키로 보이며 이번 변경과 무관하다. 오늘 두 번째 플레이키다.

### 완료 화면과 보행 화면을 나눔

미리보기 10/10 이 완료 상태와 보행 화면을 한 스크롤에 겹쳐 그리고 있어 둘 중 어느 것도 제대로 볼 수
없다는 지적을 받았다. 순회에 자리를 하나 더 뒀다.

- 10/10 「완료」: 완료 문구와 준비 표면. 보행 화면은 그리지 않는다.
- 그다음 「보행 화면」: 온보딩 상태문·진행바·개인정보 토글·준비 표면을 전부 내리고 `runtimeControls`
  만 그린다. 완료 후 앱이 머무는 화면이 실제로 이 모습이다.

DEBUG 표시 경로일 뿐이고 `firstRunPreviewWalkScreenOnly` 하나로 판정한다. 제품 동작은 그대로다.

진행바를 앞에서 껐다가 뒤쪽 대입이 다시 켜는 실수를 한 번 했다. 표시 판정이 한 함수 안에서 두 번
쓰이는 자리를 고칠 때는 나중 대입까지 봐야 한다.

### 접근성 순회 점검

TalkBack 을 에뮬레이터에 켜 봤으나 발화 문자열은 logcat 으로 나오지 않는다(오디오 포커스 요청만
찍힌다). 대신 접근성 트리를 순회 순서대로 뽑아 중복·누락·역할을 검사했다. `uiautomator dump` 는
importantForAccessibility 가 아닌 노드를 빼므로 그 순서가 스크린리더 순회에 가깝다. **직접 들은
것은 아니다.** 실기기 청취는 여전히 남아 있다.

세 화면(가입 약관, 보행, 통합 동의, 완료)에서 결함 셋이 나왔다.

1. **조항 상자가 버튼으로 읽혔다.** 오늘 넣은 `applyWsClauseBox` 가 `movementMethod` 를 붙이면서
   클릭 가능으로 잡혔고, 스크린리더가 「버튼, 두 번 탭하여 활성화」로 읽는데 눌러도 하는 일이 없다.
   손가락 스크롤은 그대로 두고 클릭 역할만 뗐다(`isClickable = false`).
2. **보행 상태를 스크린리더가 영영 못 들었다.** `statusText.contentDescription` 이 고정 문자열
   「WalkSafe 상태」라 실제 값(「보행 시작 대기」 등)을 덮고 있었다. 내 변경 이전부터다. 라벨과 값을
   함께 주도록 고쳤다. 자동 낭독은 계속 꺼 둔다(`LIVE_REGION_NONE`) — 500ms 마다 갱신되는 줄이라
   끼어들면 안 된다. 초점을 옮겼을 때만 들린다.
3. **「목적지 검색」이 연속 두 번 들렸다.** 입력칸 hint 와 검색 버튼 이름이 같았다. 보이는 hint 는
   그대로 두고 입력칸의 낭독 이름만 「목적지 입력」으로 구분했다.

고친 뒤 네 화면 모두 연속 중복 0건이다. 조항이 그 항목의 컨트롤보다 먼저 읽히는 순서도 확인했다 —
약관을 읽고 나서 선택하는 순서다.

## 음성인식 재검토 (daylog 다음 작업 2번)

**어제 적어둔 「빠진 pause/resume 및 비가역 명령 확인이 미구현」은 틀렸다.** 실제로는 구현돼 있고
배선까지 돼 있다.

- `WalkSessionVoiceControlPolicy` 가 「보행 일시정지」·「보행 재개」·「보행 종료」를 정확 문구로 받고,
  확신도 하한을 넘지 못하면 아무 것도 하지 않는다.
- 비가역 명령인 종료는 `REQUEST_END` → `CONFIRM_END`/`CANCEL_END` 2단계이고, 보류 토큰이 runtime
  epoch 에 묶여 있어 epoch 이 바뀌면 무효가 된다.
- `MainActivity` 가 `evaluate()` 와 `invalidatePendingEnd()` 를 모두 호출한다.

온디바이스 인식도 이미 쓴다 — `SpeechRecognizer.createOnDeviceSpeechRecognizer`.

### 실제로 빠져 있던 것: 듣기 시작·끝 신호

FP-025 는 「듣기 시작·종료 신호」를 요구하는데, 그 신호가 **버튼 글자와 화면 상태 문자열뿐**이었다.

```kotlin
private fun updateVoiceRecognitionSignal(label: String) {
    listOf(voiceReportButton, walkSafetyVoiceButton).forEach { it.text = label; it.contentDescription = label }
    updateNavigationStatus("voice=…")
}
```

화면을 보는 사람에게만 도착한다. 이 앱의 주 사용자에게는 마이크가 열린 것도 닫힌 것도 알 방법이
없었다. 진동 신호를 붙였다.

- 시작 `[0,35]`, 끝 `[0,35,45,35]`. 소리가 아니라 진동인 이유는 이 신호가 나가는 시점에 마이크가
  이미 열려 있어 소리를 내면 그대로 인식 입력이 되기 때문이다.
- 위험 신호와 겹치지 않게 아주 짧게 뒀다. 위험은 단발 220ms(WARNING)와 점점 길어지는 3연타(STOP),
  경로·장착은 단발 120ms 다.
- 실패로 끝나는 경로(`onError`)에도 끝 신호를 붙였다. 없으면 사용자는 계속 듣고 있는 줄 안다.
- 인식 중 다른 피드백을 억누르는 규칙에는 걸지 않았다. 그 규칙은 인식 중 안내가 끼어드는 것을 막는
  것이고, 이 신호는 인식 그 자체를 알리는 것이라 억누르면 목적이 사라진다.

### 호출어(길라잡이)는 여전히 막혀 있다 — 우리 탓이 아니다

`WakeWordController` 는 default-off 관문까지만 있고 `PRODUCTION_WAKE_WORD_PROFILE = null` 이라
절대 시작하지 않는다. 앱 어디에서도 이 컨트롤러를 쓰지 않는다(테스트만 참조). 실행 계획 문서가
이유를 적어 뒀다 — **승인된 한국어 호출어 asset 이 없어 default-off 경계까지만 구현하며 FP-025
완료로 주장하지 않는다.** asset 승인이 선행 조건이지 코드 문제가 아니다.

### FP-028·FP-030 은 오늘 UI 작업이 그대로 그 요구다

`RQ-FP-028-001`(조작 화면을 TalkBack 만으로 이해·완료), `RQ-FP-030-001`(큰 글자·대비·터치영역·상태
설명)이 오늘 한 작업과 같은 범위다. 오늘 잡은 접근성 결함 셋(조항 상자 버튼 오인, 보행 상태 낭독
불가, 이름 중복)이 FP-028 증거에 해당한다. 다만 두 요구 모두 `DRAFT · NOT_APPROVED · 시험 NOT_RUN`
이고 실기기 검증을 출시 조건으로 걸고 있다.

## 음성 모델 재검토 (daylog 다음 작업 3번)

### 「확인 중」은 결함이 아니었다

기기 점검이 「오프라인 한국어 음성 안내」를 확인 중으로 잡고 있던 이유는 단순하다. `probeOffline
KoreanTextToSpeech` 는 `AndroidStartupCapabilityProbe.start()` 안에서만 돌고, 그 probe 는 로그인
이후 기기 점검 runtime 에서만 시작한다. 에뮬레이터는 로그인을 못 하므로 영원히 확인 중이다.
순서가 로그인 → 기기 점검 → probe → 확인 → 보행으로 일관돼 있다.

probe 자체는 제대로 판정한다. TTS 초기화 성공 + `isLanguageAvailable(KOREAN)` + **네트워크가 필요
없는** 한국어 voice 가 하나라도 있을 것을 요구한다(`!voice.isNetworkConnectionRequired`).

### 실제 결함: 회복 경로가 없었다

오프라인 한국어 음성이 없으면 앱이 이렇게 말하고 끝났다.

> 이 휴대폰에서는 WalkSafe를 시작할 수 없습니다. 사용할 수 없는 기능: 오프라인 한국어 음성 안내

**막다른 길이다.** 이건 기기가 못 하는 일이 아니라 음성 데이터를 내려받으면 풀리는 문제다.
`RQ-FP-029-001` 은 「회복 가능한 문제에만 재시도나 설정 이동을 제공한다」고 요구하는데, 정작 회복
가능한 이 항목에 경로가 없었다.

- `USER_INSTALLABLE_REQUIREMENTS`(온디바이스 STT, 오프라인 한국어 TTS)를 카메라·ARCore 같은
  하드웨어 항목과 구분했다.
- 그 항목이 막고 있을 때만 「다음 행동: …은(는) 휴대폰 설정에서 음성 데이터를 내려받으면 사용할 수
  있습니다」를 붙이고 「한국어 음성 데이터 설치 열기」 버튼을 띄운다.
- 버튼은 표준 설치 intent(`ACTION_INSTALL_TTS_DATA`) → 음성 입력 설정 → 앱 설정 순으로 내려간다.
  어디로도 갈 수 없으면 그 사실을 말한다. **눌렀는데 아무 일도 안 일어나는 것이 가장 나쁘다.**

`RQ-FP-027-001` 의 차단(오프라인 음성 없으면 보행 시작 안 함)은 그대로다. 막는 것은 그대로 막되
고치는 길을 준 것뿐이다.

### voice/ 는 여전히 제품 경로가 아니다

`voice/` 는 faster-whisper STT + rule intent + Qwen3-TTS 를 제공하는 loopback 프로토타입이고
`LEGACY_REFERENCE` 다. `docs/status/voice_stt_tts_status.md` 기준일은 2026-07-13 이며, 그 문서도
Android 는 플랫폼 `SpeechRecognizer`/`TextToSpeech` 를 쓴다고 적고 있다. 제품 Android 경로는
온디바이스이고, Gateway `/api/speech/*` 는 별도 서버 보조 경로다. 안전 중대 안내는 서버 성공 여부와
무관하게 내장 TTS·진동으로 유지한다는 경계도 그 문서에 있다.

### 확인하지 못한 것

설치 버튼이 실제로 화면에 뜨는 것은 못 봤다. 그 버튼은 probe 가 「사용 불가」를 판정했을 때만
나오는데 에뮬레이터는 로그인을 못 해 probe 가 돌지 않는다. 배선은 정적 테스트로 고정했다.

### 음성이 실제로 나가는지 실측

위 두 절은 코드 경로만 본 것이라 「그래서 음성이 어떻게 됐는지」에 답하지 못했다. 에뮬레이터에서
앱이 `speakInteraction` 을 타게 하고 logcat 을 봤다.

```
GoogleTTSServiceImpl: Synthesis request for locale kor-KOR and name ko-KR-language
GoogleTTSServiceImpl: TTS dispatch: ko-kr-x-ism-seanet-embedded
MediaFocusControl: requestAudioFocus() ... CONTENT_TYPE_SPEECH
                   callingPack=kr.co.hanium.dreamup.walksafe
                   ...AndroidFeedbackActuator$$ExternalSyntheticLambda0
```

- 한국어 합성 요청이 실제로 나갔다.
- **`embedded` 음성으로 합성됐다.** 기본 설정은 `ko-kr-x-ism-server`(네트워크 음성)인데 실제 dispatch 는
  embedded 다. `RQ-FP-027-001` 이 요구하는 「네트워크 없이 한국어 재생」이 이 기기에서 성립하고,
  probe 가 `!voice.isNetworkConnectionRequired` 로 찾는 그 음성이 실재한다는 뜻이다.
- 오디오 포커스를 잡은 주체가 우리 앱의 `AndroidFeedbackActuator` 다.

온디바이스 STT 도 서비스가 있다 — `com.google.android.as/…AiAiSpeechRecognitionService`.
`createOnDeviceSpeechRecognizer` 가 붙을 대상이 존재한다.

**소리를 귀로 듣지는 않았다.** 합성 요청이 나갔고 오디오 포커스를 잡았다는 것까지가 증거다. 발음,
속도, 위험 안내가 다른 음성을 제대로 끊는지는 들어야 안다. STT 도 서비스 존재만 확인했고 실제로
「보행 일시정지」를 알아듣는지는 마이크에 대고 말해야 한다. 에뮬레이터 마이크로는 의미 있는 시험이
되지 않는다.

정리하면 **모델은 있고 경로도 붙어 있으며, 남은 것은 실기기 청취다.**
